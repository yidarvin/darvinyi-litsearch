ACEBench: Who Wins the Match Point in Tool Usage?

A 2,000-item, Chinese/English-parallel tool-use benchmark that splits evaluation into three regimes — Normal (clean instructions), Special (broken or irrelevant instructions), and Agent (multi-turn sandbox execution) — and scores each with cheap, deterministic checks instead of an LLM judge.

What problem is this solving?

By early 2025 there were already several tool-use benchmarks for LLMs — MetaTool, API-Bank, StableToolBench, the Berkeley Function-Calling Leaderboard (BFCL), τ-bench, HammerBench — and the authors argue each leaves a gap uncovered. Table 1 of the paper lays the comparison out on five axes: whether grading is LLM-free (deterministic, not an LLM-as-judge), whether the benchmark tests robustness to imperfect instructions, whether it is interactive (the model acts inside a stateful environment rather than answering one-shot), whether it probes atomic-level capability (isolating a single parameter type at a time), and whether it includes personalization (user-profile-conditioned requests). By the paper's own accounting, no prior benchmark in the table checks more than two of these five boxes at once: MetaTool and API-Bank are LLM-free but neither robust nor interactive; BFCL adds robustness but not interactiveness; τ-bench adds interactiveness but not robustness; HammerBench adds robustness but relies on LLM-based grading and isn't interactive. None of the six comparison rows checks atomic-level or personalization at all.

The authors also point to a structural complaint about multi-turn evaluation specifically: they characterize BFCL's and HammerBench's multi-turn dialogues as assembled from predefined, fixed content combinations rather than dynamically generated interactions, which limits how much they can stress genuinely adaptive, real-world conversational behavior. Combined with the cost problem — StableToolBench and ToolLLM's evaluation pipelines lean on large models to judge correctness, which is both expensive and, the authors argue, unstable across runs — this motivates a benchmark that is simultaneously broader in scenario coverage, finer-grained in what it isolates, and cheap and deterministic to score.

The method

ACEBench is built from 4,538 synthetic APIs spanning 8 top-level domains and 68 sub-domains (technology, finance, entertainment, society, health, culture, environment, and others), assembled into 2,000 annotated test entries split evenly across two linguistically parallel versions, Chinese and English. The APIs are synthetic rather than scraped from live services specifically so the benchmark doesn't rot when a real API changes shape — but they're generated with real-world API documentation as a reference, via a "self-evolving" hierarchical API context tree: an LLM expands the tree node by node, using each new API to inform the next, so the pool grows in both breadth (more domains) and depth (more APIs per domain) rather than repeating similar calls.

The three evaluation categories are built by different pipelines. Normal and Special data are fully LLM-generated: three to six candidate APIs are sampled per instance (randomly for most cases, via graph-based sampling when the instance specifically needs similar APIs or a multi-turn arc), then a dialogue is produced either by a template-based single generator (for simple, fixed-structure cases) or by a three-agent pipeline in which separate User, Assistant, and Tool agents interact to simulate a more natural conversation. Normal data is further split into Single-Turn, Multi-Turn, Similar-API, Preference (personalized, profile-conditioned requests), and Atom (candidate functions restricted to a single parameter type — number, enum, list, bool, or object — to isolate whether parameter type itself affects fill-in accuracy) subcategories. Special data injects three kinds of instruction defects: Incomplete (a required parameter is missing from the request), Error (a supplied parameter violates the function's format or allowed values), and Irrelevant (none of the candidate functions can actually satisfy the request).

Agent data, by contrast, is hand-built by domain experts rather than generated. The authors abstract four real-world scenario families — mobile-app actions (alarms, reminders, messaging), a food-delivery platform, banking (deposits, withdrawals, transfers, loans), and a travel-booking system — into runnable Python classes with explicit state (order status, account balance, login state) and business rules ("before ordering takeout, you need to obtain the user's account and log in"). Multi-turn dialogues are then run inside this sandbox with GPT-4o playing the user, so the assistant under test has to track state across turns and call functions against a live, stateful environment rather than a static candidate list. All three data streams pass through a shared verification pipeline: an automated rule-based check (API-definition clarity, call executability, dialogue-answer consistency, cross-sample consistency), then an LLM-assisted screening pass, then a two-round human expert review with a third expert reconciling disagreements, iterated three times.

Grading differs by category, and this is the benchmark's central design choice: none of the three uses an LLM as a judge. Normal data is scored by AST-parsing the model's function call and comparing function name, argument names, and argument values against a ground-truth answer (or, when multiple answers are valid, against a candidate pool) — a binary 1/0 per instance. Special data is scored on whether the model correctly flags the specific defect (missing parameter, invalid parameter, or task-function mismatch) rather than attempting a call it shouldn't make. Agent data uses two metrics: End-to-End Accuracy (1 only if every tracked state attribute in the sandbox matches the target exactly after the dialogue, else 0) and Process Accuracy, n⁄m where m is the length of the ideal function-call sequence and n is how many of the model's calls match it. A model's headline Overall score is a sample-size-weighted combination of its Normal, Special, and Agent accuracies:

All Acc = A·AccNormal + B·AccSpecial + C·AccAgent,  A = √nNormal√nNormal+√nSpecial+√nAgent (B, C analogous) // weights use the square root of each category's sample size, so the smallest category (Agent, hand-built and thus scarcer) is not swamped by the two auto-generated categories

The results

The authors evaluate 21 models on the combined Chinese+English set (Table 2 of the paper): seven closed-source (GPT-4o, GPT-4-Turbo, Qwen-Max, GPT-4o-Mini, Gemini-1.5-Pro, Claude-3-5-Sonnet, Doubao-Pro-32k) and fourteen open-source, including four models fine-tuned specifically for function calling (Hammer2.1-3B/7B, xLAM-7B-r, Watt-Tool-8B). GPT-4o leads overall at 85.4%, narrowly ahead of GPT-4-Turbo at 84.5%. Among the open-source models, the best performer isn't the largest one: Qwen2.5-Coder-32B-Instruct scores 79.6%, ahead of the much larger general-purpose Qwen2.5-72B-Instruct (74.7%) and DeepSeek-V3 (74.8%), and high enough to beat five of the seven closed-source models — Qwen-Max (78.4%), GPT-4o-Mini (72.5%), Gemini-1.5-Pro (70.7%), Claude-3-5-Sonnet (68.9%), and Doubao-Pro-32k (59.4%). Claude-3-5-Sonnet's 68.9% overall — sixth of seven closed-source models, ahead of only Doubao-Pro-32k — is a notably weaker showing than its typical function-calling reputation elsewhere.

Breaking a model's score into its three category components (Normal-summary, Special, Agent) shows Agent is the weakest category for most — but not all — models: 17 of the 21 models score lowest on Agent. The remaining four (Llama-3.1-70B-Instruct, Hammer2.1-7B, xLAM-7B-r, and Hammer2.1-3B) actually score lower on Special than on Agent — for example Llama-3.1-70B-Instruct gets 75.5% on Normal, 42.3% on Agent, but only 38.3% on Special. Table 4 (which reports only six models with a full Multi-Turn/Multi-Step, End-to-End/Process breakdown) shows this Agent weakness is uneven within the category too: GPT-4-Turbo's Multi-Step End-to-End accuracy is 85.0% — its best end-to-end result in the table (its Multi-Step Process Accuracy, 89.5%, is higher still) — while its Multi-Turn End-to-End accuracy is only 50.0%, meaning the single-interaction agent tasks are comparatively easy for it but tasks requiring the model to track state across a genuine back-and-forth with a simulated user are not.

Fine-tuning specifically for tool calling doesn't uniformly help even on Normal: Watt-Tool-8B (75.6% Normal) and Hammer2.1-7B (62.8%) post the strongest Normal-category scores among the fine-tuned group, but Hammer2.1-3B (18.7%) posts the lowest Normal score of all 21 models evaluated and xLAM-7B-r (33.7%) the third-lowest, with the general-purpose, similarly-sized Llama-3.2-3B-Instruct (29.6%) sitting between them. All four nonetheless collapse on Special: Watt-Tool-8B's Special score is 6.0%, xLAM-7B-r's is 2.7%, and Hammer2.1-3B's is 1.0% — a much steeper drop than their Normal scores would predict, well below general-purpose models of similar or smaller size. Table 5's per-model Error-Detection/Error-Correction counts on Special data show this is mostly an error-detection failure rather than an error-correction one: xLAM-7B-r registers 195 Error-Detection failures against just 1 Error-Correction failure, and Hammer2.1-3B 197 against 0, meaning these models almost never recognize the instruction is broken in the first place, rather than recognizing the problem but describing it poorly. Table 3's per-defect-type accuracy breakdown tells the same story from a different angle: xLAM-7B-r scores only 1.0% on Incomplete, 3.0% on Error, and 4.0% on Irrelevant.

Every one of the seven closed-source models scores higher on the Chinese split than the English split (Tables 7 and 8) — GPT-4o goes from 81.1% (English) to 89.6% (Chinese), GPT-4-Turbo from 80.3% to 88.6%, Claude-3-5-Sonnet from 62.2% to 75.6%, all the way down to Doubao-Pro-32k's smaller 56.0%→62.8% gap. A scaling-law sweep across Qwen2.5-Instruct and Qwen2.5-Coder (3B–32B/72B) finds performance rising with parameter count but with diminishing returns between 32B and 72B; the code-tuned Qwen2.5-Coder variant actually trails the general Qwen2.5-Instruct variant at the two smallest matched sizes (3B: ~0.28 vs ~0.38; 7B: ~0.50 vs ~0.55) before overtaking it from 14B up (14B: ~0.74 vs ~0.56; 32B: ~0.77 vs ~0.67) — a crossover, not a uniform lead.

// does it hold up?

The eval read

The headline design choice — grade everything deterministically (AST matching, defect-flag matching, sandbox state matching) instead of paying an LLM judge — is the paper's strongest claim and it largely holds up on inspection: Normal and Special scoring genuinely need no model in the loop. Agent scoring is more mixed than Table 1's unqualified "LLM-Free ✓" for ACEBench suggests, though: GPT-4o plays the user in every Agent dialogue, so a model's Agent score is not independent of GPT-4o's specific behavior as a simulated interlocutor — a different simulator model could plausibly change which assistant models look strong. The correctness scoring (state-matching against the sandbox) is deterministic; the stimulus the model under test responds to is not.

The error-analysis narrative in Section 4.2 overstates its own figure. The text says "output format error is the second most common" error type after param-value error, and cites Figure 6 (error rates broken out for the Qwen, GPT, and Qwen-Coder series). That's only true for the GPT series (20.4% output-format vs. 10.3% param-num). For the Qwen series the second-largest error type is actually param-num at 19.8%, ahead of output-format's 15.3%, and for the Qwen-Coder series the gap is wider still — param-num 25.9% vs. output-format 7.7%. The paper's summary sentence generalizes a pattern that in fact holds for one of the three model families it names, not all three.

On reproducibility: the paper reports single-run accuracy numbers throughout (Tables 2–8) with no variance, no repeated-sampling, and no stated decoding temperature — function-calling output is sensitive to both, and multi-turn Agent scores in particular (where one wrong call early in a dialogue can cascade) would benefit from an error bar. The authors are candid about two structural limitations in their own Limitations section: the LLM-generated Normal/Special data has an acknowledged "gap... compared to data from real-world applications," and Agent scenario coverage is capped by relying on manual, expert-built scenarios (four scenario families total as of this version) rather than something that scales automatically.

Baseline currency is reasonable for a benchmark whose latest revision (v8) is from November 2025, but incomplete: only two newer models — Kimi-K2 and LoopTool-8B — were added, and only to the English-only table (Table 7), not to the main Chinese+English combined comparison (Table 2) that the paper's headline numbers come from. There's no GPT-5-class, Claude-4-class, Gemini-2-class, or o1/o3-class reasoning model anywhere in the paper, so the ranking of current frontier systems on this benchmark is untested.

baselines

21 models on the combined table, spanning GPT-4o down to 3B open-source models — broad coverage of the 2024-era model generation, but the only two 2025-era additions (Kimi-K2, LoopTool-8B) appear solely in the English-only supplementary table, not the paper's headline Chinese+English comparison.

contamination

Not discussed. The benchmark and its answer set are shipped publicly on GitHub per the paper's own footnote; Normal/Special data is machine-generated from a synthetic API pool (lower reuse risk), but Agent scenario templates are a small, fixed, hand-built set of four domains that a future model could plausibly see during training or fine-tuning without detection.

what's missed

No variance/repeated-run reporting; the Agent category's correctness grading is state-based and model-independent, but the dialogue itself is generated by a fixed GPT-4o simulator, so an Agent score is partly a property of that simulator, not just the assistant under test.

would raise confidence

Multiple decoding runs with reported variance, especially on Agent; an ablation swapping the user-simulator model to check how much Agent rankings shift; a periodically refreshed leaderboard slice with a held-out, unreleased Agent scenario set to check for contamination.

// bottom line

The three-way Normal/Special/Agent split, and especially the decision to grade Special via defect-detection rather than another do-the-task pass, is a genuinely useful, cheap-to-run addition to the tool-use benchmark landscape — it catches a real failure mode (fine-tuned tool models that call functions well but can't tell when a call is a bad idea) that accuracy-only benchmarks miss. The Agent category's dependence on a fixed GPT-4o simulator and the paper's light touch on reproducibility (no variance, no contamination discussion) are the two places a reader should discount the headline numbers somewhat rather than take them as a clean, model-independent ranking.

// takeaways

What to remember

  1. ACEBench splits tool-use evaluation into three deterministically-graded regimes — Normal (clean instructions, AST-matched), Special (broken/irrelevant instructions, graded on whether the model correctly flags the defect instead of calling a function), and Agent (multi-turn sandbox execution against four hand-built scenario environments, graded by state match) — across 2,000 Chinese/English-parallel test items built from 4,538 synthetic APIs.
  2. Models fine-tuned specifically for function calling (Watt-Tool-8B, xLAM-7B-r, Hammer2.1-3B/7B) collapse on Special — down to single digits for three of the four, and to 6.0% even for the strongest of them — because they rarely detect that an instruction is broken in the first place (per Table 5's Error-Detection/Error-Correction counts), a generalization loss the paper attributes to narrow fine-tuning; two of the four (Hammer2.1-3B, xLAM-7B-r) are weak on Normal too, ranking lowest and third-lowest of all 21 models.
  3. Agent is the lowest-scoring category for most models (17 of 21) but not universally — four models, including Llama-3.1-70B-Instruct, actually score worse on Special than Agent — and every closed-source model scores measurably higher on the benchmark's Chinese split than its English split.
