MedAgentBench: A Realistic Virtual EHR Environment to Benchmark Medical LLM Agents

A 300-task, FHIR-compliant virtual EHR built from 100 de-identified Stanford patients, testing whether LLM agents can read and propose writes to clinical data through the same API surface a live EMR exposes — not just answer medical exam questions.

// the gap

What problem is this solving?

General-purpose agent benchmarks — AgentBench, AgentBoard, BFCL, τ-bench — measure whether LLMs can plan, call tools, and complete multi-step tasks, but none of them touch the clinical record systems that would make an LLM agent useful in a hospital. Medical evaluation, meanwhile, has gone the opposite direction: MedQA and MedMCQA test static, multiple-choice medical knowledge and are described by the authors as "saturated," with models already showing "superhuman performance on some structured clinical reasoning tasks." Work like CRAFT-MD and AgentClinic has separately argued that exam-style evaluation is "an over-simplification of the real-world interaction between clinicians and patients." Neither line of work asks the question this paper poses: can an LLM agent actually operate the electronic medical record — look up a lab value, aggregate vitals over a time window, document a measurement, order a test, place a medication order — through the same interoperability standard (FHIR) that real EMR vendors expose?

That gap matters because physicians spend, per the paper's own citation, roughly 27% of their time on direct clinical care and the rest on documentation and administrative work — exactly the kind of multi-step, tool-mediated task an agent (not a chatbot) would need to offload. Before any of that can be trusted in production, there needs to be a benchmark that tests agent behavior against a realistic EMR API surface, with tasks that are clinically meaningful and gradeable. MedAgentBench is built to be that benchmark: "the first benchmark requiring autonomous interactions with medical records environments," in the authors' words.

// how it works

The method

Two internal medicine physicians (co-authors Kameron Black and Jonathan Chen) wrote 300 clinically-derived tasks spanning 10 specific task types, grouped in the paper into 7 broad categories: patient information retrieval, lab result retrieval, patient data aggregation, recording patient data, test ordering, referral ordering, and medication ordering. Each task is a natural-language instruction plus a plain-language "context" sentence carrying the hospital-specific codes an agent would need (a LOINC code for a lab, an NDC for a drug, a SNOMED code for a referral) — the paper's stand-in for the site-specific EHR configuration a real deployment would have to consume. Half the tasks (150) are pure information retrieval, gradeable via GET requests only; the other half (150) require a state-changing POST — ordering a test, filing a referral, or documenting a measurement — often after a GET lookup first. The authors call these the query and action subsets.

The patient data behind these tasks is real, not synthetic: 100 patients were randomly sampled from Stanford's de-identified STARR clinical data warehouse, anchored on having an inpatient sodium lab test ordered on the morning of November 13, 2023, then backfilled with five years of lab results, vitals, procedure orders, diagnoses, and medication orders (cutoff November 13, 2018). That yields 785,207 total records — 563,426 Observation, 124,969 Procedure, 74,821 Condition, and 21,991 MedicationRequest resources — for a cohort averaging 58.15 ± 19.82 years old, 47% female. Because STARR already strips protected health information, the identifying layer (MRN, name, phone, address) is entirely synthetic: fake 7-digit MRNs prefixed with "S" (matching Stanford's real MRN format) and Faker-generated names/contact details, with all timestamps jittered per patient. So the clinical content is drawn from a real cohort; the identity layer is fabricated on top of it.

The environment is a Dockerized, open-source HAPI FHIR JPA server (deployed on a GCP c2d-standard-2 VM) that speaks the same REST API a real EMR vendor's FHIR endpoint would. The agent orchestrator — built on the AgentBench framework and inspired by BFCL — exposes nine functions: condition.search, lab.search, vital.search, vital.create, medicationrequest.search, medicationrequest.create, procedure.search, procedure.create, and patient.search. Each round, the model must emit exactly one of a bare-format GET request, a bare-format POST with a JSON payload, or finish([answers]), with no other text allowed — up to 8 rounds per task. Twelve models were evaluated at temperature 0 (o3-mini excepted): Claude 3.5 Sonnet v2, GPT-4o, GPT-4o mini, o3-mini, Gemini 2.0 Pro, Gemini 2.0 Flash, Gemini 1.5 Pro, DeepSeek-V3 (685B), Qwen2.5 (72B), Llama 3.3 (70B), Gemma2 (27B), and Mistral v0.3 (7B) — the paper's own text is inconsistent about the count (§2.5 says "11 state-of-the-art LLMs" while the introduction's contribution list and Table 3 both list these same 12; this page follows the 12-model table).

Grading is pass@1 throughout — the authors explicitly reject repeated-sampling metrics like pass@k, arguing that "the stringent accuracy requirements in healthcare applications" call for single-attempt evaluation. Query tasks are graded by comparing the agent's finish() answer against a reference solution. Action tasks are graded with hand-written "rule-based sanity checks" on the payload of the POST request the agent sends. One detail is easy to miss but load-bearing: "Given the FHIR-compliant interactive environment takes around 90 seconds to start, we decide to only send GET requests to the environment so that we do not need to re-initialize the environment for each individual task." In other words, GET requests are actually executed against the live FHIR server and its database; a POST is checked only for being valid, JSON-loadable payload data — the harness "indicate[s] success of execution to the agent system" without necessarily committing the write, and the reference-solution grader then checks the payload's content against the rule-based criteria after the fact. The write itself is never applied and read back.

// what they found

The results

Claude 3.5 Sonnet v2 tops the leaderboard with a 69.67% overall success rate, ahead of GPT-4o (64.00%) and the open-weight DeepSeek-V3 (62.67%, the best non-API model). Claude also posts the best Query SR (85.33%). But it is not the best on the harder half of the benchmark: Gemini-1.5 Pro's Action SR of 71.33% is the highest in that column — well above Claude's 54.00% — even though Gemini-1.5 Pro's overall score (62.00%) trails Claude by nearly 8 points. At the bottom, Mistral v0.3 (7B) manages only 4.00% overall, and both Mistral v0.3 and Gemma2 (27B) score a flat 0.00% on the action subset.

The paper also breaks the 300 tasks down by step count — easy (1 step), medium (2 steps), hard (≥3 steps) — and the same pattern repeats: Claude leads Easy SR (100.00%) and Medium SR (81.67%), but Gemini-1.5 Pro again takes Hard SR at 63.33%, more than double Claude's 23.33% on the hardest tier. Gemini 2.0 Flash is the extreme case of scaffold sensitivity in this table: 98.89% on Easy tasks collapsing to 17.50% on Medium and 5.56% on Hard — a 93-point spread that is the largest of any model. The paper does not explain the tier collapse specifically, but it does note a formatting problem for this model in its general error analysis: “Gemini 2.0 Flash outputs invalid actions in 54% of the cases,” because it tends to wrap its calls in a ```tool_code or ```json block despite the prompt's explicit instruction not to include any other text.

Query vs. action: across the 300 tasks, the authors write that "most models, except Gemini 1.5 Pro and Qwen2.5, are better at query-based tasks than action-based tasks." Reading the table column by column, that's true for those two named models (Gemini-1.5 Pro: 52.67% query vs. 71.33% action; Qwen2.5: 38.67% vs. 64.00%) — but Gemini 2.0 Flash shows the identical reversal (34.00% query vs. 42.67% action) without being named as an exception, so the "except" list in the prose is incomplete against the paper's own Table 3.

// does it hold up?

The eval read

MedAgentBench's central design decision — real clinical content, synthetic identity, FHIR-standard API — is a genuinely good answer to the contamination and realism problems that plague static medical QA. The patient records come from Stanford's private STARR warehouse, not a public dataset, so the specific labs, vitals, and orders behind each task are not the kind of thing a pretraining crawl could have memorized. But "realistic" needs qualifying: it is 100 patients from a single inpatient-sodium-test cohort at one hospital on one day, and the paper's own Discussion concedes "patient profiles are derived from Stanford Hospital records and are not representative of the general population, there are potential biases in the profiles." This is a snapshot benchmark, not a stress test of demographic or institutional diversity.

The bigger issue is what "success" on the 150 action tasks actually certifies. The paper states plainly that the harness "decide[s] to only send GET requests to the environment" to avoid the ~90-second FHIR server re-initialization cost per task; a POST is checked only for being "JSON-loadable" during the interaction, and the actual grading runs hand-written rule-based checks against the payload's content afterward. That means an Action SR of, say, Claude's 54.00% is a measure of whether the agent proposed the right write — correct resource type, correct codes, correct values in the JSON body — not a measure of whether that write was actually applied to the database and produced the correct downstream state. For a benchmark whose stated motivation is administrative-burden reduction inside a real EMR, that's a meaningful gap between what's measured and what would matter in deployment: a payload can be well-formed and semantically right yet still fail against idempotency, ordering, or partial-failure behavior that only shows up once a write is actually committed.

Ground truth itself is thin on process detail: the 300 tasks were written by two internal medicine physicians (co-authors Kameron Black and Jonathan Chen), but the paper attributes the reference solutions and rule-based graders only to being "manually curated" — it names no individual author for them beyond the collective “we manually write many rule-based sanity checks”, and describes no inter-rater agreement statistic, independent clinician review, or errata process for either the tasks or the graders. And despite categorizing tasks into 10 specific / 7 broad categories (Table 1), the paper never reports a per-category success-rate table — only the query/action split and the easy/medium/hard split are quantified, so a reader can't tell whether a model is weak at, say, medication ordering specifically versus referral ordering, only that it's weaker on writes than reads in aggregate.

Finally, some of the leaderboard spread is scaffold, not model, and the harness's repair behavior is inconsistent about it. The authors report a formatting habit for Gemini 2.0 Flash — without tying it to the difficulty tiers — wrapping calls in a ```tool_code or ```json block against instructions, an "invalid action" 54% of the time. For one of those two habits the harness does compensate: it strips ```tool_code separators before parsing. But that repair doesn't extend to the sibling case shown in Figure 2(b) — the same GET call wrapped in a ```json fence instead is scored as an invalid action outright, with no unwrapping and, in either case, no retry. So one formatting convention gets an ad hoc fix and a functionally identical one doesn't, and a strict single-agent, single-attempt design is still folding a chunk of format-compliance into the same number as clinical-agentic competence.

baselines

One simple agent orchestrator (built on the AgentBench framework, inspired by BFCL) run across all 12 models at temperature 0 (o3-mini excepted), fixed 8-round cap, strict literal GET/POST/finish parsing with one ad hoc repair (stripping ```tool_code fences before parsing) but no repair for the sibling ```json-fence habit and no retries at all — so scaffold-sensitivity (e.g. Gemini 2.0 Flash's code-fence habit) and genuine clinical-agent capability are folded into the same success-rate number.

contamination

Low risk on the underlying clinical facts — patient data comes from Stanford's private, de-identified STARR warehouse, not a public corpus. The benchmark suite and codebase are released publicly on GitHub, though; if the 300 reference solutions and graders ship in that release (the paper doesn't specify), the answer key itself would be exposed to any model trained or fine-tuned after the release date.

what's missed

Action-task grading checks the correctness of the proposed POST payload via rule-based sanity checks, not a verified change to the live FHIR database — the paper explicitly limits real execution to GET requests to avoid re-initializing the ~90-second-to-boot environment per task. A passing Action SR shows a well-formed, correctly-targeted write request, not a confirmed state change.

would raise confidence

A per-task-category success-rate breakdown (the paper defines 10 specific / 7 broad categories but never scores them individually); inter-rater agreement or independent clinician review of the manually-curated reference solutions and graders (the paper names no author for either); and a repair/retry ablation — extending the existing ```tool_code fix to other near-miss formats, or adding retries — to separate ad hoc scaffold-format strictness from underlying medical-agent reasoning, since the paper's own error analysis shows the two are currently conflated.

// bottom line

MedAgentBench is a real step past static medical QA — by the authors' own account, the first benchmark to make LLM agents actually operate a FHIR-standard EHR interface on real (de-identified) clinical content, and the 300-task, query/action/difficulty breakdown is a genuinely useful diagnostic surface. But its headline "success" numbers, especially on the action half, measure proposed-write correctness rather than applied-write correctness, and a non-trivial share of the model spread traces to a single unforgiving scaffold's formatting strictness rather than to differences in clinical-agentic reasoning.

// takeaways

What to remember

  1. MedAgentBench is, to the authors' knowledge, the first benchmark to test LLM agents against a FHIR-compliant, interactive EHR — 300 physician-written tasks across 10 categories, run against 100 real (de-identified) Stanford patients with synthetic identities layered on top, rather than static multiple-choice medical QA.
  2. Claude 3.5 Sonnet v2 leads overall (69.67%) and on query tasks (85.33%), but it is not the best agent for the harder write-half of the benchmark: Gemini-1.5 Pro's 71.33% Action SR and 63.33% Hard SR both beat Claude's 54.00% and 23.33% on those same columns, despite trailing Claude's overall score.
  3. "Success" on the benchmark's 150 action tasks is graded against the correctness of the agent's proposed write payload, not a verified change to the underlying database — the harness deliberately never applies POST requests to the live FHIR server, to avoid re-initializing the ~90-second-to-boot environment per task.
