T-Eval: Evaluating the Tool Utilization Capability of Large Language Models Step by Step

T-Eval breaks "can an LLM use tools" into six separately-graded sub-abilities — plan, reason, retrieve, understand, instruct, review — scored step-by-step against a human-verified gold solution path, rather than one end-to-end win-rate number.

// the gap

What problem is this solving?

Most tool-use benchmarks score an LLM agent the way a customer scores a delivery: did the final answer arrive, and was it good? ToolBench (Qin et al., 2023) grades an agent's whole solution path with a GPT-4-judged win rate against GPT-3.5; API-Bank (Li et al., 2023) mostly checks single-step tool calls; Gorilla (Patil et al., 2023) checks whether the right API was invoked. Each treats tool use as one opaque skill and compresses a multi-stage process — decide a plan, reason about the next move, pick the right tool from a list, fill in its parameters correctly, issue a well-formed call, and judge whether the tool's response actually answered the question — into a single pass/fail or win/lose number. When an agent fails end to end, that number can't say why: a wrong final answer might trace back to a bad plan, a hallucinated parameter, or the wrong tool chosen three steps earlier, and the outcome-level score looks identical in every case.

Holistic evaluation is also hostage to the tools themselves. Benchmarks built on live, real-world APIs (ToolBench draws its ~16,000 tools from RapidAPI) inherit those APIs' downtime, rate limits, and silent behavior changes as evaluation noise that has nothing to do with the model being tested. T-Eval's authors argue that without decomposing tool use into the sub-skills a working agent actually needs — and without freezing the "ground truth" so a live API's mood doesn't change the score — it's hard to tell whether a benchmark's number reflects a real capability gap or just accumulated, unlocalized noise.

// how it works

The method

T-Eval decomposes tool utilization into six abilities that map onto the actual steps of a multi-round tool-calling loop (Fig. 1): given a query and a tool list, an agent must first plan a sequence of tool calls; then, at each round, reason about what to do next, retrieve the right tool from the list, and understand what parameters it needs; then instruct — emit a correctly formatted call; and finally review the tool's response to decide whether the goal was met (and, if not, what kind of error occurred). Each ability gets its own isolated evaluation protocol: given a prefix of the gold solution path, the model is asked to predict just the next micro-decision (the next thought, the next tool, the next parameters, …), which is then compared against the gold answer for that step alone — so a model's REASON score, say, is never contaminated by whether it also got RETRIEVE right two steps later.

Most sub-abilities are graded at two difficulty levels: a loose String protocol that focuses on semantic content, and a strict JSON protocol that requires machine-parseable, product-realistic output (exact match on tool names and parameter values) — the authors added this split after finding that small models' scores got distorted by pure format failures rather than reasoning failures. REVIEW is graded differently: it's a five-way multiple-choice task (Success / Internal Error / Input Error / Irrelevant Response / Unable to Accomplish) with no String/JSON split.

PLAN score = longest ordered chain in the optimal pairing between predicted and gold action sequences // pairwise action similarity via Sentence-BERT; optimal pairing found with Hopcroft–Karp matching (§2.2.2, Appendix C)

The test data itself is built by a human-verified, multi-agent pipeline rather than by scraping real tool-use logs. First, 15 tools are hand-curated across six everyday domains (Research, Travel, Entertainment, Web, Life, Financials) with manually written, complete documentation — the authors note that tools pulled wholesale from ToolBench's RapidAPI pool often have inconsistent or missing docs, which would conflate "the model failed" with "the tool description was bad." GPT-3.5 then samples 2–3 tools at a time and drafts candidate queries, which GPT-4 refines for feasibility and diversity. To generate the gold solution path for each query, the authors deliberately split annotation across three separate GPT-3.5 roles — a planner, an executor, and a reviewer — rather than having one model role-switch through the whole chain the way ReAct or plain chain-of-thought would; they argue this reduces the error accumulation a single agent produces when it has to be planner, actor, and critic at once. Humans then verify and filter the result. Of 1,500 initial instruction-solution pairs, 553 survive two rounds of human verification, and get sliced into the six ability-specific subsets — 23,305 test cases in total (INSTRUCT 2,660; RETRIEVE 6,426; PLAN 553; REASON 6,426; REVIEW 487; UNDERSTAND 6,753), averaging 5.8 tool-calling steps per annotated solution path. Because every sub-ability is graded against this frozen, pre-recorded gold path rather than a live tool response, T-Eval sidesteps the API-instability problem entirely — no tool needs to actually respond during evaluation.

// what they found

The results

The authors evaluate 20 models: three API-based (Claude-2.1, GPT-3.5-turbo-16k, GPT-4-1106-preview) and 17 open-source models spanning roughly 7B, 13–14B, and 70–72B parameter scales (LLaMA2, CodeLLaMA, Qwen, InternLM, Baichuan2, WizardLM, Vicuna, AgentLM, Mistral, ChatGLM3) — figures on this page follow the arXiv preprint linked above; the ACL camera-ready's Table 1 adds one further open-source row, InternLM-20B (Overall 53.5, which would place it sixth of eighteen open-source rows); it isn't tallied in the counts below, and including it would not change any of them. GPT-4 posts the highest Overall score, 86.4, ahead of GPT-3.5 (84.0) and Claude2 (78.8). Among open-source models, the largest, Qwen-72B, reaches 71.4; the paper describes Qwen's rise from 7B to 72B as "significantly reducing the gap between open-source and API-based models" relative to smaller Qwen checkpoints, though a roughly 15-point Overall gap to GPT-4 remains even at 72B. Model scale helps but isn't the whole story: Qwen-7B's Overall (59.5) already beats four of the five other 13B-class open models (LLaMA2-13B 37.3, Vicuna-13B 48.1, WizardLM-13B 49.0, Baichuan2-13B 50.3 — only its own family's Qwen-14B, at 66.3, scores higher) and two of the three 70B-class ones (WizardLM-70B 44.2, LLaMA2-70B 53.0) — the paper credits this to Qwen's human-in-the-loop, format-aware instruction tuning rather than raw parameter count.

The String/JSON split exposes a second, largely orthogonal failure mode: strict, product-realistic formatting collapses some models' scores independent of their underlying reasoning. LLaMA2-7B's INSTRUCT score falls from 68.7 (String) to 0.2 (JSON); CodeLLaMA-7B falls from 96.0 to 0.9 on the same subset. The direction is not universal, though, and INSTRUCT is where it reverses: the three Qwen models and Baichuan2-13B all score far higher in JSON than in String there — Qwen-72B 27.8 → 98.3, Qwen-14B 49.7 → 97.6, Qwen-7B 28.7 → 94.2, Baichuan2-13B 8.0 → 51.7. Qwen-72B's 27.8 is the lowest single cell in its whole row, and it drags the model's INSTRUCT ability to 63.1, its second-weakest of the six behind REASON (59.5). So “JSON is the harder format” holds for most abilities but inverts sharply on instruction-following, where a model tuned to emit structured output does better when asked for structure. The gap shows up even in the model that comes closest to matching GPT-4 on raw understanding: Qwen-72B's UNDERSTAND-String score (84.5) is close to GPT-4's (83.2), but Qwen-72B's UNDERSTAND-JSON score (66.1) is more than 20 points below GPT-4's own JSON score on the same subset (88.3) — the paper reads this as evidence that open-source models understand tool parameters about as well as GPT-4 in the abstract, but lose most of that edge the moment the answer has to come back as valid, exact-match JSON. Tool retrieval is, in the paper's own words, "a relatively challenging task for most LLMs" under the strict protocol: even the largest open-source model's RETRIEVE-JSON score, Qwen-72B's 65.0, sits more than 20 points below GPT-3.5's 86.2 on the same column. REVIEW shows a similarly wide gap at the top: most open models cluster in the 50s–60s while GPT-4 leads at 94.5. (One provenance note on this format-gap discussion: the arXiv preprint's §4.2 text attributes a "65.6% (25 points larger)" PLAN string-vs-JSON gap to Baichuan2-13B, but Table 1's Baichuan2-13B PLAN row is actually 69.5/52.1, a 17.4-point gap — 65.6/39.0 belongs to Baichuan2-7B's row instead. The ACL camera-ready silently corrects the text to "it achieves 69.1% when evaluated with string format, which is 17.4 points higher than its JSON format (52.1%).")

To check that the decomposed score isn't measuring something disconnected from holistic quality, the authors re-run six representative models on ToolBench's own end-to-end win-rate metric (a GPT-4 judge comparing full solution paths against GPT-3.5-turbo) and plot it against T-Eval's Overall score (Fig. 4): the two track each other, which the paper's abstract cites as evidence that T-Eval "exhibits consistency with the outcome-oriented evaluation." But the comparison also surfaces a case where the holistic metric is more flattering than the fine-grained one: Qwen-7B achieves a 52% win rate over GPT-3.5-turbo's responses under GPT-4 judging, yet still trails GPT-3.5 across several of T-Eval's individual ability scores — the paper's point being that a coin-flip-or-better win rate can mask a real, still-open per-ability capability gap that holistic judging alone would not reveal.

A smaller analysis looks at what training data predicts tool-use skill among models built on the same LLaMA2 base. General-purpose instruction diversity (Vicuna's ShareGPT data, WizardLM's Evol-Instruct data) helps substantially at 7B scale, but the benefit shrinks or reverses at 70B — WizardLM-70B's Overall (44.2) is among the lower scores in its own scale cluster, which the paper reads as evidence that data quality, not just model scale, matters for tool learning. Comparing task-specific tuning corpora built on the same base, AgentLM-7B (agent-interaction data, Overall 41.4) scores higher than CodeLLaMA-7B (code data, Overall 28.6), but neither clearly beats general-instruction Vicuna-7B (44.8) — suggesting, per the authors, that high-quality general instruction-following is still necessary groundwork for tool use, not something narrow fine-tuning alone supplies.

// does it hold up?

The eval read

T-Eval's central methodological move — six inspectable, protocol-defined sub-scores instead of one opaque outcome number — is a genuine improvement for diagnosing where a tool agent breaks, and the paper does the right sanity check by verifying its decomposed score still tracks ToolBench's holistic win rate (Fig. 4). The authors' own camera-ready Limitations section is admirably candid about the main soft spot: the golden solution paths are machine-generated and human-verified rather than human-authored, and "it would be hard to scale up the construction process to a larger scale" without more human effort. That admission is worth taking further than the paper itself does.

baselines

The 20-model roster was current for December 2023 (per the paper's own footnote, testing ran 12/01–12/10/2023) — GPT-4-1106-preview, GPT-3.5-turbo-16k, and Claude-2.1 — but is now roughly two model generations stale (no GPT-4o, Claude 3/4, Llama 3, or any reasoning-tuned model). The headline claim that there's "a clear performance gap between open-source models and GPT-4" should be read as a snapshot of that moment, not a durable property of open vs. closed models; T-Eval's own numbers already show that gap narrowing sharply from Qwen-7B to Qwen-72B within the open-source column alone.

contamination

T-Eval's "gold" solution paths are synthesized: GPT-3.5 drafts queries, GPT-4 refines them, and a three-role GPT-3.5 planner/executor/reviewer pipeline produces the golden plan, thoughts, tool calls, and reviews that every evaluated model is graded against. Humans filter and verify (1,500 → 553 pairs across two rounds), but the paper reports no inter-annotator agreement rate and no measure of how often human verification actually overrides the machine-generated solution versus just approving it. A model being graded against another LLM's idea of a good plan risks rewarding stylistic resemblance to GPT-3.5/GPT-4's tool-use conventions as much as it rewards correctness in some model-independent sense.

what's missed

Nothing is executed at grading time — a real executor does call tools, but only once, offline, during the GPT-3.5-driven golden-solution annotation pipeline (planner/executor/reviewer); every model under evaluation is instead graded against that fixed, pre-recorded observation and a paper-authored five-way label set (Success / Internal Error / Input Error / Irrelevant Response / Unable to Accomplish). That is a deliberate, defensible design choice for removing API-instability noise, but it also means T-Eval cannot say how a model handles a genuinely novel failure — a malformed response, an undocumented rate limit, a tool silently returning stale data — since those never occur in a frozen benchmark. The paper also never connects a given sub-ability score to any downstream task-success number outside of the one small six-model ToolBench cross-check, so it's not established what, say, a 65% RETRIEVE-JSON score actually predicts about deployment reliability.

would raise confidence

An inter-annotator or human-vs-machine solution-divergence rate for the golden paths; a periodically refreshed model roster and/or held-out test split so the reported gap-to-GPT-4 doesn't calibrate against one now-superseded frontier checkpoint; and a larger live-tool-execution arm (even a modest one, beyond the six-model Fig. 4 check) tying the sub-ability scores to real downstream task success.

// bottom line

T-Eval's decomposition is a durable contribution — it gives future benchmark builders and model developers a vocabulary for pinpointing which link in the tool-use chain is actually weak, and its correlation check against holistic win rate is a genuine (if small) piece of construct validity. Its cross-model leaderboard, resting on machine-authored gold answers and a December 2023 model roster, has aged faster than its methodology and should be read as a case study in decomposed evaluation rather than a current ranking.

// takeaways

What to remember

  1. T-Eval replaces a single end-to-end tool-use score with six separately protocol-graded sub-abilities — PLAN, REASON, RETRIEVE, UNDERSTAND, INSTRUCT, REVIEW — each tested against a frozen, human-verified gold solution path rather than a live tool response.
  2. Across the 20-model, December-2023 snapshot, GPT-4 leads Overall at 86.4, GPT-3.5 84.0, Claude2 78.8; the largest open model, Qwen-72B, reaches 71.4. UNDERSTAND-String is the only sub-ability column whose all-model maximum an open model holds outright (Qwen-72B's 84.5 vs. GPT-4's 83.2) — but open models beat GPT-4 specifically, without topping the column, in several other cells too: Qwen-72B (98.3) and Qwen-14B (97.6) both out-score GPT-4's 95.9 on INSTRUCT-JSON, and Qwen-14B (95.9) and Mistral-7B (92.6) both out-score GPT-4's 91.3 on RETRIEVE-String — in both of those columns GPT-3.5, not GPT-4, holds the true column lead (99.1 and 98.3 respectively).
  3. Strict JSON-format grading, not raw reasoning ability, drives many of the worst open-source scores — LLaMA2-7B's INSTRUCT score collapses from 68.7 (String) to 0.2 (JSON) — which is exactly the confound T-Eval's dual-difficulty protocol is built to separate from genuine planning or reasoning weakness.
