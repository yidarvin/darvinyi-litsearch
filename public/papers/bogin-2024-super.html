SUPER: Evaluating Agents on Setting Up and Executing Tasks from Research Repositories

SUPER asks LLM agents to set up and execute real experiments from 45 low-profile (median 14 GitHub stars) ML/NLP research repositories -- installing dependencies, fixing bugs, configuring data, and running training/eval scripts -- then checks their answers against expert gold solutions. The best agent, SWE-Agent with GPT-4o, solves only 16.3% of these end-to-end tasks and 46.1% of 152 narrower sub-problems derived from them.

What problem is this solving?

LLMs write code well, but that's a different skill from getting someone else's research code to actually run. Reproducing a result from a real ML/NLP repository means installing an environment, resolving outdated or unlisted dependencies, making non-trivial configuration changes, fixing bugs, and figuring out the correct execution command -- and, as the authors note, this is hardest exactly where support is thinnest: repositories "in-the-wild" that aren't well-documented or actively maintained. Figure 1 gives a concrete sense of what that looks like: a user asks an agent to train a model with a new optimizer ("MEZE") on a custom dataset, following a given repository's code. A capable agent has to install dependencies, download the data, edit a data-loading file to point at the new CSV, run the training script, hit an ImportError from an incompatible transformers version, diagnose and downgrade the package, rerun, and finally report the resulting dev_accuracy -- a long chain where any single broken link fails the whole task.

No prior benchmark asked for both halves of this at once on realistic, low-profile repositories. Table 1 lines SUPER up against the four closest benchmarks along four axes, and SUPER is the only column with all four checkmarks. SWE-bench requires repository understanding and scores outcomes, but its GitHub-issue tasks don't require repository setup -- the environment is already configured. DS-1000 and MLAgentBench don't require repository understanding at all: DS-1000 is self-contained data-science snippets, and MLAgentBench targets optimizing a single given script rather than comprehending an arbitrary repository (and neither requires environment setup either -- DS-1000 has no repo to set up, and MLAgentBench's row reads "requires repository setup: ✗" too). ML-Bench (Agent) requires both understanding and setup but skips outcome-based evaluation -- it checks whether the agent issued the right command, not whether the resulting numbers are correct. And the three comparators with reported star counts -- DS-1000, SWE-bench, and ML-Bench -- draw from popular, heavily-starred repositories (median GitHub stars: 35,309 for DS-1000, 12,557 for SWE-bench, 9,632 for ML-Bench) that are well-documented and plausibly present near-verbatim in LLM pretraining corpora; Table 1 leaves MLAgentBench's own low-profile and median-stars cells blank ("-"). SUPER instead draws its Expert and Masked tasks from 45 repositories with a median of just 14 GitHub stars (23 for the separate Auto set) -- deliberately obscure, under-documented repositories that force an agent to actually read the code rather than pattern-match a famous one.

// how it works

The method

SUPER is built around a Jupyter-notebook environment: every agent action is either a Python or bash command run as a notebook cell, with state preserved between cells, so an agent can both install packages/run scripts (shell) and inspect variables from a previous step (Python) -- something prior environments typically supported only one of. On top of that environment sit three problem sets built in a three-step pipeline (Figure 2): (1) write tasks from research repositories, (2) collect expert human solutions, and (3) extract Masked code scenarios from those solutions.

The Expert set (45 tasks) starts from repositories linked to papers in the Papers With Code database (filtered to "Text" modality, posted 2021 or later). Each task asks for a single experiment mentioned in a repo's README or scripts, often pushed to be harder by requiring a dataset or model other than the one already documented. To keep compute cheap and runs comparable, tasks are restricted to CPU-only execution under 10 minutes (small models like gpt2-scale, truncated data such as "load only the first 10 examples"). Upwork-hired experts ($30-40/hour, capped at 4 hours per task with case-by-case extensions to 6) then solve each task end-to-end in Google Colab, submitting a solution notebook, the reported metrics, the exact repository git commit, and the final dependency list; the authors manually review every solution for correctness and reproducibility (three re-runs within a 10-2 error tolerance). Fifty solutions were collected for a total of $6,580; five were discarded as unexecutable, leaving the final 45.

Two evaluation measures apply to both the Expert and Masked sets. Accuracy is outcome-based: the fraction of an answer's individual values (numbers, strings) that match the gold solution's, within a 10-2 tolerance for numeric values -- unlike reference-text matching, this allows for alternate valid solutions that reach the same correct numbers by a different path. Landmarks is a softer, partial-credit signal: for each gold solution the authors manually extract 2-6 "landmark" output patterns (e.g. the literal string *** training completed ***), and the metric reports what fraction of these patterns show up anywhere in the outputs the agent's cells actually produced. Landmarks reward progress even when the final answer is wrong -- but, as the authors are careful to note, a perfect Landmarks score does not imply a correct Accuracy score, since a landmark only shows a step ran, not that it ran with the right configuration.

Accuracy = # predicted values matching gold (± 10⁻²)total values in the gold answer // outcome-based -- strict, but tolerant of alternate valid solution paths
Landmarks = # of the solution's 2-6 landmark patterns observed in agent output# of landmark patterns defined for that solution // softer partial-credit signal -- a perfect score does not guarantee a correct Accuracy score

The Masked set (152 sub-problems) is extracted from the same 45 Expert solutions using a cloze-inspired "Code Masking" procedure (Figure 3): starting from a gold solution, the authors group its cells into aspects (e.g. a "data configuration" block, an "issue solving" block), mask out one aspect's cells, and pre-execute the remaining, unmasked cells so the agent starts with that partial progress already done. The agent is then given a narrower goal derived from what was removed -- e.g. "fix the runtime error so training completes" -- and only needs to solve that one narrower slice of the original task. Because each sub-problem still has a gold output and the same landmark patterns as its parent task, Accuracy and Landmarks apply unchanged. Table 3 in the paper breaks the 152 sub-problems into six categories with their share of the set and average gold-solution length: goal-completion problems (25.0% of the set, 6.5 lines of gold code) and data-configuration problems (23.7%, but the most code-heavy at 22.7 gold lines) are the two largest categories, followed by dependency-resolution (19.7%, 4.1 lines), configuration edits (12.5%, 8.2 lines), issue-fixing such as shape mismatches (9.2%, 5.8 lines), CPU-compatibility fixes (7.2%, 5.1 lines), and a residual other category (2.6%, 3.8 lines).

The Auto set (604 tasks) trades gold solutions for scale: starting from 5,915 Papers With Code repositories posted in 2021 or later, a combination of heuristic and GPT-4o-based filtering (does the repo mention a supported dataset/model family, avoid GPU-only code, avoid LLM-API dependencies, and give a runnable script example) narrows this to 1,006 candidates, from which GPT-4o generates one task per repository (goal, dataset, model, and entry-point script), yielding 604 unique repositories. A manual audit of 100 sampled generated tasks found 81% feasible. Because there is no expert gold solution to compare against, Auto tasks are scored only by Script-Executed: a coarse pass/fail check for whether the target script ran to completion without an exception for at least 10 seconds -- a threshold chosen to filter out fast, silent early failures rather than reward real progress.

Three baseline agents are evaluated, all sharing the same Jupyter-cell environment: ReAct, the standard thought/action/observation loop; ReAct-SUPER, the paper's own extension that adds a dedicated file-edit action (agents given only bash/Python commands tended to fall back on fragile single-line sed edits); and SWE-Agent, adapted from its original GitHub-issue-fixing form and re-prompted for SUPER's execution tasks. Underlying models are GPT-4o, GPT-4o mini, Mixtral-8x22B-Instruct, and Llama 3.1 70B (the latter two served via together.ai).

// what they found

The results

On the 45-task Expert set, the strongest configuration -- SWE-Agent with GPT-4o -- reaches only 16.3% ± 2.1 Accuracy (36.8% ± 2.3 Landmarks, averaged over 3 seeds). Plain ReAct with GPT-4o trails at 12.2% ± 1.0 Accuracy / 33.6% ± 0.9 Landmarks, while ReAct-SUPER with GPT-4o lands in between on Accuracy (14.4% ± 2.2) but actually posts the highest Landmarks of the three GPT-4o agents (42.6% ± 2.9) -- meaning agents with the edit action make more overall progress even when SWE-Agent still submits more exactly-correct final answers. Every weaker model falls off sharply: GPT-4o mini's best result is 5.6% Accuracy (ReAct-SUPER), Llama 3.1 70B's best is 6.1% (ReAct-SUPER), and Mixtral 8x22B bottoms out at 1.1% Accuracy / 0.0% Landmarks under SWE-Agent -- the single lowest score anywhere in the Expert-set table.

On the 152-sub-problem Masked set, the same SWE-Agent + GPT-4o pairing reaches the paper's other headline number: 46.1% Accuracy and 74.9% Landmarks. The edit-action ablation replicates cleanly here: ReAct-SUPER (41.6% / 72.5%) clearly beats plain ReAct (37.0% / 65.7%) with GPT-4o on both metrics. Across the weaker models, though, the SWE-Agent-vs-ReAct-SUPER ordering isn't consistent: ReAct-SUPER beats SWE-Agent for GPT-4o mini (31.5%/58.3% vs. 27.0%/51.8%) and for Llama 3.1 70B (22.8%/38.3% vs. 17.4%/35.0%) -- but for Mixtral 8x22B, SWE-Agent actually wins on both metrics, 9.5% Accuracy / 26.6% Landmarks against ReAct-SUPER's 7.0% / 13.2%.

On the Auto set (evaluated on a 250-task subsample, and only with GPT-4o and GPT-4o mini), Script-Executed rates are lower across the board and the within-model agent ranking shifts again: ReAct-SUPER + GPT-4o posts the best score here (18.8%), narrowly ahead of SWE-Agent + GPT-4o (18.0%), with plain ReAct trailing (14.0%); for GPT-4o mini, plain ReAct (16.0%) actually beats both ReAct-SUPER (14.8%) and SWE-Agent (5.2%). The authors' claim that "ranking of models and agents [on Auto] are mostly consistent with the ranking on the Masked set" holds for SWE-Agent (18.0% vs. 5.2%) and ReAct-SUPER (18.8% vs. 14.8%), where GPT-4o clearly outperforms GPT-4o mini, but not for plain ReAct, where GPT-4o mini actually scores higher (16.0% vs. 14.0%); and in any case the comparison is only checked for these two closely-related OpenAI models -- Auto is never run with Llama 3.1 70B or Mixtral 8x22B.

Two further results round out the picture. Reflecting on failed attempts helps only marginally: ReAct-SUPER + GPT-4o with 3 reflection retries (Reflexion) reaches 45.4% Accuracy / 76.6% Landmarks on the Masked set, up from 41.6% / 72.5% without it -- a "positive but minimal impact," in the authors' own words. And the per-category error analysis on the Masked set shows agents are much better at fixing well-specified, error-message-driven problems than at open-ended repository comprehension: CPU-compatibility fixes are solved 73% of the time, general issue-fixing 61%, and dependency resolution 54%, while data-configuration sub-problems are solved only 27% of the time (the hardest category), general "goal"-completion sub-problems 43%, and other configuration edits 38%. Separately, the authors validate the Auto set's Script-Executed proxy by comparing it against ReAct-SUPER's own Masked-set trajectories: it agrees with a binarized Landmarks score (>0.5) 90% of the time, but with the true Accuracy metric only 69% of the time.

// does it hold up?

The eval read

SUPER's core design choices hold up well: deliberately sourcing low-star, under-documented repositories is a genuine, targeted defense against the memorization risk that shadows SWE-bench, DS-1000, and ML-Bench, whose source repos run 9,632-35,309 median GitHub stars -- popular enough that a model plausibly saw large fractions of them verbatim during pretraining. Splitting outcome-based Accuracy from partial-credit Landmarks is a useful diagnostic pair, and deriving the Masked sub-problems directly from the Expert set's own gold solutions (rather than writing them from scratch) keeps the two sets tightly linked rather than measuring different things under the same name.

But one of the paper's own comparative claims doesn't survive a full read of its own results table. Section 4.2 states: "we find that SWE-agent performs better than ReAct-SUPER with GPT-4o as the LLM, but slightly worse with all weaker models." That holds for GPT-4o mini (27.0%/51.8% vs. 31.5%/58.3%) and Llama 3.1 70B (17.4%/35.0% vs. 22.8%/38.3%) -- SWE-Agent is worse on both metrics in both cases, as claimed. But the very same Table 6 also reports Mixtral 8x22B, where SWE-Agent scores 9.5% Accuracy / 26.6% Landmarks against ReAct-SUPER's 7.0% / 13.2% -- SWE-Agent clearly ahead on both metrics, not behind. "Slightly worse with all weaker models" is not correct for all three weaker models tested; it's correct for two of three, with Mixtral 8x22B as a real, table-confirmed exception the surrounding prose never flags.

The Auto set's evaluation is also thinner than its role in the paper's narrative suggests. It's positioned as the scalable, gold-solution-free signal for future development and training, but its only validation is a 90%/69% agreement check against ReAct-SUPER trajectories from the curated Masked set -- not against Auto's own 604 repositories -- and its baselines in Table 5 cover only GPT-4o and GPT-4o mini on a 250-task subsample, not the full 604 tasks or either open-source model. A metric that disagrees with true Accuracy roughly 3 times in 10, validated on a different problem set than the one it's meant to score, is a reasonable cheap proxy but a shakier basis for the "development-set" role the paper assigns it.

baselines

Three agents (ReAct, ReAct-SUPER, SWE-Agent) across up to four models on Expert/Masked is a reasonably controlled comparison -- same environment, same truncation strategy, same prompt structure. But the Auto set, pitched as the scalable development signal, is only ever run with GPT-4o and GPT-4o mini (Table 5); no Llama 3.1 70B or Mixtral 8x22B row exists there.

contamination

Targeting median-14-star repositories (vs. 9,632-35,309 for DS-1000, SWE-bench, and ML-Bench) is a real, sound anti-memorization design choice -- but the paper never directly tests whether GPT-4o (closed weights, undisclosed training cutoff/corpus) has actually seen these specific repos. Low star count is a plausible proxy for "unlikely to be memorized," not a verified guarantee.

what's missed

Section 4.2's claim that SWE-Agent is "slightly worse [than ReAct-SUPER] with all weaker models" is contradicted by its own Table 6: for Mixtral 8x22B, SWE-Agent beats ReAct-SUPER on both Accuracy (9.5% vs. 7.0%) and Landmarks (26.6% vs. 13.2%) -- the opposite of "worse," and the prose never notes the exception.

would raise confidence

A concrete memorization probe for the specific repos used (not just a star-count proxy); Auto-set baselines run across the full model range and the full 604-task set rather than a 250-task, two-model subsample; and a corrected characterization of the SWE-Agent/ReAct-SUPER trend that accounts for the Mixtral exception instead of "all weaker models."

// bottom line

SUPER closes a real gap -- no prior benchmark combined repository setup, repository understanding, and outcome-based scoring on genuinely low-profile repositories -- and its dual Accuracy/Landmarks scoring is a useful, well-motivated design. But its 16.3%/46.1% headline numbers rest on a single best agent-model pairing, one of its own comparative claims (SWE-Agent "slightly worse... with all weaker models") is contradicted by its own Mixtral row, and the Auto set's proxy metric is validated on a different problem set than the one it scores, with baselines run on only two of the four tested models.

// takeaways

What to remember

  1. SUPER is the first benchmark to require repository understanding, repository setup, and outcome-based evaluation together, on deliberately low-profile repositories (median 14 GitHub stars for Expert/Masked, 23 for Auto) -- far less-documented and less likely to be memorized than the 9,632-35,309 median-star repos behind ML-Bench, SWE-bench, and DS-1000.
  2. The best tested configuration, SWE-Agent + GPT-4o, solves only 16.3% ± 2.1 of the 45 end-to-end Expert tasks and 46.1% of the 152 narrower Masked sub-problems; open-source models trail far behind, down to 1.1% Expert Accuracy for Mixtral 8x22B + SWE-Agent.
  3. Error analysis shows agents handle well-specified fixes (CPU compatibility, 73% solved; dependency resolution, 54%) far better than open-ended repository comprehension (data configuration, 27% -- the hardest category) -- the bottleneck is understanding an unfamiliar codebase, not resolving a known error message.
