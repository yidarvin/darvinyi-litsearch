RLBench: The Robot Learning Benchmark & Learning Environment

100 hand-designed manipulation tasks sharing one Franka Panda arm, one camera rig, and one task/variation/episode spec — plus a motion-planner that can generate an infinite supply of demonstrations for any of them. This preprint itself runs no learned agent on any task; it proposes the benchmark, a "v1.0" few-shot challenge protocol, and a task-authoring toolkit, and leaves the empirical results to the community that follows.

// the gap

What problem is this solving?

By 2019, continuous-control RL had standard benchmarks — OpenAI Gym and the DeepMind Control Suite — but the paper argues their tasks are, in its words, "toy-benchmarks" whose "focus is not on real-world problems," and that algorithms tuned on them often "do not scale to more complex, real-world tasks." Manipulation research, meanwhile, had no equivalent standard at all: groups built their own task sets to fit whatever method they were proposing, which the paper calls out directly — a method "could fail on a more challenging task, and so results would only be presented for a simpler set of tasks," making task design itself an unacknowledged hyperparameter of the reported results.

Few-shot and meta-learning work for robotics had a narrower version of the same problem. The paper singles out its own prior work (James, Bloesch & Davison's task-embedded control networks) and Finn et al.'s one-shot visual imitation as having "a very narrow distribution of tasks," where "placing a peach into a red bowl" and "placing an apple into a green bowl" would count as two different tasks rather than two variations of one. RoboTurk, an existing imitation-learning benchmark built by crowdsourcing demonstrations, is noted to have "only three tasks" as a direct consequence of how expensive crowdsourced demos are to collect.

RLBench's answer is to decouple task count from demonstration cost: instead of paying humans (RoboTurk) or a motion-capture rig (Simitate, a hybrid real/sim benchmark the paper also reviews) for every demo, RLBench scripts each task's solution once, at authoring time, with a motion planner — after that, demonstrations are free and unlimited. That trade lets the benchmark scale to 100 tasks against RoboTurk's crowdsourced "only three tasks" and Simitate's mocap pipeline, where "the addition of new tasks requires time-consuming calibration and motion capturing" — at the cost of every demo coming from the same scripted solution style rather than a human's.

// how it works

The benchmark's design

RLBench is built on V-REP (the CoppeliaSim predecessor) via PyRep, a robotics toolkit from the same authors. Every one of the 100 tasks is loaded into an identical scene: a 7-DoF Franka Emika Panda arm bolted to a wooden table, lit by 3 directional lights, observed by an over-the-shoulder stereo camera and a monocular eye-in-hand camera, each supplying rgb, depth, and segmentation-mask frames. Every episode starts with the gripper empty — the paper notes this is deliberately harder than many prior setups, since tool-using tasks must first grasp the tool rather than starting pre-grasped, "given that household robots will one day work under such conditions." Reward is sparse: +1 on task completion, nothing otherwise. Users pick from ten action-space variants — absolute or delta versions of joint velocities, joint positions, joint torques, end-effector velocities, and end-effector poses.

The paper introduces three formal terms that matter for reading any RLBench-based result correctly: a task is a set of variations — e.g. "stack blocks" — and each variation is sampled for an unlimited number of episodes. Variations can change count as well as color: Figure 4's "stack blocks" example runs "stack one red block on the target" through "stack two red blocks on the target" and "stack three red blocks on the target" across its first three variations, then changes the block's color instead in the last column shown, variation V ("stack one maroon block on the target"); episodes typically change object positions within the same variation. Each variation also ships a list of natural-language descriptions of the goal, intended for HRI/NLP research. This distinction matters because "100 tasks" and "number of variations" are not the same count — the paper does not print a total variation count across the suite, only the per-task concept illustrated in Figure 4.

Demonstrations are generated by an "expert algorithm π*" built from the Open Motion Planning Library, executing a series of waypoints that the task author places when building the task — so every demo for a given task/variation follows the same scripted motion-planning solution, not a human's. New tasks are authored as a pair of files (a .ttm V-REP scene file plus a .py file wiring success conditions), and a "task validation tool" re-collects demonstrations to check the motion-planning "only fails a small number of times" before a task can be submitted to the public task repository via pull request — the paper does not specify a numeric failure-rate threshold for this check.

// what they found

What the paper actually reports

This is a benchmark-proposal paper, not an experiments paper: the arXiv v1 text (the only version posted to arXiv) contains no learned-agent results, no reward curves, and no success-rate table for any method on any RLBench task. What it reports instead is a specification — the scene, the task/variation/episode taxonomy, the action-space and reward interface, the task-authoring toolkit — plus one quantitative characterization of the suite's own scale and difficulty distribution, shown in Figure 7.

The visible pattern in the bottom chart is that most sampled tasks cluster at the short end, with a handful of long-horizon, multi-stage tasks stretching toward the 1000-timestep ceiling — the caption specifically calls out "empty dishwasher" as an example, decomposed into "opening the washer door, sliding out the tray, grasping a plate, and then lifting the plate out of the tray." In the word-frequency chart, "open" and "put" are visibly the two most frequent content words across variation descriptions, consistent with a suite weighted toward manipulation-and-placement actions rather than, say, navigation or perception-only tasks.

The one concrete protocol the paper does specify is the RLBench Few-Shot Challenge v1.0: 10% of the 100 tasks are held out as a meta-test set spanning a range of difficulties, the rest are meta-train; at test time a system receives K demonstrations of an unseen task (the paper asks for 1-shot, 5-shot, and 20-shot results) and must then succeed on new episodes of that task, with "no prior knowledge of the unseen tasks" beyond the K demos. It is versioned "v1.0" explicitly because the authors expect the task count — and therefore the challenge's difficulty and scope — to grow. No results against this protocol are reported in the paper; the closing line of Section V says only that the authors "look forward to seeing how [existing few-shot methods] perform on this benchmark."

// does it hold up?

The eval read

Note on version: arXiv carries only v1 (posted 2019-09-26); this is the preprint, not the IEEE RA-L 2020 camera-ready (DOI 10.1109/LRA.2020.2974707). Everything below describes the preprint text specifically — a published-version addition would not contradict any claim made here about what "the paper" reports, since the camera-ready was not accessible for this build.

Because there are no learned-agent results in this document, the usual questions about baseline fairness and headline-metric gaming do not apply the way they would to a results paper — there is no headline metric here to game. The more relevant scrutiny is on the design choices a benchmark bakes in silently, since those choices will shape every paper built on top of it for years.

Task selection is a design philosophy, not a measured distribution. Section III lists the design goals — diversity, reproducibility, scale, extensibility, tiered difficulty, realism — as qualitative principles ("a truly diverse range of tasks is needed to help avoid over-fitting"), but the paper gives no quantitative coverage metric (no taxonomy of skill types, no count of how many tasks require multi-object reasoning vs. single-object pick-place, no stated inter-task similarity measure) to substantiate that the 100 tasks span a meaningful distribution rather than clustering around whatever was easy to script with a motion planner and a waypoint editor. The word-frequency chart in Figure 7 is suggestive here — "open," "put," "table," "slide," "place," "cup," "pick," "take" dominate — but the paper does not itself analyze this distribution as evidence of (or against) task diversity; that reading is ours, from the chart, not a claim the text makes.

Every demonstration comes from one solution style. Demos are generated by a motion planner (OMPL) executing waypoints placed by the task's author at creation time — meaning every demonstration for a given task/variation is a scripted, kinematically-planned trajectory, not a human's, and not sampled from a distribution of viable solutions. An imitation-learning or few-shot method trained on RLBench demos is therefore learning to imitate one specific solution style per task, chosen by whoever authored the task file. The paper is explicit that this is the trade it is making for infinite, free demonstrations, but does not discuss whether motion-planner trajectories are representative of solution styles a real robot (or a human teleoperator) would actually use — which matters for anyone hoping results transfer beyond imitating the planner.

Sim-to-real is offered as an option, not evaluated. The paper is admirably direct about this itself: "we cannot claim full photorealism in our rendering system, or general realistic physics." It offers a domain-randomization rendering option and a swappable-arm design "to maximise the potential for research on sim-to-real transfer," but the paper contains no sim-to-real experiment of its own — it is future-facing infrastructure, not a validated pipeline. That framing is honest, but it means claims about RLBench's sim-to-real value are, at this point in the paper's life, unverified.

Only the few-shot challenge has a specified protocol; the rest are prose sketches. Section V's few-shot challenge names concrete numbers (10% test split, 1/5/20-shot). Section VI's other five proposed research directions — reinforcement learning, imitation learning, sim-to-real, multi-task learning, and SLAM — get one paragraph each with no train/test split, no metric, and no baseline named; "multi-task learning," for instance, says only that "all tasks from both meta-training and meta-testing can be used during training" without specifying which tasks, how many, or what counts as success. A reader cannot reproduce a "multi-task RLBench result" from this paper the way they could reproduce a few-shot one, because only the few-shot challenge is actually specified as a protocol.

The task-validation bar is unquantified. The task-authoring pipeline's only stated quality gate is that a validation tool "attempts to collect a number of demonstrations... in order to ensure that the path planning aspect of the task only fails a small number of times" — "a number of," "a small number of times," and no threshold are all the paper gives. Since the benchmark is explicitly designed to grow via community-submitted tasks (through GitHub pull requests), the absence of a stated numeric bar for what counts as an acceptably reliable task is a real reproducibility gap for a benchmark whose value depends on every task's demo generator being trustworthy at scale.

baselines

None reported. Zero learned-agent results appear in the arXiv v1 text; the paper is a specification plus a proposed few-shot protocol, and explicitly defers empirical results to future work ("we look forward to seeing how they perform on this benchmark").

contamination

Not applicable in the usual training-data-leakage sense — RLBench is new simulated content, not scraped text/vision data. The closer analogue is solution-style leakage: every demo comes from one motion-planner solution per task, so an imitator can succeed by matching the planner's style rather than solving the task from scratch.

what's missed

No quantitative task-diversity metric; no sim-to-real validation; no formal protocol for any of the five non-few-shot research directions in Section VI (only few-shot in Section V is fully specified); no numeric threshold for the task-validation tool's reliability bar.

would raise confidence

A first round of published few-shot / RL / imitation baselines on the v1.0 protocol (which the RA-L version or follow-on papers may supply); a stated task-diversity or coverage metric; and a real sim-to-real transfer experiment using the swappable-arm design the paper describes but does not run.

// bottom line

RLBench's contribution is the infrastructure and the protocol, not a demonstrated result — and it should be read that way. The scale (100 tasks, unlimited scripted demos, a shared scene and interface) is real and became influential; the near-simultaneous release of Meta-World (which RLBench's own related work flags as not-yet-fully-documented "at the time of writing") and the later arrival of benchmarks like LIBERO and BEHAVIOR suggest the field agreed the gap RLBench identified was real. But everything about how well RLBench's tasks actually stress-test learning methods, whether its motion-planner demos are a fair imitation target, and whether its harder challenge modes are reproducible as specified, was left for the papers that came after it to determine.

// takeaways

What to remember

  1. RLBench ships 100 hand-designed manipulation tasks on a shared Franka Panda scene with stereo + wrist cameras, and every task/variation comes with an infinite supply of demonstrations because they're generated by a motion planner rather than collected from humans — a deliberate trade of demonstration realism for scale.
  2. The paper introduces three distinct counting units — task, variation, episode — that must not be conflated: "100 tasks" is not "100 variations," and the paper does not print a total variation count across the suite.
  3. The only fully-specified evaluation protocol is the "v1.0" few-shot challenge (10% held-out tasks, 1/5/20-shot); the other five proposed research directions (RL, imitation, sim-to-real, multi-task, SLAM) are one-paragraph sketches with no train/test split or metric defined.
  4. This preprint contains zero learned-agent results — it is a benchmark and toolkit proposal, and it says so about itself. Any claim about "how hard RLBench is" or "what score X model gets" comes from later papers, not this one.
