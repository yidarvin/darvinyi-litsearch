Retrieval Models Aren't Tool-Savvy: Benchmarking Tool Retrieval for Large Language Models

ToolRet folds 7.6k retrieval tasks and 43k tools from more than thirty existing tool-use datasets into one MTEB-style benchmark — and finds that even the strongest off-the-shelf embedding model, a 7B-parameter NV-Embed-v1, clears only 33.83 nDCG@10 zero-shot, a shortfall that measurably drags down the pass rate of the tool-use agents built on top of it.

// the gap

What problem is this solving?

A tool-use agent can't fit thousands of API and function descriptions into an LLM's context window, so real deployments need an information-retrieval (IR) model to first shortlist a handful of candidate tools from a large toolset before the LLM ever tries to call one. Almost every tool-use benchmark, though, sidesteps this step entirely: ToolBench and ToolACE hand-annotate roughly 10-20 relevant tools per task up front, so the agent is evaluated on tool use, never on tool retrieval from a realistic pool of thousands. That's a fair simplification only if retrieval is easy — and the authors' own pilot experiment on ToolBench suggests it isn't. Swapping ToolBench's officially annotated toolset for tools actually retrieved by five off-the-shelf IR models produces a sharp pass-rate drop for GPT-3.5-turbo: even a strong retriever like ColBERTv2 recovers only 27.3 recall@10, and the best of the five retrievers in that pilot still lands GPT-3.5 about 10 points of pass rate below the oracle-toolset ceiling of 64.2.

No prior benchmark measured this systematically across a large, heterogeneous toolset, so the paper's first contribution is simply making tool retrieval measurable: TOOLRET, a 7.6k-task, 43k-tool benchmark assembled by reformatting more than thirty existing tool-use datasets into a single MTEB-style retrieval test bed, so that any general-purpose IR model — not just whatever ad-hoc retriever a given agent paper bundled in — can be scored on how well it actually finds the tools a query needs.

// how it works

The method

TOOLRET is a corpus-assembly-and-reformatting effort more than a fresh data-collection one. The authors pull query-tool pairs from three kinds of sources — tool-use LLM benchmarks published at venues like ACL and NeurIPS (e.g. ToolBench/ToolLLM, ToolEyes, MetaTool, API-Bank, Gorilla), conference resource tracks (AppBench at EMNLP, ToolLens at CIKM), and open community datasets (e.g. ToolEmu, TaskBench) — spanning data released between August 2023 and December 2024. After deduplicating overlapping toolsets (e.g. merging COLT's toolset into ToolBench's, since they intersect) and K-means-clustering each dataset's queries to sample one task per cluster (so a huge dataset doesn't dominate a small one), they land on 7,615 tasks over a merged corpus of 43,215 tools. Every tool keeps its native documentation format, which the authors use to split TOOLRET into three subsets: Web API (36,978 tools / 4,916 tasks, structured OpenAPI/JSON descriptions), Code Function (3,794 tools / 950 tasks, function signatures like PyTorch or Hugging Face calls), and Customized App (2,443 tools / 1,749 tasks, free-form natural-language descriptions of things like sending an email).

Because instruction-following retrieval is an active IR research direction, every query is also paired with an auto-generated natural-language instruction (e.g. "retrieve tools that process audio inputs to produce accurate textual transcriptions..."). Three human experts hand-write 100 seed instructions; GPT-4o then generates one instruction per task via in-context learning, sampling from a growing pool of both seed and previously generated instructions to keep the outputs diverse. Five human reviewers checked these generated instructions on four criteria (Table 3) and found 89.2% correctly and comprehensively describe the target tools' features, with only 5.9% showing any hallucination, at 0.743 Cohen's Kappa agreement — the 10.8% flagged as mismatched were manually revised rather than discarded.

Retrieval quality is scored with four standard IR metrics at K=10: NDCG@10 (ranking quality), Recall@10 (fraction of all target tools found), Precision@10 (fraction of the top-10 that are actually targets), and Completeness@10 — borrowed from COLT — a strict binary per-task score that is 1 only if every target tool for that task lands in the top-10, else 0. Each is reported under two input conditions: w/o inst. (query alone) and w/ inst. (query + generated instruction concatenated), which isolates how much instruction-following ability actually helps. Six families of retriever are benchmarked this way: a sparse lexical baseline (BM25s); single-task dense encoders trained on MS-MARCO (gtr, contriever, ColBERTv2) plus the ad-hoc tool-retrieval model COLT; general-purpose multi-task embedding models (e5, gte, bge, all-MiniLM, in base/large sizes); instruction-pretrained embedding models marked ♠ (gte-Qwen2-1.5B-inst., e5-mistral-7b, GritLM-7B, NV-Embed-v1); cross-encoder re-rankers (MonoT5, mxbai-rerank, bge-reranker-v2, jina-reranker-v2) applied on top of NV-Embed-v1's initial list; and LLM agents used zero-shot as re-rankers via the RankGPT framework (Mixtral-8x22B, gpt-3.5-turbo-0125/1106), also re-ranking NV-Embed-v1's initial retrieval.

To close the loop, the authors also build TOOLRET-train: over 200k query-instruction-target-negatives instances, extending the same collection pipeline to the training splits of ToolACE, ToolBench, and APIGen. Negatives are the top-K tools NV-Embed-v1 retrieves that are not in the target set, and a model θ is fine-tuned with an InfoNCE-style contrastive objective over the instruction-query concatenation against its target tools and those hard negatives:

L = -1|T| Σti∈T log esim(I⊕q, ti)esim(I⊕q, ti) + Σt̂j∈T̂ esim(I⊕q, t̂j) // T = target tools, T̂ = K=10 hard negatives from NV-Embed-v1, I⊕q = instruction concatenated with query, lr = 5e-5

The results

Zero-shot, without any instruction, every retriever the authors test tops out well short of what a reader would expect from a strong conventional IR model. Even NV-Embed-v1 — a 7B-parameter, instruction-pretrained embedding model near the top of the MTEB leaderboard at the time — reaches only 33.83 average nDCG@10 (Completeness@10: 32.12) across the three TOOLRET subsets, and every model in the "w/o inst." table stays under 35% Completeness@10 and under 52% Recall@10. Some of the ordering is genuinely surprising: ColBERTv2, a strong conventional dense retriever, actually edges out plain BM25s lexical matching on the Web API subset (22.40 vs. 18.98 nDCG@10), but loses to it on Code (16.43 vs. 21.20), on Customized (19.54 vs. 26.76), and on the three-subset average (19.46 vs. 22.32). Re-ranking on top of NV-Embed-v1's list is a mixed bag rather than a reliable fix: bge-reranker-v2-gemma raises Completeness@10 by only 4.7% relative, while MonoT5 actively hurts, dragging NV-Embed-v1's average nDCG@10 down from 33.83 to 28.92.

Adding the generated instruction to the query ("w/ inst.") helps every single model, but the size of the gain doesn't track model family the way the paper implies: sorted by the Average nDCG@10 gain from Table 4 to Table 5, the instruction-pretrained gte-Qwen2-1.5B-inst. does top the list (+17.00), but the next two largest gains — gte-base-en-v1.5 (+15.93) and bge-large-en-v1.5 (+15.47) — belong to ordinary multi-task embedders that out-gain all three of the other instruction-pretrained models; NV-Embed-v1 itself gains only +8.88, 18th of 26. The sharpest case against a pure instruction-following reading is BM25s: it gains +14.14 (22.32 → 36.46), 4th of 26 and ahead of three of the four instruction-pretrained models — yet BM25s is a bag-of-words scoring function with no mechanism for following an instruction at all. Whatever the appended text is doing for it, it is contributing query terms, not instruction-following, and the paper runs no ablation separating the two. NV-Embed-v1 still climbs from 33.83 to 42.71 average nDCG@10, and gte-Qwen2-1.5B-inst. reaches 45.96 (Completeness@10: 45.39) — the best pure-embedding result in the paper. Layering re-ranking on top of instructions pushes further still: bge-reranker-v2-gemma reaches the paper's overall best, 47.52 average nDCG@10 and 48.90 average Completeness@10, up from a 22.32/22.19 BM25s floor. Comparing scores against MTEB's retrieval subset for the same 15 models (Figure 5) shows a real but partial correlation (Pearson β=0.790, Spearman τ=0.441): models that are strong on MTEB tend to be relatively stronger on TOOLRET too, but every model's TOOLRET score sits below the diagonal — the two tasks are related, but TOOLRET is uniformly harder for the same model.

Finally, the paper closes the loop back to downstream agents. Replacing ToolBench's oracle toolset with tools retrieved by an untrained IR model costs real pass rate — e.g. on ToolBench-G1, GPT-3.5-turbo's pass rate falls from an oracle 62.00 to 50.60 (-11.40) when using bge-large-en-v1.5's retrieved tools. Fine-tuning four embedding models (bge-base/large-en-v1.5, e5-base/large-v2) on the 200k-example TOOLRET-train recovers much of that gap: every trained model's NDCG@10 rises and its corresponding GPT-3.5/ToolLlama pass rate rises with it, moving each of the six ToolBench-G1/G2/G3 × {GPT-3.5, ToolLlama} panels measurably closer to its oracle line — though none reach it.

// does it hold up?

The eval read

The benchmark's core design is sound: comparing 26 retrievers spanning sparse, dense, instruction-tuned, cross-encoder, and LLM-agent families under two input conditions is a genuinely comprehensive sweep, and the paper is careful to isolate variables (same NV-Embed-v1 initial list feeding every re-ranker; w/o-inst. vs w/ inst. as a controlled toggle rather than conflated with model choice). But two things are worth flagging precisely because this is a numbers-heavy paper whose whole point is a numbers-heavy comparison.

Two of the paper's own table cells don't reduce correctly. Table 4's Average Completeness@10 for gte-Qwen2-1.5B-inst. is printed as 26.04, but the row's own three subset values (Web 21.49, Code 27.67, Customized 35.55) average to 28.24 — a genuine ~2.2-point internal inconsistency, confirmed against the rendered PDF page rather than just the extracted text. Separately, Table 5's Average N@10/C@10 for gpt-3.5-turbo-0125 is printed as 29.60/29.52 — but that row's own three w/-inst. subset cells (37.22/35.42/37.29 for N@10; 35.22/42.64/39.70 for C@10) average to 36.64/39.19. The printed 29.60/29.52 are, in fact, exactly that same model's Average cells from Table 4 (the w/o-inst. table) — a copy-paste artifact where one row's average was never updated between tables. Neither error changes the paper's qualitative story, but both mean a reader should re-derive any Table 4/5 average they plan to cite rather than trust the printed cell for these two rows specifically.

The benchmark inherits its ground truth wholesale, with no independent re-verification of the labels it imports. The paper is candid that this creates a "one-to-many problem" — because tasks are merged from 30+ source datasets, a query's true relevant-tool set may extend beyond whatever single dataset happened to annotate it, and functionally similar tools (the paper's own example: "Bing Search vs. Google Search") could be unfairly scored as retrieval misses. The authors argue this is acceptable because real deployments need fine-grained tool discrimination too, which is a defensible position — but it's a position, not a measurement; no experiment quantifies how often this actually produces a false negative.

baselines

Genuinely broad and current for a 2025 paper — sparse, single/multi-task dense, instruction-pretrained (NV-Embed-v1, GritLM-7B, e5-mistral-7b, gte-Qwen2-1.5B-inst.), cross-encoder, and LLM-agent re-ranking are all represented, and COLT (the one prior tool-retrieval-specific model) is included rather than omitted. The re-rankers and LLM agents, however, are only ever evaluated re-ranking NV-Embed-v1's fixed initial list, so their absolute numbers are capped by that one upstream retriever's recall ceiling.

contamination

Not discussed. TOOLRET's tasks are the test annotations of public 2023-2024 datasets (ToolBench, API-Bank, Gorilla, MetaTool, etc.); several embedding baselines (e5, bge, gte, NV-Embed-v1) are trained on large, partly web-scraped or synthetic instruction corpora assembled around the same period, and the paper runs no check for whether any evaluated model's training data overlaps with the source datasets' public queries or tool documentation.

what's missed

Precision@10 is structurally low (2-18 across the tables) because the average query has only 2.17 target tools among the top-10 slots — a low P@10 here doesn't mean the same thing a low P@10 means on a benchmark with denser relevance judgments, and the paper doesn't caveat this when presenting the P@10 column. Completeness@10's all-or-nothing scoring is also much harsher than Recall@10 for any multi-target query, which the two side-by-side columns (e.g. bge-reranker-v2-gemma's w/-inst. Customized-subset R@10 of 61.20 vs. C@10 of 45.65) make visible but don't discuss explicitly.

would raise confidence

A corrected Table 4/5 (the two arithmetic slips above); an explicit contamination audit for at least the instruction-pretrained embedders; a small human study quantifying how often the "one-to-many" false-negative problem actually fires, rather than only arguing it's acceptable; and extending the downstream ToolBench pass-rate analysis (currently GPT-3.5 and ToolLlama only) to at least one more recent tool-use LLM.

// bottom line

The headline claim — that strong conventional retrievers are surprisingly weak at tool retrieval, and that this weakness measurably costs downstream agents pass rate — is well supported by the paper's own numbers and survives the fact-check. The two table-arithmetic errors found while verifying this page are minor and don't change that story, but they're a reminder to re-derive any average this paper reports rather than quote it blind.

// takeaways

What to remember

  1. TOOLRET reformats 7.6k tasks and 43k tools from 30+ existing tool-use benchmarks into one MTEB-style retrieval test bed with three subsets by tool format (Web API, Code Function, Customized App) — and even the strongest instruction-pretrained embedder, NV-Embed-v1, reaches only 33.83 average nDCG@10 zero-shot, well below the same models' scores on conventional IR benchmarks like MTEB (Pearson β=0.790 but uniformly lower).
  2. Pairing the query with a short generated instruction and/or cross-encoder re-ranking helps substantially — the paper's best combination, bge-reranker-v2-gemma with instructions, reaches 47.52 average nDCG@10 / 48.90 Completeness@10 — but re-ranking alone is not a reliable fix (MonoT5 actually lowered NV-Embed-v1's average nDCG@10 from 33.83 to 28.92), and even the best result stays well under what strong retrievers reach on conventional IR tasks.
  3. Weak retrieval isn't just an IR-metrics problem: on ToolBench-G1, replacing the oracle toolset with bge-large-en-v1.5's retrieved tools drops GPT-3.5-turbo's pass rate from 62.00 to 50.60. The authors' 200k-example TOOLRET-train fine-tuning set narrows that gap for four embedding models across both GPT-3.5 and ToolLlama, without fully closing it.
