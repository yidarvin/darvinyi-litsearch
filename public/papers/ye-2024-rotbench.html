RoTBench: A Multi-Level Benchmark for Evaluating the Robustness of Large Language Models in Tool Learning

RoTBench tests six widely-used LLMs across five environments of increasing name-level noise — Clean, Slight, Medium, Heavy, and Union — and three staged tool-use scores (tool selection, parameter identification, content filling). GPT-4's tool-selection accuracy falls from 80.00 to 58.10 between Clean and Union while three human annotators drop only 2.86 points on the same task, and the "most robust" model isn't fixed: a fine-tuned open-source model beats GPT-4 outright under Heavy-level noise.

// the gap

What problem is this solving?

Tool learning — giving an LLM a set of callable functions and letting it pick one, fill in the arguments, and read back the result — has become a standard way to connect LLMs to the outside world. Almost all of the benchmarks that measure this ability (MetaTool, ToolLLM, ToolQA, T-Eval, ToolEyes) run the model against a clean, well-documented tool environment: a tool named Get_Weather that does exactly what its name says, with a parameter named location that means exactly what it says. That is not what production APIs look like. Real tool catalogs accumulate typos, legacy names, inconsistent casing, auto-generated identifiers, and renamed endpoints, none of which change what a tool actually does.

RoTBench's motivating observation, illustrated with the paper's own running example, is that this naming noise is not cosmetic for an LLM even when it is cosmetic for a human. Renaming a weather-lookup tool from Get_Weather to the meaningless string ABC does not touch the tool's function signature or its documentation — a human reading the same description would use it without hesitation — but it can be enough to make an LLM refuse the tool outright, because the model leans on the name itself as a semantic cue rather than only the accompanying description.

No prior tool-learning benchmark isolates this failure mode. General LLM robustness benchmarks like PromptBench and TextFlint perturb natural-language prompts, not the structured tool/parameter identifiers a tool-use pipeline actually depends on. RoTBench's gap, then, is narrow and specific: build a benchmark that holds tool functionality fixed and varies only the noise on tool and parameter names, across a graded range of noise severity, so that a drop in accuracy can be attributed to naming robustness rather than to task difficulty.

// how it works

The method

RoTBench starts from ToolEyes (Ye et al., 2024), which defines seven real-world application scenarios; the authors sample 15 user queries per scenario (105 queries total) and manually label a canonical invocation path for each — 41 tool categories, 95 subcategories, and 568 individual tools in total. This Clean-level set is then used to derive four progressively noisier environments by perturbing tool and/or parameter names:

  • Slight — insertion, omission, or character-substitution noise (up to 1/3 of a name's characters altered), e.g. cat_breed → cat t_breed s. 210 test cases.
  • Medium — reversal or replacement with a random nonsense string, e.g. dog_breed → deerb_god or query → ejklq. 210 test cases.
  • Heavy — exchange (tool names shuffled amongst each other, breaking the name-to-function link entirely) or addendum (an extra, unexplained mandatory parameter). 210 test cases.
  • Union — one tool-name noise method and one parameter-name noise method, drawn from the three levels above, applied simultaneously. 105 test cases.

Each test case is then scored at three cascading stages that mirror an actual tool call: the model must first select the right tool (tool selection), then identify the right parameters for that tool (parameter identification), then fill those parameters with the right content (content filling). The scores are deliberately gated rather than independent — a case only earns credit at a later stage if it already earned credit at every earlier stage, because in a real tool call, a wrong tool or a missing parameter fails the whole interaction regardless of what happens downstream:

sTS = 𝟙(t = t̂)    sPI = sTS·𝟙(P = P̂)    sCF = sPI·N Πi=1 𝟙(ci = ĉi) // t/t̂: chosen vs. required tool · P/P̂: identified vs. required parameter set · cᵢ/ĉᵢ: filled vs. correct content for the i-th parameter — each 𝟙(·) is a strict, exact-match indicator, so s_CF ≤ s_PI ≤ s_TS always

Six models are evaluated: four open-source, tool-tuned models (ToolLLaMA-2-7B-v1 and -v2, both fine-tuned from LLaMA-2-7B-base on ToolLLM's function-calling data; NexusRaven-13B-v1 and -v2, both fine-tuned from CodeLLaMA-13B to emit nested function calls) and two closed-source GPT-family models (GPT-3.5-turbo, GPT-4), plus a human reference formed by averaging three university students' scores on the same questions. Inference uses the ReAct prompting format for the GPT and ToolLLaMA families and NexusRaven's own documented prompt format for the NexusRaven family.

Having established that current models are not robust to this noise (see below), the authors propose a fix, RoTTuning, a four-phase training recipe: (1) query expansion — GPT-4 generates new user queries from the 105 seed queries, filtered for redundancy (Rouge-L ≤ 0.55) to reach 4,077 queries; (2) trajectory generation — GPT-4's own function-calling feature produces up to nine-turn tool-use trajectories for these queries (12,247 training turns); (3) environment augmentation — Clean-level trajectories are rewritten into noisy versions (3,000 augmented trajectories each for Slight/Medium/Heavy, 1,500 for Union, plus the Clean originals — 22,747 trajectories total); (4) generalizability training — LLaMA-2-7B-base, with its context window extended to 8,096 tokens via positional interpolation, is LoRA-fine-tuned for 5 epochs on this mixture to produce RoTLLaMA.

// what they found

The results

The headline number, and the one the abstract leads with: GPT-4's tool-selection accuracy falls from 80.00 (Clean) to 58.10 (Union) — a 21.90-point drop — while the three-student human average falls only from 88.57 to 85.71, a 2.86-point drop, on the identical questions. Averaged across all six LLMs, tool-selection accuracy drops about 20.32 points Clean-to-Union, versus the humans' 2.86; the same widening gap shows up in parameter identification and content filling. GPT-4 has the top tool-selection score in four of the five environments — but not Heavy, where NexusRaven-13B-v2 scores 62.38 against GPT-4's 60.00. NexusRaven-13B-v2 is even more dominant on parameter identification, where it is the best of the six models in three of the five environments (Clean: 56.19, Slight: 56.67, Heavy: 37.62), with GPT-4 only ahead on Medium and Union; on content filling it again beats GPT-4 in two of five (Slight: 39.05, Heavy: 30.00). A fine-tuned, function-call-native open-source model built on CodeLLaMA is, environment by environment, frequently the top scorer under noise — GPT-4 is the strongest model overall, but not the model to beat under every condition.

The noise-type breakdown (Figure 3) shows tool-name noise hurts far more than parameter-name noise at every stage: at the Heavy level, the average absolute drop from Clean is roughly 35.7 points for tool-name noise versus roughly 0.5 points for parameter-name noise in tool selection, and a similar (if smaller) gap persists in parameter identification and content filling. A Welch's ANOVA on content-filling scores across the five environments (per model) confirms LLM content-filling accuracy really does move with the environment for five of the six LLMs (p < 0.05) and for none of the human scores (p = 1.00, F = 0.04) — but NexusRaven-13B-v1 is the sixth LLM, and its content-filling ANOVA is not significant either (p = 0.555), because its scores sit near the floor (0.95–3.33%) in every environment rather than because it is genuinely stable.

A closer look at why GPT-family models specifically underperform in Slight (below Medium, despite Medium being nominally more corrupted) traces to an over-eager "noise correction" habit: the GPT family sometimes silently corrects a noised name back to its clean form internally and then fails because that clean name doesn't exist in the noised environment (e.g. selecting "predOict_aTge" but outputting the auto-corrected "predict_age"). The paper attributes 33.72%/33.85% of GPT-3.5-turbo's Slight-level tool-selection/parameter-identification errors to this mechanism, and 29.17%/22.83% of GPT-4's.

Giving GPT-4 two prior turns of worked interaction as in-context examples (comparing first-turn vs. third-turn content-filling accuracy) raises its average score by 22.91 points across the five environments — but its standard deviation across environments rises too, from 8.14 (first turn) to 12.56 (third turn), so the extra context makes GPT-4 more capable on average without making it any more consistent across noise levels.

RoTTuning's own RoTLLaMA is markedly more stable than GPT-4 on the same three-stage evaluation: across the five environments, RoTLLaMA's own score range is 12.38 points for tool selection (76.19 Clean down to 63.81 Union), 16.19 for parameter identification (55.24 down to 39.05), and 14.76 for content filling (42.86 down to 28.10) — versus the paper's own reported GPT-4 ranges of 21.90, 20.95, and 20.95 on the same three stages. Ablations show environment augmentation matters more than the LoRA-vs-full-fine-tuning choice: removing augmentation (w/o Augmentation) drops mean performance and widens the spread noticeably more than removing LoRA alone (w/o LoRA) does.

// does it hold up?

The eval read

RoTBench's central design decision — hold tool functionality fixed, perturb only names, and grade in three cascading stages that mirror what a real tool call actually needs — isolates naming robustness cleanly, and the headline contrast (GPT-4 loses 21.90 points on tool selection Clean-to-Union while three human graders lose 2.86 on the same items) is a genuinely striking, well-supported number. But the paper's own framing tends to collapse to "GPT-4 is the reference frontier model, and it isn't robust," when its own Table 2 tells a more complicated story: GPT-4 is not the best model in every environment. NexusRaven-13B-v2 — an open-source, CodeLLaMA-based model built specifically for function calling — beats GPT-4 on tool selection under Heavy noise (62.38 vs. 60.00), and beats it on parameter identification in three of five environments and on content filling in two of five. A reader taking away only "closed frontier models are more robust than open ones" would be wrong on this benchmark's own numbers.

There is also a genuine arithmetic wrinkle in how the paper computes its own "extreme performance difference" claims in the RoTTuning results section. For parameter identification and content filling, the stated GPT-4 ranges (20.95 for each) match the true max-minus-min across all five environments in Table 2 (Medium 53.81 minus Heavy 32.86 for parameter identification; Medium 46.19 minus Heavy 25.24 for content filling) exactly. But the stated tool-selection range for GPT-4, 21.90, matches only a Clean-minus-Union subtraction (80.00 − 58.10); the true max-minus-min across all five tool-selection environments is actually larger, because GPT-4's Medium-level score (84.29) exceeds its own Clean-level score (80.00) — noise is not monotonically harmful for GPT-4 on this stage, and the paper's own comparison method is inconsistent between the tool-selection number and the other two. Neither error changes the paper's directional conclusion (RoTLLaMA is still more stable than GPT-4 on all three stages), but a reader checking the arithmetic will find it doesn't fully reconcile.

A structural limit worth naming: every stage is scored against a single, manually-labeled canonical tool/parameter path per query, with no partial credit for a functionally valid alternative — and because the three stages are gated (a wrong tool selection zeroes out parameter identification and content filling for that case regardless of whether the model would have filled the parameters correctly), the benchmark measures agreement with one canonical path under noise, not tool-use competence more broadly. The paper's own Appendix C notes cases where this bites: ToolLLaMA-7B-v1 scores 20% on Clean vs. 40% on Union in the application-manipulation scenario specifically because it happens to have fewer viable tools to choose between in that scenario, not because Union noise helped it.

baselines

Four open-source models (two ToolLLaMA checkpoints on LLaMA-2-7B, two NexusRaven checkpoints on CodeLLaMA-13B) plus two closed GPT-family models plus a 3-student human reference — reasonable family coverage for a January-2024 arXiv submission, but the roster wasn't refreshed for the EMNLP 2024 camera-ready in November 2024, so by the time this page is read (2026) the headline numbers describe a dated model generation with no native structured-function-calling frontier models (GPT-4o, Claude 3.x, Gemini) included.

contamination

The Clean-level queries and tool inventory are sourced from the already-published ToolEyes benchmark, though the gold invocation paths were manually labeled by the RoTBench authors rather than reused from ToolEyes; the paper never checks whether any tested model's pretraining data overlapped with ToolEyes itself. The four noise variants are synthesized on top of Clean, so their specific noised names shouldn't appear verbatim in pretraining corpora — a reasonable mitigation for the noise-robustness comparison specifically, even if Clean-level absolute scores could still carry some memorization risk.

what's missed

GPT-4 is not the most robust model in every environment — NexusRaven-13B-v2 beats it on tool selection under Heavy noise and on parameter identification in three of five environments — a nuance the paper's "GPT-4 drops from 80.00 to 58.10" framing doesn't surface. NexusRaven-13B-v1's non-significant ANOVA (p=0.555) reflects floor-level scores (0.95-3.33% content filling) rather than genuine robustness, unlike the human non-significance the paper highlights (p=1.00) — the two "not significant" results mean different things and the paper treats only one of them.

would raise confidence

Testing at least one frontier model with native tool-calling released after the benchmark's own construction; partial credit (or a documented alternate-path check) for tool selections that are functionally valid but not the single labeled gold tool; resolving the tool-selection "21.90" figure against the true Table 2 range so the RoTTuning comparison is computed the same way across all three stages; and extending the first-turn-vs-third-turn in-context-example experiment (currently GPT-4-only, content-filling-only) to the other five models and the other two stages.

// bottom line

RoTBench's five-environment, three-stage design is a clean, well-targeted instrument for a real gap — tool-learning benchmarks that never test what happens when tool names get noisy — and its headline human-vs-GPT-4 contrast holds up on direct recomputation from Table 2. But its own results argue against treating GPT-4 as simply "the robust one": NexusRaven-13B-v2 beats it under Heavy-level noise on tool selection, in a majority of environments on parameter identification (3 of 5), and in two of five on content filling, one of the paper's own "extreme difference" numbers doesn't reconcile with its source table, and the single-gold-path, all-or-nothing scoring means a chunk of what reads as "noise sensitivity" may really be exact-match rigidity that the paper doesn't try to separate out.

// takeaways

What to remember

  1. Renaming a tool from something semantically meaningful (Get_Weather) to a meaningless string (ABC) can break an LLM's ability to use it even though the tool's function and documentation never changed — GPT-4's tool-selection accuracy falls from 80.00 (Clean) to 58.10 (Union) while three human graders' accuracy on the same items falls only from 88.57 to 85.71.
  2. The "most robust" model on RoTBench is not fixed to GPT-4: NexusRaven-13B-v2, an open-source, CodeLLaMA-based model built for function calling, outscores GPT-4 on tool selection under Heavy noise (62.38 vs. 60.00) and on parameter identification in three of five noise environments — a fine-tuned open model can beat a closed frontier model on this benchmark, not just match it.
  3. RoTTuning — LoRA-fine-tuning LLaMA-2-7B on noise-augmented, GPT-4-generated tool-use trajectories — narrows RoTLLaMA's own Clean-to-worst-case range to 12.38/16.19/14.76 points across tool selection/parameter identification/content filling, versus the paper's reported 21.90/20.95/20.95 for GPT-4 on the same three stages, suggesting environment diversity at training time is a workable lever for robustness independent of base model scale.
