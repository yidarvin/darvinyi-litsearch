StableToolBench: Towards Stable Large-Scale Benchmarking on Tool Learning of Large Language Models

ToolBench's real RapidAPI endpoints decay: a live rerun of its own reported numbers months later showed a "notable decline" across every method. StableToolBench replaces the live API layer with a caching-plus-LLM-simulation virtual server and a solvability-gated Pass/Win metric, then shows model rankings stay stable even when half the tools are cut off.

// the gap

What problem is this solving?

ToolBench (Qin et al., 2023) is the field's largest tool-use benchmark: 16,464 real RapidAPI endpoints across 3,451 tools, with a ToolEval harness that scores models by Pass Rate (PR) and Win Rate (WR). The catch is that ToolBench's APIs are live, third-party, real APIs — and third-party APIs go down, get deprecated, start requiring new authorisation, or silently change their outputs. A benchmark is only useful if a score measured today means the same thing as a score measured six months from now; StableToolBench's authors argue ToolBench, as deployed, cannot make that promise.

They demonstrate this rather than merely asserting it. Rerunning ChatGPT and ToolLLaMA-v2 with the exact configurations from the ToolBench paper (same gpt-3.5-turbo-0613, same Chain-of-Thought (CoT) and Depth-First-Search (DFS) inference strategies) on the I1-Instruction test group, they find every one of the four reported/reproduced pairs has fallen: GPT-3.5-Turbo-0613+CoT goes from a reported Pass Rate of 41.5% down to 35.2% reproduced, +DFS from 54.5% to 53.2%, and ToolLLaMA-v2+CoT from 25.0% down to 15.0%, +DFS from 57.0% down to 34.0%. Scanning the original RapidAPI endpoints with gpt-4-turbo-written calls, they find only 44.4% still return a successful response; 49.2% are now “Not Available” (mostly parsing errors and unreachable hosts) and 6.4% are “Not Authorised” — a combined 55.6% of ToolBench's tool surface has drifted since release.

A second, distinct source of instability is the evaluator itself. ToolBench's PR/WR pipeline relies on gpt-3.5-turbo-16k to first decide whether a task is solvable at all and then to judge the answer — a task that GPT-3.5 turns out to handle unreliably. Running CoT and DFS three independent times each on the same I1-Instruction queries with a fixed model, the authors find the PR and WR swing noticeably run to run (Table 1: CoT Pass Rates of 33.0, 31.5, and 37.5 across three identical reruns; DFS Win Rates of 54.0, 48.0, and 56.0), and the second DFS Win Rate run (48.0) even falls below the first CoT run (50.0) — despite DFS consistently outperforming CoT elsewhere in the paper. Two failure modes, one root cause: a large-scale benchmark built on live, uncontrolled infrastructure and a weak automatic judge cannot give the same paper's own baselines a stable score twice.

// how it works

The method

StableToolBench keeps ToolBench's queries, tools, and documentation as-is, and rebuilds only the two pieces that were unstable: the API layer and the evaluator.

A virtual API server: cache first, real API second, LLM simulator last

The virtual server has two components. The caching system stores every API call/response pair keyed on category, tool, API name, and arguments, seeded from ToolBench's released training-set, test-set, and reproduced-experiment call histories, then filtered by a keyword-based validity rule (Appendix D) that strips out obvious error responses. Before filtering, the combined cache held 352,630 records (58,105 train + 5,921 test + 255,828 from new experiment runs); after filtering, 164,980 remain (25,995 / 2,393 / 136,592 respectively) — more than half of the raw cache is discarded as invalid. The API simulator covers whatever the cache misses: it prompts gpt-4-turbo with the API's own documentation plus up to five real cached call/response pairs as few-shot examples, and asks it to fabricate a plausible JSON response in the same format.

The three pieces compose into one calling rule: on a request, check the cache first; on a cache miss, try the real API; only if the real API is also unavailable does the simulator answer — and whichever response is finally returned (real or simulated) gets written back into the cache for next time.

A stable evaluation system: judge solvability once, then score with GPT-4

Rather than letting an unreliable evaluator decide per-run whether each task is solvable, StableToolBench fixes the solvable set up front. Three separate LLMs — gpt-4-turbo, gemini-pro, and claude-2 — each vote a task solvable or unsolvable, and a task only enters the benchmark's solvable pool if at least two of the three agree it's solvable. Of ToolBench's 1,100 original test queries (200 each for I1-Instruction/I1-Category/I1-Tool/I2-Category/I2-Instruction, 100 for I3-Instruction), 765 survive this filter: 163 (I1-I), 153 (I1-C), 158 (I1-T), 106 (I2-I), 124 (I2-C), and 61 (I3-I).

Against this fixed solvable pool, the paper reports two metrics, both scored exclusively by gpt-4-turbo instead of GPT-3.5: Solvable Pass Rate (SoPR), which assigns a Solved answer 1 point, Unsure 0.5, and Unsolved 0; and Solvable Win Rate (SoWR), where a solved-vs-unsolved pair is decided automatically and any other pairing is broken by a gpt-4-turbo pairwise judgment.

SoPR = 1·(#Solved) + 0.5·(#Unsure) + 0·(#Unsolved)#solvable tasks // computed only over the fixed, majority-voted "solvable" subset of each ToolBench test group

The results

On the fixed solvable pool, the paper runs GPT-3.5-Turbo-0613, GPT-4-0613, GPT-3.5-Turbo-1106, GPT-4-Turbo, and ToolLLaMA-v2, each with both CoT and DFS, evaluating three times per run and averaging. The Average-column SoPR ranking (Table 4) puts GPT-3.5-Turbo-0613+DFS at 63.0±1.1, GPT-4-0613+DFS at 58.5±1.0, GPT-3.5-Turbo-1106+DFS at 62.2±0.8, GPT-4-Turbo+DFS at 60.6±1.3, and ToolLLaMA-v2+DFS at 46.6±1.7 — DFS beats CoT for every model/version, but the GPT-4-vs-GPT-3.5 ordering flips with the strategy: under CoT, GPT-4-0613 and GPT-4-Turbo lead their matched GPT-3.5 checkpoints (48.2±0.8 vs. 46.6±1.3; 53.1±0.8 vs. 48.8±0.6), while under DFS the same GPT-3.5 checkpoints actually outscore GPT-4 (63.0±1.1 vs. 58.5±1.0; 62.2±0.8 vs. 60.6±1.3) — with ToolLLaMA-v2 trailing every other model under both CoT (33.9±0.8) and DFS (46.6±1.7), consistent with the qualitative ordering ToolBench itself reported.

The paper's central stability claim is demonstrated, not just asserted, with a stress test: it manually forces a sampled percentage of previously-successful tools to fail (0%, 10%, 20%, 50% of tools on the I1-Instruction group), re-routing those calls to the simulator instead of a dead real endpoint. Under the old real-API pipeline (Section 2.3/Figure 4 of the paper), this kind of forced failure caused Solvable Pass Rate to visibly degrade as more tools were cut. Under StableToolBench's virtual API pipeline, the same stress test (averaged over all six I1/I2/I3 groups) leaves performance "not significant" even at 50% of tools failing — e.g., GPT-4-0613+DFS moves from 69.7±1.4 (0% forced-failure) to 71.4±1.4 (10%) to 71.2±0.9 (20%) to 69.9±0.9 (50%), well within the run-to-run variance already present at 0%.

Three further checks probe whether the simulator's realism comes at a hidden cost. A 70-pair human “Turing Test” asking three annotators to pick the more realistic of a real vs. simulated API response finds Simulated preferred 20.0% of the time vs. Real preferred only 12.9% overall (Format Accuracy: Simulated 5.7% vs. Real 0.0%; Answer Relevance: Simulated 20.0% vs. Real 10.0%), with a Tie the modal outcome in all three dimensions (67.1% overall, 94.3% format, 70.0% relevance) — humans mostly can't tell them apart, and when they can, they lean toward the simulated response, not the real one. A separate 50-sample documentation-adherence check finds 90% of simulated outputs judged to reasonably follow the API's own documentation (6% unreasonable, 4% uncertain). And a diversity check — encoding 246 real and simulated Tool-category API responses with Sentence-BERT and visualising with UMAP — shows the two response distributions occupying overlapping embedding regions, with only 2 of 60 sampled simulated APIs returning an identical response across any two of five repeated calls.

// does it hold up?

The eval read

The paper is honest about its own biggest structural weakness, and it's worth taking at face value: the entire virtual API server rests on gpt-4-turbo as both the simulator backbone and (a version-pinned) evaluator. The Limitations section states this plainly — "the backbone LLM may experience significant upgrades, which may affect the performance" and "current open-source LLMs are not performant enough to simulate API behaviours well... closed-source LLMs are the only options." That is precisely the reproducibility problem the paper set out to solve, just relocated from RapidAPI's servers to OpenAI's model lineage. The ablation in Table 6 (swapping GPT-4-Turbo's 1106-preview vs. 0125 checkpoints and T=1 vs. T=0.1) shows SoPR moving by a few points at most across settings — e.g. GPT-4-Turbo+DFS goes from 73.2±1.1 (1106-preview, T=1) to 77.3±0.9 (0125, T=0.1) — which the authors call "acceptable... within the variance of LLM evaluation," but a several-point swing from swapping only the simulator's own checkpoint is itself evidence that simulator drift is a live, not hypothetical, risk for exactly the kind of long-term score comparability this benchmark exists to guarantee.

The cache-hit numbers in Table 7 also complicate the "stability" story in a way the paper doesn't fully unpack. The near-perfect 96.5–97.0% cache hit rates are measured on the same four in-domain methods (GPT-3.5-Turbo-0613 and GPT-4-0613, CoT/DFS) that ToolBench's own reproduction data already ran end-to-end — of course a rerun of an experiment ToolBench already recorded hits the cache almost every time. The moment a genuinely new setup is tried (GPT-3.5-Turbo-1106 and GPT-4-Turbo, both "out-of-domain" additions this paper made), the hit rate falls to 75.8–91.4% depending on solver: with DFS specifically it drops to 75.8–77.8%, meaning roughly a quarter of those calls still fall through to the GPT-4-Turbo simulator, while CoT stays higher at 88.2–91.4%. The paper's own stress test (Figure 4/Table 12) only ever forces failure on tools that were previously successful, and only up to 50% of the tool pool at a time — it does not report what happens to a brand-new method's score stability when the simulator, not the cache, is doing the majority of the work, which is the regime any future benchmark user querying an unseen model will actually be in.

The paper's diversity and realism checks, while a genuinely good instinct that most benchmark papers skip, are small: the human Turing Test uses only 70 API pairs and 3 annotators with no reported inter-annotator agreement statistic, and the documentation-adherence check uses only 50 samples judged by what the text implies is a single human evaluator. The finding that simulated responses are preferred over real ones (20.0% vs. 12.9% overall) is presented as reassuring, but with this few raters and no reported agreement, it is not clear whether that gap is a real signal or noise from a handful of judgment calls.

baselines

Only ToolBench's own model roster is tested (GPT-3.5-Turbo-0613/1106, GPT-4-0613/Turbo, ToolLLaMA-v2, each CoT/DFS). There is no comparison against other tool-use systems built on different infrastructure (e.g. Gorilla, ToolAlpaca, API-Bank's own baselines), so the "stability" claim is validated only within the ToolBench/ToolLLaMA lineage the benchmark is built on top of.

contamination

Not applicable in the usual training-data-leakage sense — this is an infrastructure/evaluator-stability paper, not a new task-contamination surface. The closer analogue is simulator drift (discussed above): because the "ground truth" API responses for cache-miss cases are generated by a specific GPT-4 checkpoint rather than observed from the real world, a future model finetuned or prompted with access to that checkpoint's typical output style could game the simulator's response distribution in a way a real, unpredictable API never would.

what's missed

The stress test never goes past 50% forced tool failure, and never tests a method whose calls mostly rely on the simulator rather than the cache — exactly the harder, more realistic case for anyone benchmarking a brand-new model years after the cache was built. The paper is also silent on cost: running GPT-4-turbo as both simulator and evaluator is far more expensive than ToolBench's original GPT-3.5 pipeline, a real adoption barrier the Limitations section only alludes to in passing.

would raise confidence

A stress test at higher forced-failure rates (75%, 100%) and specifically on out-of-domain methods with low cache-hit rates; a larger, agreement-reported human Turing Test; and a demonstration that scores stay comparable across a full GPT-4 model-family upgrade (e.g. GPT-4-turbo to GPT-4o or later), not just across two close checkpoints of the same "-turbo" line.

// bottom line

StableToolBench correctly diagnoses that ToolBench's live-API design breaks reproducibility, and it backs the diagnosis with real numbers (the 41.5%→35.2% Pass Rate drop, the 55.6% API-status decay). Its fix — cache first, real API second, GPT-4-simulate last, plus a majority-voted solvable-task gate scored only by GPT-4 — measurably works within the paper's own stress tests. But the fix trades one instability (uncontrolled third-party APIs) for another, better-behaved but not eliminated one (a specific GPT-4 checkpoint's behaviour as the ground truth for anything not already cached), and the evidence for how well that trade holds up outside the in-domain methods ToolBench already ran is thinner than the evidence for the original problem.

// takeaways

What to remember

  1. ToolBench's real RapidAPI endpoints decay fast enough to matter: rerunning the paper's own baselines months later dropped every reported Pass Rate, and a scan found 55.6% of APIs no longer return a clean success (49.2% "Not Available", 6.4% "Not Authorised").
  2. StableToolBench's fix is a cache-first / real-API-second / GPT-4-simulator-last virtual API server, paired with a stable evaluation system: a 3-LLM majority vote fixes which of ToolBench's 1,100 test queries are solvable (765 survive), then only GPT-4-turbo scores Solvable Pass Rate and Solvable Win Rate.
  3. The fix is demonstrated to work under stress — SoPR barely moves even with 50% of tools forced to fail — but it works best for the exact in-domain methods ToolBench already cached (96.5–97.0% cache hit rate), and noticeably less so for new, out-of-domain methods run with DFS (75.8–77.8% cache hit rate, vs. 88.2–91.4% with CoT), which is the harder case any future benchmark user is actually in.
