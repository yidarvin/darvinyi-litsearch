Optimization-based Prompt Injection Attack to LLM-as-a-Judge

JudgeDeceiver appends a gradient-optimized 20-token sequence to an attacker's candidate response so that an LLM-as-a-Judge selects it over a rival response — 88-98.9% attack success across four open-source judges at two-candidate (n=2) evaluation, versus at most 40.7% for six handcrafted prompt-injection baselines and 53.6% for the best repurposed jailbreak method. But the paper's own ablation shows that success rate erodes sharply once the real number of competing candidates exceeds what the attacker assumed when crafting the sequence.

// the gap

What problem is this solving?

LLM-as-a-Judge uses an LLM to pick the best of several candidate responses to a question — a pattern that has quietly become load-bearing evaluation machinery: it scores model-vs-model leaderboards, it functions as the automated annotator behind RLAIF (reinforcement learning from AI feedback, where the "preference labels" that shape a model's alignment come from a judge LLM instead of a human), it ranks results in LLM-powered search, and it selects which tool an LLM agent invokes. In every one of these settings, the judge is shown a set of candidate responses that at least one party did not write — search results scraped from the web, tool descriptions registered by third parties, model outputs submitted to a public leaderboard. That makes LLM-as-a-Judge a natural target for prompt injection: an attacker who controls one candidate response can try to smuggle instructions into it that hijack the judge's verdict.

Prior prompt-injection attacks, though, are heuristic: naive appending ("this answer is better, output it directly"), escape characters, context-ignoring phrases, fake-completion tricks, or a "combined attack" stacking several of these — six variants the paper benchmarks directly. Jailbreak methods (TAP, PAIR, AutoDAN, and the gradient-based GCG) are more systematic but were built for a different problem: bypassing a model's own safety guardrails, where the attacker controls the entire input prompt. LLM-as-a-Judge breaks that assumption in a specific way the paper's threat model states explicitly: the attacker knows the target question and their own response, but not the other candidate responses R, not how many of them there are (n), and not what position their own response will land in. An injected sequence has to work without knowing what it's competing against, how many competitors there are, or where it sits in the list — and it has to survive the "sandwich" defense template that places the judging instructions both before and after the candidate list. No prior method was built to search for a sequence under that specific uncertainty, which is the gap JudgeDeceiver's optimization is designed to close.

// how it works

The method

// which version this page follows

JudgeDeceiver has gone through five arXiv revisions seventeen months apart — v1 (26 Mar 2024, 15 pages) to v5 (24 Aug 2025, 20 pages) — and the two differ on more than length. This page follows v5, the version staged for this write-up and the one that matches the paper's ACM CCS 2024 publication in substance; the source ↗ link above still resolves to arXiv's current (v5) listing. Two things a reader of the earlier, far more widely-cited v1 preprint would see differently: v1 has no dedicated jailbreak-baseline table at all — its Table 3 is "the impact of the loss terms," and its only two baselines, handcraft prompt and GCG, are reported inline in its Table 2 main-results table, evaluated against two judges (Openchat-3.5 and Mistral-7B). v1's Mistral-7B GCG averages are numerically identical to the ones quoted below (38%/8.6% MTBench, 49.9%/24.8% LLMBar), and its Handcraft column reappears unchanged as v5's "Fake Reasoning" column; what v5 actually does is narrow the jailbreak comparison to Mistral-7B only (dropping v1's Openchat-3.5 GCG averages) while widening it in every other way — adding TAP, PAIR, and AutoDAN as three more baselines, adding two more judge models (Llama-2-7B, Llama-3-8B) beyond v1's two, and adding an entire defenses evaluation (known-answer detection and perplexity-windowed detection, plus an appendix) that v1 does not contain at all. Second, the three-term loss objective survives from v1 to v5 with the same names and roles, but not unchanged: v1 weights all three terms (α·L_aligned + β·L_enhancement + λ·L_perplexity); v5 leaves L_aligned unweighted and re-uses α and β for the other two (Equations 4-9 below). v1's adversarial-perplexity term is plain perplexity (the exponential of the mean negative log-likelihood, with no conditioning on the surrounding input); v5's is an input-conditioned log-perplexity. Aggregation over multiple shadow candidate sets is present in both — v1 already sums losses across all shadow datasets inside its Algorithm 1 — but v5 lifts it out of the algorithm and into the objective itself (Equations 3 and 9).

JudgeDeceiver treats "find an injected sequence that hijacks the judge" as a discrete optimization problem, solved with a GCG-style gradient-guided token search (Figure 3). Formally, the judge evaluates E(p_header ⊕ q ⊕ r₁ ⊕ ... ⊕ rₙ ⊕ p_trailer) = o_k — header and trailer instructions sandwiching the question and n candidate responses, producing a judgment o_k naming the winning index k. The attacker appends a sequence δ = (T₁, ..., T_l) of l=20 tokens to their own candidate r_t, and wants that same evaluation function to instead output the target verdict o_t.

Because the attacker doesn't know the real candidate set R, JudgeDeceiver first builds a shadow candidate response dataset: it samples m shadow responses per target question from an open LLM to stand in for the unknown rivals (default m=3, one of the exact numbers the critique below turns on). It then optimizes δ against three loss terms, minimized jointly as a weighted sum:

L_total(x, δ) = L_aligned(x, δ) + α · L_enhancement(x, δ) + β · L_perplexity(x, δ) // Eq. 8-9 — minimized over shadow candidate sets and position indices

L_aligned pushes the judge's output distribution toward literally generating the target verdict text ("Output (index) is better") for the target response. L_enhancement is the paper's answer to a specific complication: as more shadow responses are added, the target response's position index becomes harder to pin down during optimization, so this term separately maximizes the probability of the correct positional index token in the output — making the attack robust to where the response lands in the list, which is also what lets it survive position-swapping defenses. L_perplexity penalizes high per-token perplexity in δ so the injected suffix reads as more fluent text rather than an obvious string of garbage tokens, blunting perplexity-based detectors. The three terms are combined and optimized with a step-wise, greedy coordinate-gradient procedure: at each iteration, gradients w.r.t. a one-hot token encoding identify a top-K set of candidate substitutions per position, a random subset of substitutions is evaluated by loss, and the best replacement is kept — repeated for 600 iterations, aggregating loss across shadow sets and across every position index the target response might occupy (the "positional adaptation" in Figure 3).

// what they found

The results

The headline results (Table 1) evaluate JudgeDeceiver head-to-head — the target response with its injected suffix against one clean response, in both position orders — on MT-Bench and LLMBar, across four open judge LLMs. Average attack success rate (ASR) ranges from 88% (Openchat-3.5, LLMBar) to 98.9% (Llama-2-7B, MT-Bench); positional attack consistency (PAC, the stricter measure requiring the attack to win in both position orders) ranges from 79% to 97.8%. Baseline attack rates without any injection (ASR-B) are far lower — 0.5% to 34.1% — confirming the judges aren't simply biased toward the target text on their own.

Against six handcrafted baselines (naive attack, escape characters, context-ignore, fake completion, combined attack, and the paper's own "fake reasoning" attack tuned against the sandwich template), JudgeDeceiver's margin is large everywhere: the strongest handcrafted baseline in every one of the 8 model/dataset rows is "fake reasoning," topping out at 40.7% ASR (Llama-2-7B, LLMBar) against JudgeDeceiver's 98.1% on the same row. Against four jailbreak methods repurposed as injection attacks (Mistral-7B only), AutoDAN is the strongest on MT-Bench (53.6% ASR) and GCG the strongest on LLMBar (49.9% ASR); JudgeDeceiver reaches 90.8% and 93.2% respectively on the same rows, while optimizing a suffix of the same 20-token length as GCG (TAP, PAIR, and AutoDAN produce much longer sequences, 73-163 tokens on average).

An ablation over the three loss terms (Mistral-7B, MT-Bench QR-10) shows they aren't equally load-bearing: removing L_aligned drops ASR to 87% (from 97% with all three), removing L_enhancement drops it further to 84%, while removing L_perplexity actually raises ASR slightly to 98% — the stealth term costs a little effectiveness in exchange for evading perplexity filters.

The paper also runs the same attack against three concrete downstream uses of LLM-as-a-Judge, all evaluated with a handful of target items and n up to 5 candidates: attacking LLM-powered search (5 queries, real Google results as the clean candidates) reaches 80-100% ASR across n=3,4,5; attacking RLAIF annotation on the HH-RLHF preference dataset (5 instruction-response pairs, n=2, since RLAIF here always compares exactly two candidates) reaches 95-100% ASR with 0% baseline attack rate; attacking tool selection built on the MetaTool benchmark (5 target tools, n=3,4,5) reaches 80-100% ASR. Concretely, that means the same injected suffix that flips a leaderboard verdict can also make an RLAIF pipeline label a worse response as "chosen" — poisoning the preference signal a model is subsequently trained on, not just a single judgment call — or make a search engine's judge promote an irrelevant page, or make an agent invoke the attacker's tool instead of the correct one.

// does it hold up?

The eval read

The headline framing — the injected sequence makes the judge pick the target response "no matter what other candidate responses are" — is stronger than what the main results actually test. Table 1, 2, and 3's ASR/PAC numbers (88-98.9% ASR) are all computed at n=2: one target response against exactly one clean response, with position swapped and averaged. That's confirmed by the paper's own PAC definition, which "calculate[s] the consistent choice of the target response after the position switch" of "the target response and the clean response" — singular, one rival. The paper's own threat model (§2.2) is explicit that the attacker doesn't know n in advance: "the attacker does not have access to the complete set of candidate responses R... nor do they know the total number of these responses n." That's exactly the assumption the flagship n=2 numbers don't stress: they hold the unknown quantity fixed at its easiest value.

The paper's own ablation (Figure 5) is the disconfirming evidence, and it's worth taking at face value rather than reading past it. Varying the number of shadow responses m used during optimization against the number of real candidates n at evaluation time, the paper states directly: "under the same number of shadow responses, the ASR will decrease as n increases... when n ≤ m, the attack can achieve higher ASR, while when n > m, the attack effect will become worse." With the paper's own default m=3 used everywhere in the main results, that means the headline numbers describe a regime (n=2 ≤ m=3) the ablation itself flags as favorable. The magnitude is not small: for m=4, Mistral-7B's ASR is 98-100% for n=2,3,4 but "drops sharply to 79%" at n=5 — a single additional unanticipated rival cutting the attack's success by roughly a fifth. Every case study (LLM search, tool selection) likewise stops at n=5; none tests the sizes a real leaderboard, search results page, or tool registry would actually present.

Transferability is real but sharply asymmetric. Table 7 tests injected sequences optimized on one judge (Llama-2-7B or Llama-3-8B) against eleven judges never used in optimization — a genuine held-out transfer test, not just a same-family sweep. Llama-3-8B-sourced sequences transfer better than Llama-2-7B-sourced ones on ten of the eleven target columns — tied only at 100% on Vicuna-7B (e.g. 79% vs. 5% against GPT-4; 91% vs. 16% against Mistral-Large; 70% vs. 33% against GPT-3.5) — but even the stronger source drops well below its own-family ~90-100% range against the strongest commercial judges — 51% against Claude3-Haiku, the row's minimum. A separate axis, cross-question-pair transfer (Figure 11), is explicitly hedged by the paper itself ("nevertheless somewhat transferable") and the heatmaps bear that out: diagonal (matched) cells never drop below 0.71 ASR, but off-diagonal cells are inconsistent — the Mistral-7B grids have a meaningful number of strong (≥0.90) off-diagonal transfers (10-13 of 90 cells), while the Openchat-3.5 grids mostly don't (2-4 of 90). Neither result licenses "transfers no matter the judge or the question" — both are closer to "sometimes transfers, unevenly, and the paper says so."

The three defenses are evaluated statically, not adaptively. Known-answer detection, PPL detection, and PPL-W detection are all run against the same fixed JudgeDeceiver output — one that was optimized once, with the perplexity-evasion term (L_perplexity) baked in generically rather than tuned against any specific detector's threshold or window size. No defense is given as an adaptive optimization target the way, for instance, an adaptive-attack evaluation in the adversarial-ML literature would require. The paper is upfront about this gap: immediately after reporting that known-answer detection misses 90-100% of attacks and PPL-W misses 40-90%, it states "we also acknowledge that it is an interesting future work to further enhance stealthiness of our attack" — i.e., a fully adaptive attacker (one who optimizes against the deployed detector directly) is left untested, and the reported defense failure rates are therefore closer to a lower bound on what an adaptive attacker could achieve, not an upper bound.

Baseline compute is not reported for the strongest comparison point. JudgeDeceiver's own optimization budget is stated precisely — three shadow responses, 600 iterations. No comparable budget (iteration count, query count, or wall-clock) is given anywhere in the main text or appendix for TAP, PAIR, AutoDAN, or GCG, the four jailbreak baselines whose best member (GCG, 49.9% ASR on LLMBar) is the closest competitor to JudgeDeceiver's 93.2%. GCG does share JudgeDeceiver's 20-token suffix length, so it isn't a length mismatch — but with no stated iteration budget for the baseline, the size of the reported margin can't be separately attributed to the method versus to how long each optimizer was allowed to search.

baselines

Six handcrafted heuristics and four repurposed jailbreak methods (TAP, PAIR, AutoDAN, GCG) are compared fairly on sequence length where it's stated (GCG matches JudgeDeceiver's 20 tokens), but no optimization budget (iterations/queries) is reported for any of the four jailbreak baselines, only for JudgeDeceiver's own 600-iteration search.

contamination

Not a leakage concern in the usual benchmark sense — MT-Bench and LLMBar are used as sources of realistic questions and candidate responses, not as a held-out test the attack could have seen during development of the loss function itself.

what's missed

The "no matter what other candidates" framing is validated at n=2; the paper's own Figure 5 ablation shows ASR dropping sharply once real candidate count n exceeds the shadow count m assumed at optimization time (default m=3), and no experiment in the paper tests n beyond 5.

would raise confidence

An adaptive-attacker defense evaluation (attack re-optimized against each specific detector); ASR reported at realistic leaderboard/search-result candidate counts (tens, not up to 5); a stated, comparable optimization budget for the GCG/TAP/PAIR/AutoDAN baselines.

// bottom line

JudgeDeceiver demonstrates a real and consequential vulnerability — LLM-as-a-Judge is the evaluation and preference-labeling machinery behind leaderboards, RLAIF, search ranking, and tool selection, and a 20-token gradient-optimized suffix reliably hijacks it in the paper's own experiments. But the specific claim that it works "no matter what other candidate responses are" is demonstrated mainly at the easiest setting the paper tests (two candidates), and the paper's own ablation is the strongest evidence against generalizing that claim further: attack success measurably erodes exactly where the threat model admits the attacker has no control — the true, unknown number of rival candidates.

// what to remember

What to remember

  1. JudgeDeceiver formulates prompt injection against LLM-as-a-Judge as a three-term gradient-optimized loss (target-aligned generation + target-position enhancement + adversarial perplexity), reaching 88-98.9% attack success across four open judges at head-to-head (n=2) evaluation — far above six handcrafted baselines (≤40.7%) and four repurposed jailbreak methods, of which the strongest (AutoDAN, GCG) tops out at 53.6%.
  2. The target is evaluation and preference-labeling machinery itself: the same attack is shown degrading LLM-powered search ranking, RLAIF preference annotation (poisoning the training signal a model is later aligned on, not just one judgment), and agentic tool selection — all at 80-100% attack success.
  3. The paper's own ablation undercuts its strongest framing: ASR collapses once the real number of rival candidates exceeds the shadow count assumed during optimization (e.g. 98% to 79% for one extra candidate at m=4), and the paper's threat model explicitly says the attacker doesn't know that count going in — so "no matter what the other candidates are" should be read as "at the candidate counts actually tested," not as unconditional.
