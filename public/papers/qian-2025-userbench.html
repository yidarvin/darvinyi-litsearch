UserBench: An Interactive Gym Environment for User-Centric Agents

A Gymnasium environment where the "task" is really a hidden person: the simulated user starts with a vague travel request and only reveals preferences when an agent asks well, forcing a split between whether the agent finishes the task and whether it ever understood what the user wanted.

// the gap

What problem is this solving?

Agent benchmarks have gotten good at measuring whether a model can call the right tool. They have mostly not measured whether the model understood what the human asking for the tool call actually wanted — because most of them hand the agent a fully-specified task up front. UserBench's authors argue real requests rarely arrive that way: people under-specify ("book me a flight to SF"), reveal constraints incrementally as the conversation goes on, and often state preferences indirectly rather than as a checklist ("I always keep my schedule packed tight" instead of "I want a direct flight"). They name these three traits underspecification, incrementality, and indirectness, and build a benchmark specifically to stress them.

The paper's Table 1 scores eight prior interaction benchmarks — τ²-Bench, τ-Bench, ToolSandbox, MINT, IN3, ToolTalk, API-Bank, MetaTool — against nine traits (multi-turn interaction, goal ambiguity, tool use, dynamic state, multi-aspect reasoning, user simulation, domain diversity, customizability, scalability). None of the eight checks all nine; several strong tool-use benchmarks (API-Bank, MetaTool) don't attempt multi-turn user simulation at all, and τ-Bench / τ²-Bench simulate a user but don't score multi-aspect reasoning across several interdependent decisions in the same conversation. UserBench is the only row the paper marks as fully checking every trait — which is exactly the gap the rest of the paper is built to fill: an environment where the agent must run a whole travel plan (flight, hotel, apartment, car, restaurant) through one conversation with a user who never states all of her constraints at once.

// how it works

The method

UserBench is a travel-planning Gym environment (built on the standard Gymnasium step()/reset() interface) spanning five aspects — flight, hotel, apartment, car rental, restaurant. Each test scenario is constructed from a library of roughly a hundred curated, realistic preferences (Table 2 counts 82 total preferences across 24 categories in the released set) spanning the five aspects, each one paired with several natural, implicit ways of expressing it without stating it outright (the paper's example: "I always keep my schedule packed tight, so I prefer travel routes that minimize transit time" for a direct-flight preference). Preferences are randomly combined into scenarios and bucketed into three difficulty tiers by how many preferences are involved: Easy (118 test scenarios, e.g. "Travel-22" — two aspects, two preferences each), Medium (201, e.g. "Travel-33"), Hard (152, e.g. "Travel-44"), for 471 test scenarios total in Table 2 (the running text instead says "417 data points for testing," a discrepancy the paper doesn't reconcile) plus 2,651 scenarios held out for future training.

Every aspect gets its own mock search tool (flight/hotel/apartment/car/restaurant search) returning pre-generated — not live — options, each scenario's option pool built from three kinds of entries: correct options (satisfy every preference; exactly one is "best," the correct option with lowest total cost under the paper's budget-aware setting), wrong options (violate at least one preference), and noise options (irrelevant or unrealistic — the paper's own example is a flight quoted at $1,000,000 for a 1,000-hour "direct" trip). Table 2 records a base composition of 1 best / 3 correct-total / 10 wrong / 5 noise options per aspect, and the paper notes a full scenario can carry "up to over 100 options" once several aspects are combined.

Inside an episode (capped at 20 turns, GPT-4o at temperature 0 driving the user side), the tested agent must invoke one action per turn through a single required tool call: search (query a database by aspect and arguments — the environment only returns results if the arguments exactly match the scenario's ground truth), action (talk to the simulated user), or answer (submit one or more option IDs per aspect for scoring). Every "action" utterance is itself classified by an LLM judge into one of four types: a concrete ask about a preference the user actually holds (which triggers an implicit reveal of that preference), a concrete ask about a preference the user doesn't have, a vague general question, or ordinary conversation. If the agent goes three consecutive turns without a valid, concrete ask, the environment proactively — and still implicitly — reveals one of the user's remaining preferences on its own; the paper counts this as passive elicitation, distinct from preferences the agent surfaced itself (active elicitation).

Scoring, in the paper's own worked example: for each aspect, selecting the best option earns 1.0, a correct-but-not-best option earns 0.8, anything else earns 0.0; in the multi-choice setting the environment takes the max reward among the options the agent submitted for that aspect, then averages across aspects.

Final Score = max(1.0, 0.8) + max(0.0, 0.8, 0.0)2 = 0.9 // the paper's own two-aspect worked example: aspect 1 selections score {1.0, 0.8}, aspect 2 selections score {0.0, 0.8, 0.0}

Two optional variants extend the base setup: a noisy-search mode that corrupts a configurable fraction of search results, and a budget-aware mode (used in all reported experiments) that specifically rewards the lowest-total-cost option among the correct ones rather than any correct option equally.

// what they found

The results

The authors test 11 models — GPT-4o, GPT-4o-mini, Gemini-2.5-Pro, Gemini-2.5-Flash, Claude-4-Sonnet, Deepseek-V3, Qwen3-8B/14B/32B, Llama-3.1-8B, Llama-3.3-70B — under two answer formats. In the single-choice setting (the paper's main evaluation), the agent may submit exactly one option per aspect; in multi-choice, it may submit several, and the environment scores the best-reward pick among them. GPT-4o leads both settings on the headline Score metric: 0.329 single-choice, 0.710 multi-choice — with Gemini-2.5-Pro (0.317 / 0.673) and Claude-4-Sonnet (0.307 / 0.612) close behind, and Gemini-2.5-Flash trailing every model in single-choice at 0.125. Every one of the 11 models scores higher in multi-choice than in single-choice (e.g. Gemini-2.5-Flash rises from 0.125 to 0.311), consistent with the paper's framing that the single-answer constraint is what makes the benchmark hard.

Two dissociations stand out in the auxiliary metrics (all from Table 3, single-choice). First, tool use is not the bottleneck: valid Search Attempt rates sit well above valid Action Attempt rates for essentially every model (e.g. GPT-4o 82.48% search-valid vs. 27.82% action-valid; Claude-4-Sonnet 74.28% vs. 24.26%), meaning models issue well-formed database queries far more reliably than they issue genuinely targeted clarifying questions. Second, eliciting preferences and scoring well are not the same skill: Claude-4-Sonnet has the highest overall Preference-Elicited rate in both settings (34.25% single-choice, 42.21% multi-choice) yet is not the Score leader in either — GPT-4o is, despite eliciting noticeably fewer preferences (27.32% / 15.10%). The paper's own weighted-timing analysis (Table 5, which re-weights each model's first valid answer by w(i)=1/(i+1)) makes the same point from a different angle: Gemini-2.5-Flash has both the earliest average first valid answer of any model (turn index 0.927) and the lowest Weighted Score (0.054 for GPT-4o vs. 0.014 for Gemini-2.5-Flash) and lowest Correct-Exists Rate (0.080) — i.e. it guesses fast and is usually wrong.

Ablations narrow down what actually drives difficulty. Holding the number of travel aspects fixed and increasing preferences per aspect (Travel-22 → 33 → 44, averaging 0.257 → 0.224 → 0.200) hurts scores more than holding total preferences fixed and spreading them across more aspects (Travel-44 → 233 → 2222, all totaling 8 preferences, averaging 0.201 → 0.190 → 0.241) — preference density per aspect, not preference count or aspect count on its own, is what the paper identifies as the main difficulty driver. Two further ablations suggest the ceiling is a reasoning one rather than a budget one: giving four tested models (GPT-4o, Deepseek-V3, Qwen3-14B/32B) more interaction turns (15→30) does not produce consistent gains, and pass@k sampling (k=1→16) raises the best-of-k Max score steadily while the Avg score stays roughly flat — the paper reads this as models relying on "sampling luck" more than reliable reasoning. Reducing the number of wrong/noise distractor options (Table 6) also gives only modest gains for strong models (Deepseek-V3's biggest single lift is +0.048, from 0.223 to 0.271, when noise options are removed entirely) and even small drops for Qwen3-14B in two of three reduced-distractor configurations.

// does it hold up?

The eval read

UserBench's central move — separating "did the agent finish the task" from "did the agent ever find out what the user wanted" — is a real and useful distinction, and the paper's own numbers back it up cleanly. But the whole benchmark is built and graded by one model, and that model is also a contestant, which raises questions the paper doesn't test.

GPT-4o plays four roles at once. It generates the ideal-itinerary text and the database options during dataset construction (under human supervision), it drives the simulated user during every evaluated episode (temperature 0), it is the LLM judge behind all four in-episode prompts (search-argument alignment, action-utterance-type classification, implicit preference reveal, and neutral continuation), and it is also one of the 11 tested agents — where it wins outright on Score in both settings. None of this means the result is wrong, but it does mean a reader can't currently distinguish "GPT-4o understands users best" from "GPT-4o's outputs are easiest for a GPT-4o-driven judge and GPT-4o-authored data to score well," because the paper reports no ablation that swaps the user-simulator/judge backbone to a different model and re-ranks the same 11 agents.

The headline abstract numbers are scoped to one setting without saying so. The abstract states "even the most advanced models uncover fewer than 30% of all user preferences through active interaction" — true for the single-choice table (max: Claude-4-Sonnet at 26.31% active), but not for the multi-choice table reported in the same paper, where Claude-4-Sonnet's active elicitation rate is 30.67%. A reader who checks only the multi-choice table would find the claim false as stated; it needs the single-choice qualifier the abstract omits.

"Top-performing models" clearing 80% search-validity depends on which table you read. The results narrative says "Top-performing models maintain over 80% success in valid search attempts" in a section that summarizes both Table 3 and Table 4. In the single-choice table the paper calls its main evaluation setup, only one of the top three Score-ranked models clears 80% search-valid — GPT-4o (82.48%), not Gemini-2.5-Pro (77.40%) or Claude-4-Sonnet (74.28%) — but all three do clear it in the multi-choice table (85.96%, 80.43%, 87.94% respectively). The single highest search-validity rate in the single-choice table, 83.62%, belongs to Gemini-2.5-Flash, the lowest of the 11 models on Score, Best Exist Rate, Correct Exist Rate, and total Preference Elicited — a dissociation the paper itself calls out ("Some models, such as Gemini-2.5-Flash, achieve high Action Attempt Valid rates but relatively low Active Preference Elicited"). Search competence and preference-driven decision quality are visibly not the same axis, consistent with the paper's broader argument — but the "over 80%" framing is defensible only if read against the multi-choice table, and is a near-miss (1 of 3) in the single-choice table the paper treats as primary.

To its credit, the paper is upfront about one closely related risk itself: it flags Action Attempt Valid % as "a relative metric — high validity does not necessarily mean more preferences are elicited," giving its own example of a model that asks a single valid question and scores 100% on that metric alone. That's exactly why the paper reports Preference Elicited % (Active/Passive) as a separate, absolute-coverage metric — a distinction worth keeping straight when quoting either number.

A couple of smaller internal numbers don't quite reconcile: the running text says the benchmark reserves "417 data points for testing" while Table 2's own total row says 471; and the diversity claim of "around a hundred distinct preferences" sits against Table 2's printed total of 82. (GPT-4o's single-choice Score reads 0.340 in Table 6's ablation against 0.329 in Table 3's main results, but the paper states explicitly that Table 6's choice-distribution ablation, like the turn-based and pass-k analyses, runs only on the Travel-22/33/44 scenario subset rather than the full test set — so that gap is expected, not a slip.) Neither remaining discrepancy looks like a validity-threatening error — they read like reporting slips — but they mean the exact scenario counts are worth re-deriving from the released data rather than quoting from the paper verbatim.

baselines

11 models spanning GPT-4o/4o-mini, Gemini-2.5-Pro/Flash, Claude-4-Sonnet, Deepseek-V3, Qwen3-8B/14B/32B, and Llama-3.1-8B/3.3-70B — a reasonably current mid-2025 mix of closed and open models, all run single-seed at temperature 0 with no reasoning-focused models (o1/o3, DeepSeek-R1) included.

contamination

The dataset is fully synthetic (GPT-4o-generated ideal-scenario text and search-space options, both under human supervision; the implicit preference phrasings themselves are hand-curated and validated rather than model-generated), so classical pretraining leakage of this exact test split is unlikely pre-release. The paper does earmark 2,651 held-out scenarios for future SFT/RL training on the same environment, but says nothing about keeping that split separate from future evaluation use.

what's missed

No human validation of the live user-simulator's judgments (intent-type classification, implicit-reveal quality); no ablation swapping the user-simulator/judge backbone away from GPT-4o, despite GPT-4o also being a top-scoring contestant; the turn-cap and pass@k ablations run on only 4 of the 11 tested models, leaving variance and scaffold-sensitivity uncharacterized for the rest.

would raise confidence

A held-out human or cross-model check of a sample of user-simulator/judge decisions; re-ranking the 11 agents with a non-GPT-4o simulator backbone; multi-sample (not single temp-0 run) main-table numbers; extending Figures 5–6's ablations to all 11 models.

// bottom line

The dissociation UserBench surfaces — strong tool use, weak preference elicitation, and a wide gap between eliciting preferences and actually using them — is a real and well-evidenced finding within the paper's own tables. But because one model (GPT-4o) authors the data, plays the user, judges every turn, and also wins the leaderboard, the benchmark's rankings should be read as conditional on that specific evaluator stack until someone reruns it with a different backbone in the judge/user seat.

// takeaways

What to remember

  1. UserBench targets a gap tool-use benchmarks miss by design: models with 74–83% valid search rates still plateau near a 0.33 Score in the single-choice setting, because failure comes from not eliciting the user's hidden preferences (GPT-4o elicits 27.32% of them in total, only 24.06% through its own questions) rather than from failing to operate the search tools.
  2. The paper's own ablations localize the difficulty driver to preference density per aspect (not aspect count or total preference count) and show scores are largely insensitive to letting agents run more turns or sample more times — evidence for a reasoning ceiling rather than an interaction-budget one.
  3. GPT-4o simultaneously authors the benchmark's data, drives the simulated user, judges every in-episode decision, and tops the leaderboard as a tested agent — a four-way overlap the paper doesn't ablate, so cross-model rankings should be read as conditional on that specific evaluator stack.
