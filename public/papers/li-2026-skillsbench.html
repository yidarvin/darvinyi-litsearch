SkillsBench: Benchmarking How Well Agent Skills Work Across Diverse Tasks

SkillsBench pairs the same 87 real-world tasks with and without a curated Agent Skills bundle across 18 model-harness configurations, isolating what a Skill actually adds: curated Skills raise the mean pass rate from 33.9% to 50.5% (+16.6 points), while Skills an agent writes for itself land below the no-Skills baseline.

What problem is this solving?

Agent Skills — Anthropic's format for structured, file-system-based procedural packages (a required SKILL.md plus optional scripts, templates, and reference material) that an agent harness can discover and load at inference time without touching model weights — have gone from a launch announcement to a sprawling ecosystem in a few months. SkillsBench's own construction snapshot counts 2,014,000 unique source-partitioned Skills (234,896 direct GitHub/source Skills, 1,773,213 marketplace Skills, and 5,891 partner Skills), up more than an order of magnitude from an earlier 37k-Skill snapshot taken in January 2026. Daily new-Skill creation peaked at 33,692 on April 7, 2026.

Despite that proliferation, the paper argues there was no standard way to answer a simple deployment question: does adding this Skill help my agent on this task, and by how much? Existing agent benchmarks — AgentBench, WebArena, SWE-bench, Terminal-Bench, and others the paper cites in its related-work survey — measure end-to-end task completion, folding model capability, harness implementation, and any augmentation (tools, retrieval, Skills) into a single pass rate. None of them isolate the marginal contribution of a Skill by holding the model and harness fixed and only toggling Skill access. SkillsBench is built specifically to answer that narrower, paired question, using a benchmark of 87 tasks across 8 domains, each shipped with a curated Skills bundle and a deterministic verifier.

// how it works

The method

Every SkillsBench task is a self-contained, containerized module with four parts: a human-authored instruction, a Docker environment with task data (and a skills/ subdirectory holding the curated bundle), an oracle reference solution that must pass the verifier end-to-end, and a deterministic pytest-based verifier. Tasks are run under three possible conditions that share the same instruction, container, and test battery: Condition A (no Skills) — instruction only; Condition B (curated Skills) — the expert-authored bundle is mounted for the agent to discover (never named in the instruction itself, so the agent must find it through the standard progressive-disclosure mechanism); and Condition C (self-generated) — a separate, clean agent session first authors its own Skill packs using Anthropic's skill-creator tool, and a fresh solver session then attempts the task with only those self-authored packs mounted. Each condition yields a fraction-of-tests-passed score (rA, rB, rC); Skill efficacy is read off as ∆curated = rB − rA and ∆self = rC − rA, both against the same no-Skills baseline.

The primary metric is task-macro pass rate, following Terminal-Bench: for each (task, condition) cell the three selected public trials are averaged, then those per-task scores are averaged over the fixed 87-task inventory. The paper reports this alongside normalized gain, which measures how much of the remaining headroom above the no-Skills baseline the Skill closes:

g = PassRate(curated) − PassRate(no Skills)1 − PassRate(no Skills) // normalized gain — proportional progress toward a perfect (100%) pass rate; interpreted jointly with the absolute ∆ so a small gain near the ceiling isn't overstated

Construction treats the filtering pipeline as part of the contribution, not an afterthought, because a benchmark that measures "Skill efficacy" collapses into ordinary instruction-following the moment a Skill is allowed to encode a task-specific answer. The team grew a 1,400-member contributor community and ingested 400 candidate task submissions from 142 contributors. Every submission must clear four automated gates (structural integrity; 100% oracle pass; an AI-text detector plus human label on the instruction, yielding a fully human-authored release set; and a Skill-to-solution leakage audit that rejects task-specific filenames, magic numbers, or verbatim oracle commands in the Skill) before at least one 30-minute maintainer review — and tasks with no measurable separation between the no-Skills and curated-Skills conditions are rejected outright as "low-signal." 87 of the 400 submissions (22%) survived to the current public evaluation aggregate, spanning 8 domains and, by estimated human-specialist completion time, 6 Core (<60 min), 53 Extended (1–4 h), and 28 Extreme (>4 h) tasks.

The latest aggregate evaluates 18 model–harness configurations under matched no-Skills and curated-Skills conditions: OpenHands paired with 15 different models (from Gemini 3.1 Flash Lite up to GPT-5.5), plus one configuration each for Gemini CLI (Gemini 3.1 Pro), Claude Code (Claude Opus 4.7), and Codex CLI (GPT-5.5) — the fixed frame targets 18 × 87 × 2 conditions × 3 trials = 9,396 result slots, with 9,396 selected public trials currently available. The self-generated condition is evaluated only on the three dedicated-harness configurations (Claude Code + Opus 4.7, Codex + GPT-5.5, Gemini CLI + Gemini 3.1 Pro) and reported as a separate diagnostic rather than folded into the main two-condition aggregate.

// what they found

The results

Across all 18 model–harness configurations, curated Skills raise the mean task-macro pass rate from 33.9% to 50.5% — an absolute gain of +16.6 percentage points and a normalized gain of 25.5%. Every single configuration improves, but the size of the improvement varies enormously: from +4.1 pp (OpenHands + Gemini 3.1 Flash Lite, nearly flat) up to +25.7 pp (OpenHands + GLM 5.1). The strongest absolute performers with Skills — OpenHands + GPT-5.5 (67.3%), Codex + GPT-5.5 (66.5%), Claude Code + Opus 4.7 (61.2%) — are not the biggest beneficiaries of Skills; the paper's Finding 2 names the largest lifts as OpenHands + GLM 5.1 (+25.7 pp), Gemini CLI + Gemini 3.1 Pro (+24.8 pp), and OpenHands + DeepSeek V4 Pro (+23.2 pp) — though Table 2 itself ranks OpenHands + MiniMax M3 (+23.3 pp) just above DeepSeek V4 Pro. OpenHands + Gemini 3.5 Flash illustrates the opposite pattern: a strong 41.1% no-Skills baseline but only a +7.1 pp gain.

Harness choice changes how the same model benefits: GPT-5.5 reaches 67.3% with Skills in OpenHands vs. 66.5% in Codex; Gemini 3.1 Pro reaches 60.8% in Gemini CLI vs. only 52.8% in OpenHands; Claude Opus 4.7 reaches 61.2% in Claude Code vs. 53.1% in OpenHands. The paper also separates discovery from resolution: it defines a per-configuration Skill Invocation Rate (a curated-Skills trial counts only if the trajectory actually reads or invokes the task-specific Skill under environment/skills) and finds invocation rates are frequently high even where resolution stays low — i.e., Skill discovery is usually not the bottleneck to Skill efficacy.

Cybersecurity and Media & Content Production sit below the paper's own N = 8 task-count threshold, though, so it flags per-domain claims on those two slices as descriptive rather than inferential until more tasks are added.

Two design ablations refine the picture further. By Skill count: tasks paired with exactly 1 Skill gain +18.0 pp, 2–3 Skills gain +19.0 pp, but ≥4 Skills gain only +10.1 pp — bundling in more Skills doesn't compound the benefit. By Skill documentation length (bucketed by SKILL.md size at the 25th/50th/95th percentiles): Compact (+19.0 pp) and Standard (+21.5 pp) documentation beat Detailed (+14.5 pp), and Comprehensive documentation is essentially flat (+0.7 pp). And on the model-vs-Skills tradeoff: MiniMax M2.7 with Skills reaches 34.9%, exceeding stronger no-Skills baselines such as OpenHands + GLM 5.1 (32.7% without Skills) and OpenHands + MiniMax M3 (29.7% without Skills) — Skills can partly substitute for model capacity on procedural tasks.

Not every Skill helps: 13 of the 87 tasks show negative deltas under curated Skills, the largest drops on exam-block-sequencing and suricata-custom-exfil (−7.4 pp each), and on adaptive-cruise-control, mars-clouds-clustering, r2r-mpc-control, and econ-detrending-correlation (−5.6 pp each). A paired-trajectory audit attributes these to three repeatable patterns: the Skill points to an unnecessarily heavyweight pipeline that crowds out a simpler valid path, Skill activation displaces a stronger native strategy the agent would otherwise have used, or the Skill routes the agent into a brittle solver it can't debug.

The trajectory audit attributes the deficit to a mix of causes: generated packs the solver session never discovers, creator-side authoring effort that displaces solver progress (only relevant in the Claude Code realization, which regenerates packs inside the same trial's sandbox), and packs whose content is confidently wrong when it is used.

// does it hold up?

The eval read

SkillsBench's verification is genuinely rigorous where it counts: every one of the 87 tasks is scored by a deterministic pytest-based verifier rather than an LLM judge, oracle solutions must pass 100% before a task is admitted, and the leakage audit explicitly rejects Skills that smuggle in task-specific filenames, magic numbers, or verbatim oracle commands. That's a real, checkable rigor bar most agent benchmarks don't clear. But two of the paper's own design choices deserve more scrutiny than the headline +16.6 pp gets.

First, the task-admission pipeline explicitly filters for the effect being measured: "tasks with no measurable separation between conditions are rejected as low-signal." That's a defensible engineering choice — a task where Skills can't possibly matter is a wasted verifier — but it means the accepted 87-task population is not a random or representative sample of real work; it's pre-selected for Skill-sensitivity. A benchmark built this way will, structurally, always show Skills "help" on average, regardless of the true population-wide rate at which Skills help or hurt across arbitrary tasks. Second, the curated Skills used in the main aggregate score 10.1/12 on the paper's own quality rubric, against a measured ecosystem mean of 6.2/12 — the authors call this an "optimistic scenario" themselves in Appendix A.4. Combined with the low acceptance rate (87 of 400 submissions, 22%), the +16.6 pp headline describes an upper bound under top-quartile Skills and Skill-sensitive tasks, not the average effect a practitioner should expect from a random Skill pulled off the 2-million-Skill marketplace.

The self-generated-Skills condition is the paper's most interesting result — Skills an agent writes for itself land below not using Skills at all — but it's only run on 3 of the 18 configurations, so the strongest available counterfactual for "is it curation, specifically, that matters, or just having some skill-shaped text in context" covers a sixth of the evaluated aggregate. The paper is also candid about two confounds it doesn't fully resolve: Skill injection lengthens context, so part of the gain could reflect "more context" rather than procedural content (the self-generated condition only partially controls for this, since its own deficit mixes content quality with discovery and creator/solver interference effects); and Claude models were trained with awareness of the Agent Skills specification itself, a harness-model interaction the paper flags (Appendix D.3) but does not isolate.

baselines

18 configurations across 4 commercial harnesses (OpenHands ×15 models, plus one each for Claude Code, Codex CLI, Gemini CLI) is broad coverage of the main no-Skills-vs-curated-Skills comparison, but the sharper self-generated-Skills counterfactual — the one that actually tests whether curation matters — is run on only 3 of the 18.

contamination

A leakage audit blocks in-Skill answer-key artifacts (filenames, magic numbers, verbatim oracle commands) and an AI-detector-plus-human-label pass verifies instructions are human-written; there's no canary-string or training-cutoff test for whether the public task set itself becomes crawlable/memorizable once released, and the authors admit containerization provides state isolation but "not perfect determinism or immunity to training-set leakage."

what's missed

The task-acceptance rule explicitly rejects "low-signal" tasks with no with/without-Skills separation, and the curated Skills used score 10.1/12 vs. an ecosystem mean of 6.2/12 — so the +16.6 pp aggregate is a best-case bound under Skill-sensitive tasks and top-quartile Skills, not an estimate of the ecosystem-average Skill's effect. The benchmark is also terminal-based and containerized only; GUI agents, multi-agent coordination, and very long-horizon workflows are explicitly out of scope.

would raise confidence

Run the self-generated (and a length-matched irrelevant-text) control across all 18 configurations rather than 3; report a second aggregate using an ecosystem-representative (not top-quartile) sample of Skills to bound the realistic, not optimistic, effect size; and separate the Claude-model Agent-Skills-awareness confound from a harness-only advantage.

// bottom line

The paired no-Skills/curated-Skills design and deterministic verification are a real methodological upgrade over folding augmentation into a single pass-rate number, and the self-generated-Skills result is a genuinely useful negative finding. But the task-selection criterion and top-quartile Skill curation mean the headline +16.6 pp is best read as "how much a good Skill can help on a task where it's known to matter," not as a population-level estimate of Skills' average value across the ecosystem the paper itself measured at 2,014,000 Skills and a 6.2/12 mean quality score.

// takeaways

What to remember

  1. Under matched no-Skills/curated-Skills conditions on the same 87 tasks, curated Agent Skills raise the mean task-macro pass rate from 33.9% to 50.5% (+16.6 pp; 25.5% normalized gain) across 18 model–harness configurations — but the gain ranges from +4.1 pp to +25.7 pp, so Skill efficacy is a property of the specific agent stack, not a universal constant.
  2. Skills an agent authors for itself are worse than no Skills at all: on the three configurations tested, self-generated Skills land 8.1–11.5 pp below the no-Skills baseline, while curated Skills add +18.2 to +24.8 pp on the same three — the paper reads this as evidence that model-authored procedural text doesn't reproduce the curated-Skills gain, while noting the deficit also mixes discovery failures (the model often never invokes what it wrote) and creator/solver interference, so it stops short of concluding curation alone explains the gap.
  3. More and longer isn't better: 2–3 Skills (+19.0 pp) beat bundles of ≥4 Skills (+10.1 pp), and Compact/Standard-length documentation (+19.0/+21.5 pp) beats Comprehensive prose (+0.7 pp, essentially flat).
  4. The curated Skills used score 10.1/12 on the paper's own quality rubric against a 6.2/12 ecosystem mean, and the task-acceptance pipeline rejects tasks with no measurable Skill effect as "low-signal" — the authors themselves call this an optimistic scenario, so the headline number is an upper bound, not an ecosystem-average estimate.
  5. Skills can substitute for some model capacity: MiniMax M2.7 with Skills (34.9%) beats stronger no-Skills baselines like OpenHands + GLM 5.1 (32.7%) and OpenHands + MiniMax M3 (29.7%).
