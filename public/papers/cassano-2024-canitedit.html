Can It Edit? Evaluating the Ability of Large Language Models to Follow Code Editing Instructions

A 105-problem, hand-written benchmark that isolates instructional code editing — take existing code plus a natural-language instruction, produce the corrected/changed code — and evaluates it under two instruction styles at once, exposing both an open/closed model gap and a real instruction-sensitivity gap that generic code-generation benchmarks never surface.

// the gap

Editing code is not the same skill as writing it

By late 2023, code LLMs were ranked almost entirely on synthesis benchmarks: HumanEval and MBPP ask a model to write a Python function from a natural-language description (Chen et al., 2021; Austin et al., 2021), MultiPL-E extends that to 18+ languages (Cassano et al., 2023b), and EvalPlus and EvoEval harden or diversify the test suites around the same "generate-from-scratch" task. None of these ask a model to take an existing block of code and change it according to an instruction — yet that is exactly what people use LLM-powered coding assistants for. The paper opens with a concrete usage stat: of 4,188 in-the-wild LMSYS conversations that contain code, 831 (19%) are the user asking the model to edit code it (or the user) already wrote.

The closest existing benchmarks each miss a piece. HumanEvalPack's HumanEvalFix variant (Muennighoff et al., 2023) tests bug-fixing, but with a single fixed instruction per problem and no natural-language description of intent — the model must infer what changed from the broken code and its test suite alone, which the authors argue is closer to intrinsic code editing than instructional editing. SWE-Bench (Jimenez et al., 2023) evaluates real GitHub issues end-to-end, but blends planning, retrieval, and editing together, and sources its problems from GitHub — meaning any model trained on GitHub commits and issues (as StarCoder and StarCoder2 explicitly are) carries contamination risk that a hand-written benchmark avoids. CodeEditorBench (Guo et al., 2024b) is also about editing, but — in this paper's own characterization — uses fixed prompts and lacks both topic diversity and a dual-instruction design. And InstructCoder (Hu et al., 2023), which trains a model specifically for instructional editing, was evaluated with GPT-4-generated and human labels (a reproducibility concern) and was never publicly released, so this paper couldn't even benchmark it directly.

The paper's own framing is a function M(c, I) → c′: given code c and an instruction I, produce the modified code c′. What's missing from prior work isn't just a benchmark for this function — it's a benchmark that also tests how the instruction is phrased, since a terse "lazy" user request and a fully spelled-out "descriptive" one (the kind an agent revising its own code might produce) place very different demands on a model's ability to infer intent.

// how it works

CanItEdit: 105 problems, two instructions each, a hidden test suite

CANITEDIT comprises 105 hand-crafted Python code-editing problems, evenly split across three change categories drawn from Swanson's (1976) software-maintenance taxonomy: corrective (fix a bug), adaptive (meet a new requirement), and perfective (improve an existing feature) — 35 problems each. Every problem ships with two natural-language instructions meant to produce the same "after" code: a descriptive instruction (comprehensive, the kind a planning agent might generate) and a lazy instruction (terse, the kind an actual user tends to type). That doubles the dataset to 210 scoreable problems. The topics span data structures & algorithms (39 tasks), mathematics (25), language processing (21), data science (10) and miscellaneous domains (10), with 22 tasks additionally requiring a popular external library (NumPy, Pandas, PyTorch, etc.).

An eight-person team of experienced Python programmers built the dataset under a lead reviewer: each problem starts from a written description, then a "before" code segment plus hidden test suite, then the "after" code, then both instruction styles. An automated pipeline enforces that the test suite reaches 100% line coverage and that it passes on the "after" code while failing on the "before" code — so a problem can't accidentally already be solved. On average the "before" segment runs 42.5 lines and the "after" 49.8 lines (Levenshtein distance between them: 302.1 characters); descriptive instructions average 81.7 tokens against 35.6 for lazy ones.

Two metrics score every completion. pass@1 is the standard functional-correctness rate — the chance a single sampled completion passes the full hidden test suite (20 completions per problem, temperature 0.2, top-p 0.95, following the MultiPL-E sampling convention). ExcessCode is the paper's own contribution: the fraction of changed lines in a completion that the test suite's coverage report shows were never actually exercised, averaged only over the completions that passed — a lower-is-better proxy for "did the model sneak in unnecessary code."

Fine-tuning data: EditPackFT and Commits2023FT

To close the gap the evaluation exposes, the authors build two new instruction-tuning corpora from GitHub commits and fine-tune the DeepSeekCoder-Base family (1.3B/6.7B/33B) on them, computing the loss only on the "after" code segment. EditPackFT further filters the Python split of CommitPackFT (Muennighoff et al., 2023) — dropping empty diffs, no-ops, TODO/FIXME/BUG-flagged commits, and unparseable "after" code — taking 56,025 raw commits down to 22,602. Commits2023FT is built fresh from 416,792 permissively-licensed 2023 GitHub Python file changes with the same filters plus CommitPackFT's "imperative-verb commit message" filter, yielding 24,129 examples with roughly 4× the mean code-segment length (119.3 vs. 29.2 lines) and over 2× the mean commit-message length (23.1 vs. 10.1 tokens) of EditPackFT.

An ablation over four training sets (raw 25k-commit sample, EditPackFT alone, Commits2023FT alone, and the combination) finds the combined Commits2023FT+EditPackFT (74M tokens, 46,274 items after dedup) is the best training mix for DeepSeekCoder-6.7B-Base on both instruction styles, and it's what the paper uses for its final fine-tuned models, called EDITCODER.

// what they found

GPT-4 leads, but fine-tuning narrows the gap sharply at 33B and 6.7B

Table 3 reports pass@1 and ExcessCode for 19 model/scale combinations on CANITEDIT; Appendix A.5's Table 8 adds six more — StarCoderBase at 15b/7b/3b/1b and StarCoder2 at 7b/3b — for 25 combinations in total. Within Table 3's 19 rows, descriptive instructions outperform lazy ones by 8.68 points of pass@1 on average, and the same direction holds for five of Table 8's six additional rows (the exception is StarCoderBase-1b, where lazy edges out descriptive, 5.48 vs. 4.90). Larger models within a family also tend to score higher in pass@1 — most cleanly in DeepSeekCoder-Base, and, once Table 8's rows are folded in, in StarCoderBase and StarCoder2 as well, where pass@1 rises monotonically with parameter count at every step. The paper also reports ExcessCode falling with scale in these families, though that pattern is noisier: StarCoderBase's largest model, 15b, actually posts the family's highest ExcessCode under descriptive instructions (1.55), not its lowest.

Closed beats open, among un-tuned models. GPT-4 surpasses DeepSeekCoder-Instruct-33b — the strongest of the existing (non-fine-tuned) open models by descriptive pass@1 — by an average of roughly 13 points of pass@1 across the two instruction styles (13.55 on descriptive, 13.01 on lazy). Among these existing open models, DeepSeekCoder-Instruct-33b is the only one that beats a closed model at all in Table 3: its descriptive pass@1 of 49.78 edges past GPT-3.5-Turbo's 48.14 descriptive score. No other existing open model's descriptive or lazy pass@1 exceeds either closed model's corresponding score.

Fine-tuning changes that picture. EditCoder-33b — DeepSeekCoder-Base-33b fine-tuned on Commits2023FT+EditPackFT — reaches 55.90/42.33 pass@1, beating GPT-3.5-Turbo on descriptive instructions and landing close to it on lazy ones; EditCoder-6.7b (48.33/39.29) does the same at a fraction of the parameter count. Per the ablation table, the combined Commits2023FT+EditPackFT training set is the top performer among the four datasets tested (vs. EditPackFT alone at 47.14/36.05, Commits2023FT alone at 46.57/37.19, and a random 25k-commit sample at 42.57/35.14) for DeepSeekCoder-6.7B-Base on both instruction styles.

Where the gains concentrate. Breaking EditCoder-33b's results down by change type (Appendix, Table 6) shows pass@1 of 56.86 on corrective problems, 51.21 on adaptive, and only 39.29 on perfective — the same corrective > adaptive > perfective ordering holds for EditCoder-6.7b (48.64 / 42.71 / 40.07). The paper frames this directly: EditCoder "excels in corrective changes but is less effective in perfective changes," which tracks with its training data being drawn from commits and bug-fix-style edits rather than feature-improvement instructions.

On the separately-run HumanEvalPack comparison (Appendix A.4, Python subset of HumanEvalFix/Synthesize), the paper reports a Pearson correlation of 0.661 between CanItEdit pass@1 and HumanEvalSynthesize pass@1 across models evaluated on both — "a moderate positive correlation," in the authors' words, consistent with code-editing and code-generation ability being related but distinct skills.

// does it hold up?

The eval read

The descriptive/lazy split is this paper's most useful methodological idea, and it delivers exactly the kind of finding a single-instruction-style benchmark would hide: all 19 of Table 3's evaluated model configurations do worse on the terser instruction, by 8.68 points of pass@1 on average, and the gap is large enough (11+ points for GPT-4 itself) that a benchmark reporting only one instruction style would materially overstate how well any of these models handle real, under-specified user requests. The pattern isn't quite universal once Appendix A.5's six additional StarCoder-family rows (Table 8) are counted in — StarCoderBase-1b's lazy pass@1, 5.48, edges out its descriptive 4.90 — but the direction holds for 24 of the paper's 25 reported model/scale combinations. That said, the "lazy" instructions are still annotator-written approximations of terse phrasing, not instructions sampled from the 831 real LMSYS code-editing conversations the paper cites as motivation. The paper does partially address that gap itself, though: Appendix E reports that the authors inspected a subset of those 831 real conversations and found "almost all of the requests are of the 'lazy' kind that we include in CANITEDIT," with several verbatim examples (e.g. "change this code to python"). That's a reasonable qualitative spot check, but it isn't a systematic sample-and-compare, so it doesn't establish that the benchmark's specific lazy phrasings are representative of the real distribution in aggregate — only that the general style is plausible.

The training-data story deserves a second look too. EditPackFT is filtered from CommitPackFT — the same corpus OctoCoder (a baseline in Table 3) was instruction-tuned on — so EditCoder's fine-tuning data and one of its open-model comparators share a lineage; that's disclosed, not hidden, but it means the "open vs. closed" and "fine-tuned vs. not" comparisons aren't fully independent of each other. More concretely, the paper's own per-change-type breakdown (Table 6) shows EditCoder's gains are lopsided: strong on corrective edits (56.86 pass@1 at 33B), weaker on perfective ones (39.29) — consistent with commit messages being a better proxy for "fix this bug" than for "improve this feature," and a reason to be cautious about how far the headline pass@1 gains generalize to editing tasks that don't look like bug-fix commits.

ExcessCode is a clever idea but a partial one by construction: it's averaged only over completions that already passed the test suite, so a model that fails outright — even by writing wildly bloated, wrong code — pays no ExcessCode penalty at all. It measures "is a model's correct code also concise," not "does a model avoid writing sprawling code in general," and the two aren't the same question.

Finally, one aggregate statistic in the paper is hard to reconcile with its own Table 3: the text reports EditCoder-33b showing "an overall 10.7% increase in pass@1 ... compared to its base model, DeepSeekCoder-Base-33b," but combining Table 3's own descriptive/lazy pass@1 cells for those two rows gives roughly a 19% relative increase, not 10.7% (the 10.7% figure reconciles more closely against DeepSeekCoder-Instruct-33b instead). That's a minor, isolated reproducibility rough edge in one aggregate percentage — the underlying per-cell pass@1 numbers in Table 3 are internally consistent — but it isn't the paper's only internal wrinkle of this kind: its "model size correlates positively with pass@1" claim, which holds cleanly for DeepSeekCoder-Base, StarCoderBase, and StarCoder2 (checked above), has a counterexample inside Table 3 itself — CodeLlama-Instruct-7b (32.83/23.49) outscores the larger CodeLlama-Instruct-13b (26.90/16.89) on both instruction types. Neither wrinkle is disqualifying by itself, but together they're a reminder to check a paper's aggregate and qualitative claims against its own tables rather than taking either at face value.

baselines

Reasonably broad and contemporaneous for December 2023 — GPT-4, GPT-3.5-Turbo, CodeLlama-Instruct up to 70B, DeepSeekCoder, Mixtral-Instruct, StarCoder/StarCoder2/OctoCoder — each prompted with its own recommended template. It does not benchmark deployed coding assistants (Cursor, Copilot Chat) directly, only cites them as motivation, and InstructCoder — the one prior model built specifically for this task — couldn't be included because it was never released.

contamination

The benchmark is hand-written specifically to sidestep the GitHub-scrape contamination risk the authors call out in StarCoder/StarCoder2 (both trained on GitHub commits/issues) and implicitly in SWE-Bench. It doesn't address the newer, forward-looking risk of its own kind: CanItEdit has been public on GitHub since December 2023, so any model trained on recent web/code crawls risks having memorized these exact 105 problems and their test suites.

what's missed

ExcessCode's survivorship design (scored only on passing completions); Python-only scope (an explicit, stated limitation); one-shot editing only, no iterative/multi-turn revision; pass@1 is the headline metric, with pass@10/pass@100 relegated to an appendix at higher sampling temperature.

would raise confidence

An unconditional excess-code measure that also penalizes failing completions; lazy instructions drawn from real LMSYS-style user requests rather than annotator approximations; a change-type-stratified headline table (not just an appendix breakdown) given how unevenly EditCoder's gains are distributed across corrective/adaptive/perfective; and languages beyond Python, which the authors themselves flag as future work.

// bottom line

A well-constructed, appropriately small benchmark that asks a genuinely different question from HumanEval-style synthesis tests, and its descriptive/lazy design is a real contribution to measuring instruction sensitivity rather than just accuracy. The fine-tuning result is real and the ablation supporting it is clean, but its benefits are concentrated on bug-fix-shaped edits, and the ExcessCode metric's exclusion of failing completions means it can't be read as a general anti-bloat measure.

// takeaways

What to remember

  1. CanItEdit isolates instructional code editing — code plus an instruction, not code from scratch — as its own 105-problem, hand-written benchmark, scored under both a "descriptive" and a "lazy" instruction per problem (210 scoreable items total).
  2. GPT-4 leads at 63.33/51.95 pass@1 (descriptive/lazy); descriptive instructions beat lazy ones by 8.68 points of pass@1 on average across Table 3's 19 model/scale combinations, and the same direction holds for all but one of the paper's six other reported combinations (StarCoderBase-1b is the exception) — instruction phrasing alone is worth roughly as much as several points of model scale.
  3. Fine-tuning DeepSeekCoder-Base on two new commit-derived datasets (EditPackFT + Commits2023FT) produces EditCoder, which beats GPT-3.5-Turbo on descriptive instructions at both 33B and 6.7B — but its gains concentrate on corrective (bug-fix) edits over perfective ones, a pattern visible directly in the paper's own per-change-type breakdown.
