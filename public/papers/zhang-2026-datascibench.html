DataSciBench: An LLM Agent Benchmark for Data Science

222 curated data-science prompts, 519 hand-verified test cases, and a Task–Function–Code framework built to score outputs a plain pass/fail can't reach — GPT-4o tops every one of the nine columns of the main results table, but even it clears a full-success run only 66.31% of the time, and its composite score caps out at 64.51%.

// the gap

What problem is this solving?

Data science work rarely reduces to a single number you can check against a reference string. A typical prompt — Figure 1's example asks a model to implement a function that computes the marketing spend required to hit a target unit-sales number — bundles together data cleaning, model fitting, a calculation, and a file-format requirement, and whether the model "got it right" depends on a mix of exact-match checks, threshold comparisons, and even a judgment call about whether a saved chart looks correct. Prior data-science benchmarks side-step that difficulty: DS-1000 and BigCodeBench check generated code against test cases; InfiAgent-DABench grades against a single accuracy number, while MLAgentBench pairs accuracy with a success-rate metric and a human-evaluation component; Text2Analysis mixes an executable-code ratio with regression scores. The paper's Table 1 lines these up explicitly, and its own framing is that such prior benchmarks typically pair a narrower prompt source with more straightforward evaluation metrics (e.g., plain accuracy) than DataSciBench's multi-deliverable, partial-credit approach.

DataSciBench's authors argue this understates the real evaluation problem: a genuinely hard data-science prompt produces multiple deliverables (a cleaned file, a fitted model, a saved plot, a written interpretation), each of which needs its own notion of correctness, and the ground truth for several of those deliverables isn't obvious even to a human without care (what MSE threshold counts as "close enough" to the reference model? what silhouette score counts as valid clustering?). Their target gap is specifically the space between "we can check test cases" and "we can score a genuinely open-ended, multi-part, real-world data-science task" — and they build both the prompts and the grading machinery to sit in that gap.

// how it works

The method

DataSciBench collects 222 prompts spanning six task types — data cleaning & preprocessing, data exploration & statistics, data visualization, predictive modeling, data mining & pattern recognition, and interpretability & report generation — sourced four ways: 167 prompts extracted and rewritten from BigCodeBench, natural prompts pulled from the CodeGeeX online code-generation platform, hand-written prompts by the authors, and prompts synthesized by an LLM from few-shot human-written examples. Every prompt goes through question filtering (keyword selection, removal of questions that require rewriting existing code, finding errors, or explaining basic concepts) and a three-stage expert review that verifies correctness, standardizes the input/prompt/expected-output format, and collects or generates the actual input datasets.

The grading machinery is the paper's core contribution: a Task–Function–Code (TFC) framework. For each prompt, GPT-4o-mini first selects which of the six task types apply and proposes an evaluation function and code for each, producing a set of (Task, Function, Code) tuples; a "data interpreter" agent then organizes these into a hierarchical directed acyclic graph so that dependent subtasks are evaluated in order. The candidate functions are then aggregated to a fixed vocabulary: the authors keep the top-K (K=5) most common evaluation functions per task type, landing on 25 aggregate functions total across the six task types (e.g., for data cleaning: Data Cleaning Completeness, DataFrame Shape Validation, Data Completeness, Normalization Range Check, Data Quality Score). Each function's output is normalized by a programmatic rule into either a boolean or a decimal in [0,1] — e.g., a clustering task's silhouette score is boolean-thresholded at 0.5 — so that every one of the resulting 519 test cases reduces to a comparable pass/fail or graded signal against ground truth.

Ground truth itself is semi-automated. For prompts sourced from BigCodeBench, the paper reuses BCB's own test cases and has humans re-check any answer that passes them all. For the rest, the authors sample an LLM's outputs multiple times, apply a self-consistency strategy (Wang et al., 2022) to converge on a candidate answer, and then have six of the paper's authors verify the assigned task type, evaluation function, programmatic code, and final output for every case; when uncertainty remains, three authors cross-validate. The result is graded on two coarse-grained axes and six fine-grained ones. Completion Rate (CR) gives each TFC step a score of 0 (missing/fail), 1 (success-non-compliant), or 2 (success-compliant), then normalizes by the maximum possible score across all steps in a run:

CR = Σt=1..T stT × smax // s_t = completion score of step t, s_max = 2, T = number of TFC steps in the run

Success Rate (SR), modeled on Codex's pass@k-style estimator, is stricter: a prompt only counts as a success in a given run if every TFC tuple in it passes, and SR is the unbiased estimate of that all-or-nothing success rate across 10 sampled runs. On top of these two coarse metrics sit six fine-grained ones: a VLM-as-a-judge score (GPT-4o-mini scoring generated charts against defined visual criteria) plus five aggregate function scores — F1 (Data Quality Score, cleaning), F2 (Plot Validity, visualization), F3 (Data Accuracy, statistics/MSE-threshold), F4 (Visualization Completeness, file existence), and F5 (Model Accuracy, predictive modeling). Everything is then rolled into a single weighted composite:

Score = 0.05×Σi=1..5Fi + 0.05×VLM + 0.05×SR + 0.65×CR // CR dominates the composite at 65% of the weight; the five F-scores and VLM together carry 30%, SR only 5%

That weighting matters for reading the results: DataSciBench's headline "Score" is not a pass rate or an accuracy percentage — it's a partial-credit composite dominated by step-level completion, with the strict all-tuples-pass Success Rate contributing only a twentieth of the total. The 23 evaluated models split into three groups: 6 API-based (o1-mini, GPT-4o, GPT-4o-mini, GPT-4-Turbo, Claude-3.5-Sonnet, GLM-4-Flash), 8 open-source general models (the Llama-3/3.1-8B, Qwen2/2.5-7B and Qwen2-1.5B, Gemma-2-9B, GLM-4-9B, and Yi-1.5-9B families), and 9 open-source code models (DeepSeek-Coder at 1.3B/6.7B/33B, CodeLlama at 7B/13B/34B, Qwen2.5-Coder at 1.5B/7B, and StarCoder2-15B).

// what they found

The results

Across all 23 models and all nine metrics in the main results table, GPT-4o (2024-05-13) posts the single highest value in every column — SR (66.31%), CR (68.44%), the VLM judge score (3.91), F1–F5, and the composite Score (64.51%). That 64.51% Score is 9.86 points above the next-best API model, GPT-4-Turbo, at 54.65%. Among the 17 open-source models, DeepSeek-Coder-33B-Instruct is the standout, scoring 56.76% — not just the best open-source result, but higher than five of the six API-based models (it trails only GPT-4o at 64.51%, and beats GPT-4-Turbo's 54.65%, GPT-4o-mini's 54.18%, Claude-3.5-Sonnet's 52.29%, o1-mini's 38.78%, and GLM-4-Flash's 30.74%). Qwen2.5-Coder-7B-Instruct (47.67%) and Qwen2.5-7B-Instruct (45.99%) trail it but are still competitive with several proprietary models.

Grouped by access type, the API-based average Score is 49.15% versus 23.01% for open-source models (both figures printed directly on the paper's summary chart) — roughly a 2x gap. But the distribution among open-source models is wide: several small or mismatched models collapse entirely. CodeLlama-34B-Instruct scores just 1.33%, actually below its own smaller siblings (CodeLlama-13B at 12.64%, CodeLlama-7B at 3.31%) — an inversion the authors flag explicitly as anomalous rather than explain away, attributing it to the larger checkpoint's weaker adherence to the requested output format rather than any lack of capability.

Splitting by task difficulty (167 "easy" prompts drawn from BigCodeBench with CSV-formatted data, 30 "medium" human hand-written prompts, and 25 "hard" data-science-related deep-learning-task prompts) shows completion rate collapsing sharply as difficulty rises: the average CR across all models is 37.76% on easy prompts but only 6.56% on medium and 3.83% on hard prompts. Reading the (unlabeled) per-model bars in Figure 5 only approximately, even the strongest models — GPT-4o, GPT-4o-mini, GPT-4-Turbo, and DeepSeek-Coder-33B-Instruct — see their hard-prompt CR fall to roughly a fifth of their easy-prompt CR or less; what distinguishes them from weaker models is a relatively higher and more consistent CR across all three difficulty bands, not a hard-task CR that approaches their easy-task numbers.

The paper also checks whether DataSciBench measures something LiveCodeBench and BigCodeBench don't already capture. Pearson/Spearman correlations between DataSciBench rankings and each benchmark are both strongly positive — r=0.853, ρ=0.673 against LiveCodeBench, and r=0.823, ρ=0.808 against BigCodeBench — but the authors highlight specific rank disagreements (Meta-Llama-3-8B-Instruct and CodeLlama-34B-Instruct behave differently on DataSciBench than on general coding benchmarks) as evidence the benchmark captures something data-science-specific beyond general code correctness.

// does it hold up?

The eval read

DataSciBench's central contribution is methodological rather than empirical: a grading framework capable of scoring multi-deliverable, partially-subjective tasks. That's a real gap it fills, and the semi-automated GT pipeline — self-consistency sampling followed by author verification, with cross-validation on disputed cases — is more rigorous than a single LLM-as-judge pass. But several parts of the setup deserve scrutiny before treating the headline numbers as a clean measure of "data science ability."

The most consequential is the composite Score itself. It is 65% Completion Rate, a partial-credit metric whose per-step rubric has four tiers — missing (0), fail (0), success-non-compliant (1 of 2), success-compliant (2 of 2) — so a step only banks credit if the model actually succeeds at it; a step that is merely missing or that fails outright earns nothing. Even so, a step that succeeds but doesn't meet the required output format still banks half credit, so a run of many succeed-but-noncompliant steps can out-score a run of fewer, fully-correct ones, since the strict all-tuples-pass Success Rate contributes only 5% of the total weight — the paper's own SR/CR pairs illustrate the gap (GPT-4o: SR 66.31 vs. CR 68.44, a modest spread, but weaker models often show a much larger CR-over-SR margin, e.g. Gemma-2-9B-it at SR 7.07 vs. CR 11.00 vs. a Score of 12.66 that is inflated further by F1 26.16). The paper never actually defines what "compliant" means, either. The rubric line introduces the term cold, and the later uses gesture at output format without pinning it down: §5.4 attributes o1-mini's failures partly to "non-compliance with instructions," and an appendix failure case is annotated "the answer does not comply with required output instructions." So the boundary between a "success-compliant" step and a "success-non-compliant" one is unauditable from outside the paper. Readers who take "Score" as a pass rate will also overstate how often these models actually deliver usable, fully-correct data-science outputs; the paper never claims otherwise, but the composite's name invites that misreading.

The second is prompt provenance and contamination risk. 167 of the 222 prompts (75%) are extracted and rewritten from BigCodeBench, a benchmark released in mid-2024 that itself draws heavily on public StackOverflow-derived code; the remaining prompts come from a public online code-generation platform (CodeGeeX) or from human/LLM authoring. Because DataSciBench "refines" BCB prompts into its own format rather than inventing new problems, the underlying task content overlaps substantially with material that could plausibly appear in the pretraining corpora of models released after BCB and CodeGeeX went public — a risk the paper does not discuss or attempt to bound (no contamination check, deduplication analysis, or held-out-recency argument appears anywhere in the main text or appendix). The paper's own appendix supplies suggestive evidence on exactly this split: Tables 5 and 6 report every model's results separately for the 167 BigCodeBench-sourced prompts versus the 55 prompts the authors collected themselves, and the gap is large. GPT-4o scores 81.81 on the BCB-sourced subset (Table 6) versus 24.32 on the 55 curated prompts (Table 5) — and on that curated subset the top three API models (GPT-4o 24.32, GPT-4-Turbo 24.24, GPT-4o-mini 24.13) compress into a 0.19-point spread, where the same three models spread widely on the BCB subset. That pattern is consistent with either genuine difficulty differences between the two prompt pools or with BCB-sourced content being easier because it's familiar to these models from pretraining — the paper doesn't run the analysis needed to distinguish the two, so the split is suggestive rather than dispositive. This doesn't invalidate the relative ranking of models, but it is a gap the paper leaves open rather than one it addresses and clears.

Third, the VLM-as-a-judge component for visualization tasks is explicitly flagged by the authors themselves as underpowered ("our initial metrics and evaluation methods (e.g., VLM-as-a-judge) may lack precision... [f]urther refinement of metrics is required to evaluate data visualization tasks effectively" — the paper's own Limitations section). That's an honest disclosure, but it means one of the three visualization-facing axes — and the only one that judges the rendered image holistically rather than checking a narrow proxy (F2 is a shape-consistency check against the ground-truth chart, F4 is just whether the plot file exists) — is acknowledged by the authors to be the shakiest measurement in the benchmark.

Fourth, ground-truth generation for non-BCB prompts leans on the paper's own six authors as verifiers rather than independent external annotators or a reported inter-annotator agreement statistic; the paper doesn't quantify how often the self-consistency-plus-author-review process disagreed internally or how often cross-validation among three authors overturned an initial judgment, so there's no way to audit the reliability of the 519 test cases from outside the paper.

baselines

23 models spanning 6 API-based and 17 open-source (8 general, 9 code) checkpoints is a wide and reasonably current sweep for a Feb-2025 preprint, though the only reasoning-tuned model tested is o1-mini — the arXiv record shows no revision beyond v1, so it's unclear whether a newer reasoning model (e.g. DeepSeek-R1, released the month before) was added for the Findings of ACL 2026 version.

contamination

75% of prompts are rewritten from BigCodeBench, a public benchmark already in circulation; the paper never discusses or measures the resulting leakage risk into models' pretraining data. Its own appendix (Tables 5–6) hints at the risk without confirming it: GPT-4o scores 81.81 on the BCB-sourced subset vs. 24.32 on the 55 curated prompts, where the top three API models compress to a 0.19-point spread.

what's missed

The headline Score is a 65%-CR-weighted composite, not a solve rate; its per-step rubric awards half credit for a step that succeeds but doesn't meet the output-format requirement, so runs with many succeed-but-noncompliant steps can out-score runs with fewer fully-correct ones — and the paper never defines what "compliant" means anywhere in its 40 pages.

would raise confidence

A contamination/deduplication check against BigCodeBench and CodeGeeX; an inter-annotator agreement number for the human-verified ground truth; and a validated (not self-described-as-imprecise) visualization-quality metric.

// bottom line

DataSciBench's TFC framework is a genuinely useful answer to "how do you grade a multi-part, partially-subjective data-science task programmatically" — and its finding that reasoning-strong models like o1-mini can still fail on fine-grained instruction-following and tool-use in this domain is a real, well-supported result. But the benchmark's own composite metric is easy to over-read as an accuracy figure when it is mostly step-level completion credit, and the heavy reuse of BigCodeBench prompts leaves contamination as an open question the paper doesn't address.

// takeaways

What to remember

  1. DataSciBench's contribution is the Task–Function–Code grading framework as much as the 222-prompt, 519-test-case dataset itself: a semi-automated pipeline that turns each open-ended data-science prompt into a set of boolean/threshold-checkable subtask evaluations, aggregated to 25 reusable functions across six task types.
  2. GPT-4o leads every one of the nine columns of the main results table, with a composite Score of 64.51% versus GPT-4-Turbo's 54.65%; among open-source models, DeepSeek-Coder-33B-Instruct's 56.76% beats five of the six API-based models outright (everything except GPT-4o), and difficulty scaling is brutal across the board — the 23-model average completion rate falls from 37.76% on easy prompts to 3.83% on hard ones, and every individual model's hard-prompt CR sits below its own easy-prompt CR.
  3. Treat the headline "Score" as a 65%-completion-rate-weighted composite, not a pass/solve rate, and note that 75% of the prompt set is rewritten from BigCodeBench with no contamination analysis offered — both are important caveats for anyone citing DataSciBench numbers as a clean measure of data-science capability.
