API-BLEND: A Comprehensive Corpora for Training and Benchmarking API LLMs

Ten datasets, one exact-match protocol: five human-annotated dialogue/semantic-parsing corpora re-purposed into API-call sequences for training, held against five out-of-distribution tool-use suites — including a newly built SeqToolQA — where most models fine-tuned on the combined mix beat the tool-specific checkpoints they were compared against.

// the gap

What problem is this solving?

By early 2024, two strategies dominated how researchers got LLMs enough train/test data to call APIs and tools. The first — synthetic data generation, as in ToolLLM's 16,000+ RapidAPI-derived calls or Gorilla's LLM-generated API examples — is cheap to scale but inherits the sampling model's biases and lacks diversity, which the authors argue is exactly what causes models to overfit to in-distribution APIs and fail to generalize to ones they haven't seen. The second — curating task-adjacent datasets by hand — is higher quality but has historically focused on just two of the three sub-skills a tool-calling assistant needs: API detection (which API to call) and slot filling (extracting the right parameters). Sequencing — chaining several API calls together to satisfy one higher-level request, e.g. checking a balance and then transferring money — has stayed rare in existing corpora, even though it's what realistic multi-step assistant tasks actually require.

Meanwhile, a separate pool of human-annotated datasets in adjacent domains — task-oriented dialogue (Schema-Guided Dialogue, MultiWOZ), semantic parsing (TopV2), and voice-assistant intent/slot corpora (ATIS, SNIPS) — already encode exactly the intent + parameter + multi-turn structure a tool-calling model needs, but the paper argues these have gone largely unnoticed for this purpose because of the recent emphasis on synthetic generation. API-BLEND's premise is that transforming five of these existing, high-quality, diverse-domain datasets into API-call form — while holding out five separate out-of-distribution (OOD) tool benchmarks purely for testing — gets both the training diversity synthetic data lacks and the sequencing coverage prior curated corpora skipped.

// how it works

The method

API-BLEND treats every example as: a single natural-language utterance in, a sequence of API calls (each with parameter names and values) out. It assembles 10 datasets via three distinct curation approaches: two — LLM-assisted and grammar-based generation — build six new datasets on top of existing corpora (five used in-distribution, for training and in-domain testing, plus a sixth, SeqToolQA, held out purely as an OOD test set); the third approach repackages the remaining four existing tool-benchmarks off-the-shelf, likewise purely as out-of-distribution test sets, never trained on.

LLM-assisted generation — SeqSGD, SeqMultiWOZ

Schema-Guided Dialogue (SGD) and MultiWOZ are multi-domain, human-annotated task-oriented dialogue datasets spanning banks, events, media, calendars, travel, and weather. For each conversation, the authors prompt FLAN-T5-XXL to turn each individual API call into a natural-language request, then concatenate those per-call requests into one summarized utterance covering the whole conversation — deliberately not summarizing the raw dialogue itself, since it also contains noisy API execution results. Examples where the generated utterance doesn't faithfully reflect the ground-truth APIs are filtered out. The result: SeqSGD (6,782 train / 1,092 dev / 1,567 test, avg. 2.44 APIs per example, avg. 3.5 parameters per API) and SeqMultiWOZ (6,816 train / 485 dev / 983 test, avg. 2.36 APIs, avg. 3.67 parameters).

Grammar-based generation — SeqATIS, SeqSNIPS, SeqTopV2, SeqToolQA

ATIS and SNIPS are classic intent/slot-labeled voice-assistant corpora; MixATIS and MixSNIPS extend them into multi-intent utterances by joining single-intent sentences with conjunctions. Because the multi-intent versions only mark which text spans are which slots — not which parameters belong to which API — the authors split each multi-intent utterance back into its original single-intent parts, parse the IOB (Inside/Outside/Beginning) slot tags deterministically into API-parameter pairs, then re-merge the utterance with its ordered API sequence. No generative model is involved in this pipeline. This produces SeqATIS (11,670 / 694 / 774, avg. 2.13 APIs, avg. 4.85 parameters) and SeqSNIPS (39,750 / 2,198 / 2,199, avg. 1.96 APIs, avg. 5.06 parameters). A third dataset, SeqTopV2, applies the same deterministic conversion to TopV2's own intent (IN:) and slot (SL:) notation across eight domains (alarm, event, messaging, music, navigation, reminder, timer, weather) — e.g. "Remind me to email Joy about the client tonight" becomes a SEND_MESSAGE call that is a prerequisite for a CREATE_REMINDER call — after dropping "UNSUPPORTED"-labeled and duplicate/ambiguous examples, yielding 94,458 / 13,477 / 6,095 examples.

Off-the-shelf usage — four off-the-shelf suites, plus the new SeqToolQA

To measure generalization, five datasets are used strictly as held-out OOD test sets, never for training. Four are existing tool-benchmarks used off-the-shelf: a two-domain (Home-Search, Booking) subset of ToolBench; the ToolLLM G1/G2/G3 subsets (single-tool, intra-category multi-tool, intra-collection multi-tool; API-only, no parameters); API-Bank's test dialogues, split into per-turn examples (L1/L2); and ToolAlpaca's test instances. The fifth, SeqToolQA, is not an off-the-shelf import — it's one of the paper's own grammar-based-generation datasets (see above), just held out for OOD testing instead of training: ToolQA supplies template questions with final answers but not the intermediate API calls needed to reach them, so the authors used ToolQA's own reference implementation of how each template question is answered to derive the corresponding API sequence, abstracting 17 APIs across 6 domains into 358 test examples — the one OOD dataset in the suite that didn't already exist as tool-calling data anywhere.

// data quality check

Because six of the ten datasets are the authors' own transformations, they ran a human annotation pass over 50 sampled examples per in-distribution dataset (≥2 annotators each), scoring Intent correctness, Sequence(Intent) ordering, and Slot correctness. Scores are uniformly high — 0.85–1.00 average quality and 0.90–1.00 annotator agreement across all five datasets and all three dimensions — with Slot the lowest-scoring dimension in every dataset, consistent with parameter extraction being the harder sub-task throughout the paper.

Evaluation setup

Eight open-source models are tested across three in-distribution regimes: no fine-tuning (Falcon-180B, LLaMA-2-70B, 3-shot prompted, plus the pre-existing ToolLLaMA-2-7B checkpoint), fine-tuned on one target dataset (FLAN-T5-XXL, StarCoder-15B, Falcon-40B, MPT-30B via QLoRA), and fine-tuned on the combined training data (the same four plus LLaMA-2-7B). A ninth model, Lynx-7B — an existing checkpoint fine-tuned on API-Bank's own data — is added only for the OOD comparison, alongside ToolLLaMA-2-7B. Every prediction is scored on three metrics: API-F1 (exact-match F1 over predicted vs. gold API names), Parameter-F1 (exact-match F1 over predicted vs. gold slot names+values), and LCS-F1 (F1 built from longest-common-subsequence precision/recall between predicted and gold API sequences, capturing call order rather than just the right set of calls).

// what they found

The results

In-distribution: API detection is easy, parameters are hard

Without any fine-tuning, all three tested models struggle: weighted-average API-F1 | Parameter-F1 | LCS-F1 is 0.19 | 0.04 | 0.20 for Falcon-180B, 0.11 | 0.02 | 0.12 for LLaMA-2-70B, and 0.27 | 0.05 | 0.28 for ToolLLaMA-2-7B — every model gets some APIs right but its Parameter-F1 barely clears single digits. Fine-tuning changes this sharply: every model fine-tuned on its own target dataset clears 90%+ API-F1 on every one of the five in-distribution datasets, and every model fine-tuned model reaches 1.00 API-F1 on SeqMultiWOZ specifically (both when fine-tuned per-dataset and on the combined mix) — the paper attributes this to SeqMultiWOZ's small API inventory (12 APIs). Parameter-F1 stays the harder metric throughout: e.g. StarCoder-15B fine-tuned on SeqATIS alone reaches 0.99 API-F1 but only 0.84 Parameter-F1 on the same test set.

Training on the combined dataset instead of one dataset at a time raises Parameter-F1 for every one of the four models tested in both settings — FLAN-T5-XXL (0.83→0.85), StarCoder-15B (0.80→0.82), Falcon-40B (0.67→0.72), MPT-30B (0.84→0.85) — while API-F1 and LCS-F1 hold flat or edge up slightly (never down). Out-of-distribution: does the diversity pay off?

The paper's central generalization claim: take the five models fine-tuned on the combined API-BLEND training mix and test them, 3-shot, on five OOD suites they never trained on — alongside ToolLLaMA-2-7B and Lynx-7B, two existing tool-tuned checkpoints (from ToolLLM and API-Bank respectively) that were trained on data drawn from two of those same OOD families.

Four of the five API-BLEND-tuned models — Falcon-40B, MPT-30B, LLaMA-2-7B, StarCoder-15B — beat both ToolLLaMA-2-7B and Lynx-7B on all three weighted-average metrics. The fifth, FLAN-T5-XXL, still beats both on API-F1 and LCS-F1, but its Parameter-F1 (0.09) only ties ToolLLaMA-2-7B's (0.09) and trails Lynx-7B's (0.14) — the one weighted-average cell where an API-BLEND-tuned model doesn't come out ahead. Breaking it down by suite: on the API-only ToolLLM subsets, among the five API-BLEND-tuned models, Falcon-40B and StarCoder-15B take the top two API-F1 spots on G1 (Falcon-40B 0.48, StarCoder-15B 0.32) and G2 (StarCoder-15B 0.53 ahead, Falcon-40B 0.48 second), but G3 is a near three-way tie among MPT-30B (0.51), Falcon-40B (0.50), and StarCoder-15B (0.49), with MPT-30B technically on top. That framing undersells one baseline across the full seven-model field, though: Lynx-7B, API-Bank's own checkpoint, is genuinely competitive on ToolLLM — it lands second on G1 (0.43, ahead of StarCoder-15B's 0.32) and ties Falcon-40B for second on G3 (0.50). FLAN-T5-XXL and MPT-30B lead on API-Bank and ToolAlpaca; Falcon-40B alone tops both ToolBench subsets (Home-Search 0.95, Booking 0.89 API-F1) across all seven models, tool-tuned checkpoints included. On the newly-built SeqToolQA, every model's Parameter-F1 caps at 0.02 or below — the paper attributes this to gold parameter values that are codes, SQL snippets, and math functions the models never saw during training and can't reliably produce from a handful of ICL examples. FLAN-T5-XXL has no ToolLLM scores at all — the paper states this is because it hit its max sequence length limit, not a result the model produced and failed.

The paper's qualitative error analysis (§5.7) documents two systematic causes of exact-match misses that aren't outright capability failures: unnormalized slot values (e.g. gold "March 3rd, this Sunday" vs. predicted "March 3rd, the 3rd"; gold Date(3, 9, 2023) vs. predicted Date(year=2023, month=3, day=9)), and semantically-similar-but-differently-named parameters across the constituent datasets (e.g. gold destination_airport vs. predicted destination). The paper reports these as observed patterns without a normalization pass to quantify their share of the Parameter-F1 gap.

// does it hold up?

The eval read

API-BLEND's core contribution is genuinely useful and unusually transparent about its own limits — a documented human data-quality pass, an explicit sequencing gap it targets, and a qualitative error analysis that names its own metric's blind spots. But several parts of the headline "generalizes better" claim deserve a closer look than the tables alone give.

The metric that decides the paper's central claim is also the one its own qualitative section shows undercounts correct answers. Every comparison in Tables 3 and 4 runs on exact-match API-F1/Parameter-F1, yet §5.7 documents unnormalized-slot-value mismatches (date phrasing, city-vs-city+state) and synonym parameter names (destination vs. destination_airport) as recurring false negatives — with no normalization layer or human-adjudicated re-scoring pass to bound how much of the reported gap between models, or between API-BLEND and the two baselines, is measurement noise rather than a real capability difference.

ToolLLaMA-2-7B and Lynx-7B are graded on a metric they were never built for. The paper is admirably candid about this: "In their papers, they used different metrics, e.g., pass rate... and win rate... Even though ToolLLaMA-2-7B and Lynx-7B are from ToolLLM and API-Bank respectively, still they are performing poorly [here]." That's an honest disclosure, but it also means the headline "our models beat them" result compares five models freshly fine-tuned to satisfy exact-match slot/API scoring against two checkpoints optimized for a soft, LLM-judged pass/win-rate criterion. The comparison conflates two different questions — "which corpus generalizes better" and "which evaluation protocol were you optimized for" — and the paper doesn't run ToolLLaMA-2-7B or Lynx-7B under their own native metrics on the same test items to separate the two effects.

No frontier closed-model reference point. Every baseline is open-source and ≤180B parameters (Falcon-180B is the largest, and it isn't fine-tuned). There's no GPT-3.5/GPT-4 in-context-learning number anywhere, so a reader can't tell whether this diverse fine-tuning recipe would still show gains against the kind of strong ICL baseline that tool-use systems compete with in practice.

The near-ceiling in-distribution numbers and the true OOD numbers are easy to conflate at a glance. Table 3's 90–100% API-F1 scores are all on in-distribution test splits drawn from the same five datasets the models were fine-tuned on; they mostly measure fit to a known distribution, not generalization. The paper does keep this distinction clean by running a separate OOD table, but the two tables sit one page apart with similarly-formatted cells, and Table 3's ceiling effect on SeqMultiWOZ — every single fine-tuned model in both the own-dataset and combined-data settings reaches exactly 1.00 API-F1 there — could easily be over-credited by a reader who doesn't track which table is which.

Contamination is unaddressed. Every constituent dataset (ATIS 1990, SNIPS 2018, SGD 2020, MultiWOZ, TopV2 2020, and the 2023-era ToolLLM/API-Bank/ToolBench/ToolAlpaca OOD sets) has circulated publicly for one to thirty-plus years before this paper's base models (LLaMA-2, Falcon, MPT, StarCoder, FLAN-T5) were pretrained. The paper never discusses whether any of this material — in-distribution or OOD — could already be inside those base models' pretraining corpora, which would inflate both the "no fine-tuning" and the fine-tuned numbers to an unknown degree.

baselines

Seven open-source models spanning 7B–180B (Falcon-180B/40B, LLaMA-2-70B/7B, FLAN-T5-XXL, StarCoder-15B, MPT-30B) plus two externally pre-trained tool checkpoints (ToolLLaMA-2-7B, Lynx-7B) — nine in all, per §5.1; no closed frontier model (GPT-3.5/GPT-4) is evaluated anywhere for scale calibration.

contamination

Not discussed. The constituent datasets range from 1990 (ATIS) to 2023 (the OOD tool benchmarks) and have been public well before the base models used here were pretrained.

what's missed

No normalization pass to quantify how much of the Parameter-F1 gap (in either direction) is unnormalized-value/synonym-name noise versus real model error; ToolLLaMA-2-7B and Lynx-7B are never re-scored under their own native pass-rate/win-rate metrics on the same items, so "metric mismatch" and "data-diversity advantage" are never disentangled.

would raise confidence

A slot-value normalization or human-adjudicated re-scoring pass; ToolLLaMA-2-7B/Lynx-7B evaluated under both their native metric and API-BLEND's exact-match metric side by side; at least one frontier ICL baseline; and a genuinely novel-domain OOD suite beyond other tool-calling benchmarks assembled the same way.

// bottom line

A solid, unusually self-aware corpus-and-benchmark aggregation — real sequencing coverage prior work skipped, a documented data-quality pass, and a genuinely new OOD dataset (SeqToolQA) in the held-out suite. Its headline OOD win is real by its own exact-match metric, but that metric is also the one the paper's own qualitative section shows misses semantically-correct answers, and the comparison against ToolLLaMA-2-7B/Lynx-7B runs those two models under a metric neither was designed to satisfy.

// takeaways

What to remember

  1. Ten datasets, two purposes. Five existing human-annotated datasets (SGD, MultiWOZ via LLM-assisted generation; ATIS, SNIPS, TopV2 via deterministic grammar-based parsing) become the training/in-domain-test corpus, targeting the sequencing sub-task prior tool-use corpora rarely covered; five more (ToolLLM, API-Bank, ToolBench, ToolAlpaca, plus the newly-built SeqToolQA) are held out purely for OOD benchmarking, never trained on.
  2. Combined-data fine-tuning consistently helps parameter extraction. Across the four models tested both ways, training on all five in-distribution datasets together (vs. one at a time) raises weighted-average Parameter-F1 by 1–5 points for every model, while API-F1/LCS-F1 hold flat or edge up — never down.
  3. Four of the five API-BLEND-fine-tuned models beat two existing tool-tuned checkpoints (ToolLLaMA-2-7B, Lynx-7B) on every weighted-average OOD metric (the fifth, FLAN-T5-XXL, only ties or trails on Parameter-F1) — and the paper's own text flags that those two checkpoints were built for pass-rate/win-rate evaluation, not the exact-match API/Parameter/LCS-F1 protocol they're graded on here.
