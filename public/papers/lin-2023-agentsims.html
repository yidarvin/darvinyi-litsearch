AgentSims: An Open-Source Sandbox for Large Language Model Evaluation

A pixel-game town where LLM agents plan, remember, and use tools — pitched as infrastructure for "task-based evaluation" of LLMs. It is a systems/demo paper: it ships a sandbox and a proposed evaluation paradigm, but reports no benchmark tasks, no pass rates, and no experiments of its own.

// the gap

What problem is this solving?

The paper opens with a diagnosis of three shortcomings in how LLMs were being evaluated in mid-2023: (1) constrained evaluation abilities — most new benchmarks (MMLU, C-Eval, AGIEval, and similar) are single-turn QA, so they "fail to assess the models' proficiency in adhering to instructions in dialogue or mimicking human-like social interactions"; (2) vulnerable benchmarks — as pretraining corpora balloon, "it has become more and more inevitable to inadvertently mix test cases into the training set," quietly contaminating static test sets; and (3) unobjective metrics — open-ended QA has moved from human rating to using GPT-4 as an automatic rater, but that approach "can not evaluate super GPT4-level models, and LLMs are biased toward specific features."

The authors' proposed fix is task-based evaluation: instead of scoring a model's answer to a fixed question, drop an LLM-driven agent into a simulated social-economic environment and measure whether it completes a goal — the same way a human would be judged by whether they accomplished something in the real world or in a game. Their argument for why this solves all three problems at once: task completion exercises Theory-of-Mind-level social reasoning that plain QA can't reach; emergent, diversified social behavior inside a sandbox is much harder to pre-script into a training corpus than a fixed test set; and a pass/fail rate is "an objective and fair metric" because it doesn't depend on any black-box rater. The gap they identify, though, is a paradigm gap, not a tooling gap by itself — what's actually missing, in their telling, is "a standard paradigm, an easy-to-use and extensible research platform" that lets researchers outside core NLP (behavioral economists, social psychologists) build such tasks without hand-rolling a simulation stack. AgentSims is offered as that platform.

// how it works

The method

AgentSims builds an artificial town out of two kinds of pieces: generative agents driven by LLMs, and the buildings and equipment that make up the physical environment they move through. Each agent is assembled from an LLM backbone plus three pluggable support systems, following the architecture in Figure 2 below:

  • Planning System — decomposes a goal, summarizes the agent's current situation from memory, and generates the next subtask; once a step finishes, it is written back to memory.
  • Memory System — a vector-database-backed store of an agent's daily experience stream (encoded as embeddings), retrieved when the agent needs context — e.g. recalling a relationship before chatting with someone familiar.
  • Tool-Use System — stores learned equipment-operation pairs. An agent infers an operation from an equipment's text description, the equipment's support function returns a result (hard-coded or LLM-generated), and if the outcome matches the agent's intent, that operation is kept as a reusable skill.

Buildings (a store, a gym, a house) are defined purely by which equipment they contain, and equipment is defined by descriptive text plus a support function that turns an agent's free-text operation into an outcome — e.g. asking a stove for "a cup of tea" might return the hard-coded "Meaningless operation" or a model-generated "You can not get tea from a stove," which the agent is then expected to learn from.

On top of this, the system exposes two interaction modes. User Mode gives non-specialist researchers a pixel-game-style GUI (Figure 1) to create agents (setting an LLM backbone, memory/planning system, goal, and biography from drop-down menus) and construct buildings by placing pre-configured equipment — no code required — and even lets the researcher play as an in-world "mayor" character to intervene by talking to agents directly, rather than editing their memory or goals by hand. Developer Mode targets researchers building new support mechanisms: the paper shows an abstracted Agent/LLMCaller class interface (a handful of methods — plan(), memory_store(), use() — each just formatting a prompt and calling the backbone LLM), plus JSON configuration files for defining new equipment (id, type, a support function, a description, and an optional economic schedule of prices/salaries) and buildings (a type, a 2-D block layout, and the equipment ids placed in it).

The implementation itself is a fairly ordinary web stack: a Python 3.9 Tornado backend for the web server (with the websockets library for push notifications and mysql-connector-python against a MySQL database), and a Unity/WebGL front end embedded in the page and served through nginx.

// what they found

The results

There are no experiments in this paper. AgentSims reports no pass rates, no accuracy numbers, no comparison across LLMs, and no ablation of its own Planning/Memory/Tool-Use systems — the "Example Application Tasks" section sketches three ways the sandbox could be used, not studies that were run.

  1. Subject LLM as participant. The subject model is dropped into a scene formulated by stronger-LLM-driven baseline agents — the paper's own example is embedding "colleague agents driven by GPT4 with a strong desire of bullying newcomers" and testing whether the subject model can "understand other's emotion and improve how colleagues perceive it." This is presented as an illustrative scenario, with no results reported for it.
  2. Subject LLM as mayor. The subject model is appointed mayor of the town (or president of a company) among GPT-4-driven residents, and is meant to be scored, in principle, "by analyzing the success rate of LLM mayor under different difficulties" as it recruits residents, issues policies, and builds new buildings to meet emerging problems. Again: a proposed protocol, not a measured one — no difficulty levels, mayors, or success rates are actually reported.
  3. Applications besides evaluation. The authors also pitch AgentSims as a data-generation platform for social-judgment data (pointing to Liu et al.'s prior work using simulated society for alignment data) and as a low-cost pilot-experiment tool for social scientists testing a hypothesis before running it on humans. No such generated dataset or pilot study is shown here either.

The only concrete numbers in the paper are UI mock-up values inside the figures — e.g. an example NPC's cash balance ("$10,000"), an example agent-creation "Total payment" ($12,000), and an example building purchase price ($2,000) — which are illustrative interface placeholders, not evaluation data, and should not be read as reported results.

// does it hold up?

The eval read

Judge AgentSims for what it actually is — a systems/demo paper proposing evaluation infrastructure — rather than for what its framing implies. The abstract and introduction argue at length that task-based evaluation solves the field's contamination and objectivity problems, but the paper never tests that claim on itself: there is no released task suite with fixed scoring, no pass-rate numbers for any model, and no evidence that the sandbox's social scenarios are in fact harder to memorize than QA benchmarks. The "one-for-all solution" pitch is a hypothesis, presented with the confidence of a finding.

baselines

None exist to evaluate. Every scenario in the paper is hypothetical ("we can embed colleague agents driven by GPT4…"), so there is no baseline-vs-subject-model comparison anywhere in the text — nothing to check for fairness or recency because nothing was actually run.

contamination

Asserted, not measured. The paper's central contamination argument — that "emergent social behaviors and groups are less likely to be described and included in training corpus" than QA test items — is never tested, and cuts the other way once the sandbox itself is public: the demo, the town layout, and its building/equipment templates are open-source at agentsims.com, so any specific task instance a researcher builds and shares (as the paper explicitly hopes researchers will) is just as crawlable as a leaked QA answer key once transcripts of it circulate.

what's missed

Every quantitative question the design raises is left open: does the three-system (Planning/Memory/Tool-Use) architecture actually raise task success versus a bare LLM, does GPT-4-as-surrounding-cast introduce its own bias into "subject" agent scores, what does it cost in tokens/latency to run a town of GPT-4-backed NPCs long enough to observe emergent behavior, and can a non-specialist researcher (the paper's stated target user) really author a working task through the GUI without touching the Developer Mode code — no user study or timing data is offered for that claim either.

would raise confidence

Concretely: run even one of the three sketched scenarios end to end and report a pass/success rate for 2–3 different subject LLMs; ablate Memory/Planning/Tool-Use against a plain-LLM agent on the same task; publish a small human or LLM-judged "believability" check of the emergent behavior the introduction leans on; and report GPT-4 token cost per simulated day, since every baseline NPC in the given examples is GPT-4-driven.

// bottom line

AgentSims is a reasonable, well-documented piece of tooling — a game-style GUI plus a Developer Mode SDK for wiring up LLM agents in a simulated town — and its diagnosis of QA-benchmark contamination and rater bias is a fair summary of a real 2023 problem. But the paper is not itself a benchmark and reports no benchmark results: no fixed task suite, no scores, no baselines, nothing to reproduce. Cite it as infrastructure a researcher could build an agent-evaluation task on top of, not as an evaluation result to compare against.

// takeaways

What to remember

  1. AgentSims decomposes an LLM agent into three swappable support systems — Planning, a vector-database-backed Memory, and Tool-Use (learned equipment-operation pairs) — wired to a pixel-game Unity/WebGL front end over a Tornado/MySQL backend, with a User Mode (no-code GUI) and a Developer Mode (a small Python class interface plus JSON building/equipment configs).
  2. Its pitch is "task-based evaluation": replace single-turn QA benchmarks with pass/fail social-simulation tasks (subject LLM as participant, or as mayor of a town) whose completion rate is argued to be more objective and harder to contaminate than LLM-as-judge scoring or static test sets — a claim the paper argues for but never measures.
  3. The paper itself contains zero experiments: no pass rates, no model comparisons, no ablations of its own architecture. Treat it as an open-source sandbox for building future agent-evaluation tasks, not as a benchmark with results to cite.
