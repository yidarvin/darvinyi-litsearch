ManiSkill: Generalizable Manipulation Skill Benchmark with Large-Scale Demonstrations

Most manipulation benchmarks test whether a policy can repeat one task on one object. ManiSkill asks a harder question: trained on some cabinets, chairs and buckets, can a policy open, push, or lift ones it has never seen? Four full-physics tasks over 162 PartNet-Mobility objects, scored from point-cloud/RGB-D input alone (no privileged object state), backed by ~36,000 demonstration trajectories collected not by teleoperation but by an RL-and-divide-and-conquer pipeline run object-by-object.

// the gap

What problem is this solving?

Humans learn a manipulation skill once and immediately apply it to unfamiliar instances of the same category — regardless of whether a swivel chair has an armrest, five wheels or three, a tall backrest or none, we can push it. The paper calls this ability object-level generalizable manipulation skill, and argues no existing benchmark in 2021 actually measured it. The argument is built around four design factors, each of which some prior benchmark gets wrong. Policy structure: many interactive simulators (AI2-THOR, VirtualHome, Gibson, Habitat, ThreeDWorld) support only abstract, already-solved action spaces rather than full low-level physics, so they can't pose genuinely hard manipulation control problems. Diversity of objects and tasks: robosuite, RLBench and Meta-World cover a wide range of task types but a narrow set of objects per task, so they can't test whether a skill transfers across object instances; DoorGym gets closer with procedurally generated doors of varying knob shapes and board sizes, but procedural generation "often fails to cover objects with real-world complexity" that crowd-sourced 3D scans capture. Targeted perception: benchmarks built around fixed, non-robot-mounted 2D cameras (like DoorGym's) limit what a policy can be asked to solve, where a moving 3D sensor — point clouds especially — is standard in real robotics. Targeted policy algorithms: imitation learning and offline RL need demonstration datasets that online RL doesn't, and the paper argues a benchmark should split evaluation into clear tracks rather than force every algorithm family through the same protocol.

ManiSkill's response is four matching features: a full-physics simulator (built on SAPIEN) with large intra-class object variation; four manipulation tasks chosen to span distinct motion types; an ego-centric panoramic point-cloud/RGB-D camera rather than privileged state; and a large public demonstration dataset generated at scale specifically to support learning-from-demonstrations research, alongside a three-track protocol so vision, RL and robotics researchers can each focus on the piece they study.

// how it works

The method

ManiSkill ships four tasks, each built to exemplify a different type of object motion constraint: OpenCabinetDoor (revolute joint — a single-arm robot opens a designated cabinet door), OpenCabinetDrawer (prismatic joint — same robot, opens a designated drawer), PushChair (planar motion via wheel-ground contact — a dual-arm robot pushes a swivel chair to a target location without tipping it over), and MoveBucket (unconstrained motion — a dual-arm robot lifts a bucket containing a loose ball onto a platform, with the bucket-ball system's center of mass constantly shifting). Table 1 gives each task's object counts and difficulty: OpenCabinetDoor draws on 52 unique cabinets (82 total doors, 42 train / 10 test), OpenCabinetDrawer on 35 cabinets (70 drawers, 25 train / 10 test), PushChair on 36 chairs (26 train / 10 test), MoveBucket on 39 buckets (29 train / 10 test) — 162 objects across 3 object categories in total. Motion-planning solvability is rated Easy for both cabinet tasks, Medium for MoveBucket, Hard for PushChair (where classical motion planning struggles with the chair's own complex, under-actuated dynamics).

Every robot is the same platform across tasks: a moving base plus a Sciurus body, carrying one Franka Panda arm (13 joints total) for the single-arm cabinet tasks or two (22 joints) for the dual-arm chair/bucket tasks, driven by PID joint controllers (with an operational-space Cartesian option also available). Perception comes from three cameras mounted 120° apart on the robot, 400×160 resolution each, fused into one ego-centric panoramic view; ManiSkill exposes three observation modes — state (full privileged state), pointcloud, and rgbd — but the paper is explicit that state "is not suitable for studying generalizability, as object states are not available in realistic setups," so the generalization experiments use point clouds only.

Producing demonstrations at this scale was itself an engineering problem: teleoperation doesn't scale to hundreds of objects, and a single RL agent trained across all objects in a task proved too hard given the object count and task difficulty. So the paper uses a two-stage, divide-and-conquer pipeline. First, for each task, a shared dense-reward template (not a per-object reward) is authored once and quickly sanity-checked with Model-Predictive Control via the Cross-Entropy Method — parallelized across 20 CPUs, CEM can find a successful trajectory from a single initial state in under 15 minutes when the template is workable, which is fast enough to iterate on reward design but too slow to generate the full dataset (each of the 300 initial states per training object would need its own from-scratch CEM run). Second, once a template is verified, a model-free SAC agent is trained separately per environment (per object instance) to actually generate the bulk demonstrations. The result is ~36,000 successful trajectories (300 per training object — consistent with the 122 training objects summed across Table 1's four tasks) and ~1.5M point-cloud/RGB-D frames, stored as internal environment states rather than rendered images to save disk space, with rendering scripts provided to materialize them on demand.

Asset quality gets its own multi-stage cleanup, described in §2.6: PartNet-Mobility models are first manually screened to exclude annotation errors (e.g. door hinges annotated on the same side as the handle); collision shapes are then generated by the VHACD convex-decomposition algorithm, which the paper found introduces visible artifacts like bumps and seams on some geometries (buckets specifically), fixed by hand in Blender; finally every object is verified end-to-end by attempting to learn a policy for it, with objects that fail re-processed until a policy can solve them. The benchmark also defines three evaluation tracks so different research communities can target the piece they care about: No Interactions (train only from the provided demonstrations, no further environment access — a pure supervised/offline setting well-suited to 3D-vision researchers); No External Annotations (online fine-tuning on top of No Interactions is allowed, but no new labeled data or objects); and No Restrictions (anything goes, including new annotations, motion planning, or hand-designed control rules).

For baselines, the paper adopts point-cloud input throughout (citing prior evidence that point clouds outperform RGB-D for this kind of task) and concatenates robot state to each point's features (position, RGB, and a per-point segmentation mask). Two architectures are compared: a single global PointNet backbone feeding a final MLP, and PointNet + Transformer, which runs a separate PointNet per segmentation mask, feeds the resulting per-object-part features through a Transformer encoder, and pools with attention before the final MLP — intended to let the model reason about relations between different parts/objects in the scene. Three algorithms are benchmarked on top: Behavior Cloning (BC) (imitation learning — minimize L2 distance between predicted and demonstrated action), BCQ (Batch-Constrained Q-Learning, an offline RL method), and TD3+BC (a minimalist offline-RL baseline built on Twin-Delayed DDPG). All three train exclusively from the static demonstration dataset with no further environment interaction — i.e., every baseline in this paper sits inside the No Interactions track; No External Annotations and No Restrictions are defined but not benchmarked here.

// what they found

The results

Table 2 isolates algorithmic difficulty from object-generalization difficulty by fixing everything to one single OpenCabinetDrawer environment (one object instance) and sweeping the number of available demonstration trajectories (10/30/100/300/1000, matched to 2,000/4,000/10,000/20,000/40,000 gradient steps), evaluated over 100 trajectories. PointNet+Transformer with BC is the strongest configuration at every trajectory count tested — 0.16 / 0.35 / 0.51 / 0.85 / 0.90 success as demonstrations scale from 10 to 1,000 — consistently ahead of plain PointNet with BC (0.13 / 0.23 / 0.37 / 0.68 / 0.76) at all five counts. Neither offline-RL variant ever beats BC on this single environment: PointNet+Transformer with BCQ reaches only 0.02 / 0.05 / 0.23 / 0.45 / 0.55, and with TD3+BC only 0.03 / 0.13 / 0.22 / 0.31 / 0.57 — BC's PointNet+Transformer number is strictly higher than both offline-RL numbers at all 5 trajectory counts, matching the paper's own reading: "we did not find offline RL algorithms to outperform BC," which it attributes to the demonstrations all being successful trajectories, making supervised imitation an easier fit than the harder optimization offline RL has to solve.

Table 3 is the actual object-level generalization test: each of the four tasks trains on its full training-object pool with 300 demonstrations per object (150k gradient steps — about 5 hours for BC, 35 hours for BCQ, 9 hours for TD3+BC on one RTX 2080Ti, using the PointNet+Transformer architecture), then reports mean ± std success over 5 runs on both the training objects and the 10 held-out test objects per task.

Two patterns hold across the whole table. First, training success itself is low even before generalization is asked for — the best training number anywhere is BC/PointNet+Transformer's 0.37 on OpenCabinetDrawer, and MoveBucket never exceeds 0.15 on training objects with any algorithm, a long way from Table 2's 0.85–0.90 on a single fixed environment. Second, test success never exceeds training success — checked across all 4 tasks × 4 algorithm/architecture columns (16 cells), training success is strictly higher than test success in every one of them, with the narrowest gap being MoveBucket's plain-PointNet BC (0.03 train vs. 0.02 test). The paper reads this as evidence that "existing works on 3D deep learning and learning-from-demonstrations algorithms might have been insufficient yet" for this kind of object-level generalization. One place the headline "our best agent (BC PointNet+Transformer)" framing doesn't hold task-by-task: on PushChair's test column, plain PointNet+BC actually edges out PointNet+Transformer+BC, 0.09 vs. 0.08 (a tie with BCQ and TD3+BC's own 0.08) — the architecture that wins everywhere else in the table isn't the best test performer on this one task. There is a plausible mechanism the paper never tests. Its supplement lists the segmentation masks per task: OpenCabinetDoor and OpenCabinetDrawer each get three (target handle, target door or drawer, robot), while PushChair and MoveBucket get one (the robot). The paper explains why — “we provide the robot mask and any mask that is necessary for specifying the target,” and a chair or bucket needs no disambiguation where a cabinet with many drawers does — so the asymmetry is deliberate, not an oversight. But the transformer’s advantage over plain PointNet is precisely that it can attend across mask-defined segments, and the one task where it fails to lead is a one-mask task. No ablation isolates this.

// does it hold up?

The eval read

The benchmark's central claim — that object-level generalization is hard — is well supported by its own numbers: the 16-of-16 train-beats-test sweep above isn't cherry-picked, and Table 2's much higher single-environment ceiling makes clear the drop in Table 3 isn't merely an optimization failure of the algorithms tested. But the paper's declared scope is broader than what it actually measures. It defines three evaluation tracks (No Interactions, No External Annotations, No Restrictions) specifically so RL and robotics researchers, not just vision researchers, have a track to target — yet every baseline reported (BC, BCQ, TD3+BC) trains solely from the static demonstration dataset with zero further environment interaction, which is the No Interactions track alone. The abstract's "we provide baselines using 3D deep learning and LfD algorithms" is accurate but narrower than it might read: two of the paper's own three tracks ship with no numbers at all.

A second gap sits in how the train/test object split was constructed. Section 2.1 states only that "objects are partitioned into training objects O_train and test objects O_test" — no randomization procedure, category-balancing rule, or de-duplication check against near-identical object variants is described anywhere in the main text or in the supplementary system-details section (Sec. B). Since the assets are re-modeled and manually processed from PartNet-Mobility rather than independently sourced, it's plausible some categories contain near-duplicate geometries (two very similar office chairs, say); if any such pair straddled the train/test boundary, the reported generalization gap would be an underestimate of the true difficulty. Nothing in the paper rules this out or confirms it doesn't happen.

The baselines themselves are appropriate for a 2021 benchmark paper establishing a new task, but thin by construction: one imitation-learning method and two offline-RL methods, none making use of the interaction budget the No External Annotations / No Restrictions tracks explicitly permit, and no motion-planning baseline reported even though Table 1 rates two of the four tasks (OpenCabinetDoor, OpenCabinetDrawer) as "Easy" to solve by motion planning — a natural sanity-check ceiling the paper itself flags as relevant but never runs.

baselines

BC, BCQ, TD3+BC — reasonable as an opening slate, but all three sit in the "No Interactions" track only; the paper's own "No External Annotations" and "No Restrictions" tracks (online RL, motion planning) get zero baseline numbers despite being part of its declared protocol.

contamination

Not an LLM-style leakage risk, but its structural analog is unaddressed: the train/test object partition method (random? category-stratified? de-duplicated?) is never described, so near-duplicate objects landing on both sides of the split can't be ruled out.

what's missed

No ablation isolates how much of the Table 2 → Table 3 success-rate collapse comes from optimization difficulty (many objects, one policy) versus true geometric generalization difficulty (unseen objects) — the two are confounded in every reported number.

would raise confidence

A described (ideally randomized, de-duplication-checked) train/test split protocol; at least one online-RL or motion-planning baseline to cover the paper's own other two tracks; and a controlled sweep of training-object count at fixed total demonstrations to separate multi-object optimization difficulty from generalization difficulty.

// bottom line

ManiSkill's headline result — training success consistently exceeds test success, in all 16 architecture × task cells reported — is real and well demonstrated. What's underdocumented is the machinery behind that result: how "unseen" the test objects actually are (no split-construction detail, no de-duplication check) and how much of the reported difficulty is optimization vs. generalization, since Table 2's single-environment ceiling and Table 3's multi-object numbers are never bridged by an intermediate ablation. The closest thing the paper has sits in the supplement and is never connected to the main results: Table 5 sweeps the number of training cabinets for OpenCabinetDrawer and reports 100% / 82% / 2% / 0% success at 1 / 5 / 10 / 20 objects. That is a striking collapse driven purely by object count — and it involves no generalization at all, since every one of those cabinets is a training object. But it is SAC trained from scratch in state mode with dense rewards and no demonstrations, so it cannot be laid alongside Table 2's demonstration-driven single-environment ceiling or Table 3's point-cloud results on held-out objects. It suggests the optimization half of the problem is severe on its own; it does not separate the two. The benchmark's own three-track design is broader than what this paper measures — a gap its direct successor, ManiSkill2, moves to close with a far larger task and object set.

// takeaways

What to remember

  1. ManiSkill tests object-level generalization — not task variety — across four full-physics tasks (OpenCabinetDoor, OpenCabinetDrawer, PushChair, MoveBucket) over 162 PartNet-Mobility objects in 3 categories, scored purely from egocentric point-cloud/RGB-D input, with 10 held-out test objects per task.
  2. Its ~36,000-trajectory demonstration dataset (~1.5M frames) was generated not by teleoperation but by a two-stage RL pipeline — a shared reward template quality-checked with CEM/MPC, then a per-object SAC agent run divide-and-conquer style — worth remembering whenever the dataset's demonstration quality or diversity is a downstream assumption.
  3. Object-level generalization collapses hard: the same PointNet+Transformer/BC combination that reaches up to 0.90 success in one fixed environment (Table 2) tops out at 0.37 training success and 0.12 test success once many objects are in play (Table 3) — training beats test in all 16 reported architecture × task cells — and the paper's own three-track evaluation protocol is only a third benchmarked here, a gap its direct successor ManiSkill2 was built to close.
